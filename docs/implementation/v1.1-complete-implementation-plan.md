## 1. Purpose

v1.1.0 is the first Jig minor release that intentionally extends the product beyond the Linux-browser-only operating model.

The implementation must deliver, as one coherent release candidate:

1. the corrected sticky/two-row narrow header;
2. the reminder-due attention model and corrected browser notification path;
3. precise Task-card drag/drop with an explicit insertion indicator and dedicated drag handle;
4. two-phase installation with **value-first governed onboarding** rendered inside the canonical Jig application frame: Android/narrow uses the bounded single-column flow, desktop uses the stable value/context region plus bounded setup pane, and success transitions directly to Planner;
5. one-intent GitHub repository connection with automatic protocol/access/acquisition/adoption orchestration, exposing only GitHub-required consent/code entry and genuine repository choice;
6. a native Android application using the same canonical Task/planning and portable Git data contracts;
7. direct local development APK installation and physical-device certification;
8. native Android reminders, offline-first persistence, Git synchronization and daily rollover;
9. F-Droid readiness as the first public Android distribution path;
10. one History/Settings destination-heading owner in the application header, with duplicate body title/subtitle removed;
11. Settings synchronization transparency that presents planning-data home, local safety and continuity in user language while retaining exact Local Git/Remote Git/service/database facts as secondary diagnostics;
12. one restrained, accessible motion system across desktop and Android/mobile with explicit reduced-motion behavior and no motion-dependent correctness.

This plan is binding implementation authority. UX-F0..UX-F7 remain historical closure evidence for the 2026-11-19 remediation. Physical/use acceptance on 2026-11-20 exposed bounded defects that supersede only their affected clauses without reopening unrelated architecture. IMP-18 owns compact presentation corrections; IMP-19 owns one canonical current/future scheduling rule plus feedback; IMP-20 owns recurrence-aware rollover non-accumulation; IMP-21 re-certifies the resulting candidate and evidence; IMP-22 owns the accepted cross-platform motion implementation and reduced-motion closure outside adjacent-week paging; IMP-23 is reopened and owns the corrected FR-33/SD-43 Astryx Carousel integration, single Week visual composition, removal of the parallel preview presentation and transition-fidelity certification; IMP-24 owns the shared operational-attention Banner alignment correction. Synchronization architecture, GitHub orchestration, SQLite driver ownership, recurrence enumeration/materialization and reminder/notification-delivery architecture remain unchanged except where existing owners are consumed. J110-IMP-09 remains complete. J110-IMP-15 cannot close until IMP-18..24 close; issue #31 remains the separate live Linux/Desktop acceptance gate.

## 2. Non-negotiable architecture

The following rules apply to every task.

- There is one canonical Task model and one TaskCommand model in src/core.
- There is one canonical planning implementation for create/edit/move/complete/reopen/delete/rollover.
- There is one portable Jig record contract and dataset identity shared by Linux and Android.
- SQLite remains local operational authority. Mobile support must not create a cloud Task store.
- The shared persistence semantics live once in TypeScript. Linux and Android provide low-level SQLite drivers only.
- Platform boundaries are imperative-shell boundaries, not new domain layers.
- Do not add DTO/ViewModel hierarchies, repository/service/use-case class stacks, workflow frameworks, parallel Task projections or a second mobile model.
- TypeScript remains strict. External values are narrowed at the smallest boundary. Do not add any, double casts, non-null assertions or unchecked assertion chains as shortcuts.
- Git remains authoritative for clone/fetch/push transport, repository topology, refs, remote history, credentials and reconciliation. Jig must not become a branch/remote/conflict manager.
- Existing local Git repositories remain provider-neutral and valid even with no remote.
- GitHub-specific behavior exists only for the optimized acquisition/authentication path.
- User interaction is intent-first across desktop and Android. Internal protocol, polling, access-discovery, clone, validation, adoption, persistence and synchronization phases must not become user-operated workflow merely because they exist as implementation steps.
- Onboarding is a body state inside the one canonical Jig AppShell/header/body composition from first render. Do not create or preserve a standalone setup utility shell. The governed v1.1 mobile/desktop reference files are binding presentation inputs: product value precedes provider mechanics; desktop uses the stable value/context + bounded setup-pane composition; Android/narrow uses the bounded single-column composition.
- GitHub Device Flow has one unavoidable provider interaction: the GitHub-generated 8-character user code must be visible and copyable while the user completes GitHub-owned verification. Jig owns automatic polling, access re-check, acquisition and continuation around that provider step.
- GitHub installation/repository access remains GitHub-owned. Jig may hand the user to GitHub and observe the result; it must not reproduce installation/access controls or require manual Refresh access.
- Repository/install enumeration is authoritative only after all GitHub pagination is consumed. Never infer zero/one/many eligible repositories from the first page.
- Android v1.1.0 is the only native mobile target. Do not add iOS build/signing/App Store work.
- F-Droid is the first public Android distribution target. Development APKs are local certification artifacts, not a second public v1.1 Android channel. Google Play is deferred.
- Keep Astryx as the UI/design-system authority. Do not add another component/theme framework.
- The Planner drag/drop implementation has one owner. Pangea is rejected by the physical gate; do not run it, legacy dnd-kit code, a second drag framework or parallel custom sensors beside the proof-gated current dnd-kit candidate.
- package.json.version remains 1.0.6 throughout ordinary implementation work. The version changes to 1.1.0 only in the later governed release/v1.1.0 metadata PR.
- Every ordinary implementation PR updates CHANGELOG.md [Unreleased].
- `v1.1` is the single implementation/integration authority until physical certification is complete. Ordinary v1.1 implementation, documentation, evidence and device-correction work lands on `v1.1`, not `master` and not parallel `work/v1.1-*` branches. Temporary CI/transport branches are non-authoritative and must be retired after their accepted content is integrated. `package.json.version` remains at the published version until the governed release transition. The final promotion from `v1.1` to `master` carries `SemVer impact: **minor**` / `Target release: **1.1.0**` metadata as required by the permanent guard.
- Local GitHub Actions rehearsal is an optional developer preflight, not a release-candidate closure gate and not a second CI architecture. The permanent hosted Verify/Release workflows are authoritative. If `act` is used, reuse the permanent workflows wherever possible and keep all temporary workflow/event/secrets scaffolding outside the repository.

## J110-IMP-17 — Cross-installation synchronization convergence and integrity

### A. Architecture and ownership

Implement the minimum architecture required by SD-41:

1. Add or reuse **one pure strictly typed classifier in `src/core`** for already-observed synchronization facts. It returns the governed result only; it performs no I/O and has no Git/provider/SQLite/UI dependency.

### B. Normal FR-24 outcomes

Implement and test the four ordinary cases before edge-case handling:

- **Local only:** no configured synchronization remote remains healthy; local SQLite and local portable export continue normally.
- **Synchronized:** local/remote portable heads are equal; report Up to date only when the current SQLite revision is represented by that head.
- **Adopt remote:** remote is a validated descendant of local and there is no unsynchronized local SQLite revision; adopt automatically.
- **Push local:** local is a descendant of remote and contains the current local work; ordinary non-forced push.

### C. SYNC-E1 — both sides changed

Required implementation:

1. Observe/fetch the remote **before** creating another remote-backed local snapshot.
2. If the remote advanced while SQLite contains an unsynchronized local revision, do not create a new Git snapshot on the stale local head.
3. Preserve local SQLite and remote state.
4. Return the existing generic `sync-issue` / Needs attention outcome.
5. If the Git heads are already divergent, use the same Attention result.
6. Do not attempt semantic Task reconciliation or Git merge/rebase/force.

Required proof:
- remote-ahead + pending SQLite produces no new stale-base local Git commit;
- already-divergent heads remain unchanged;
- local planning remains usable.

### D. SYNC-E2 — remote advances during push

Required implementation:

1. Treat non-fast-forward/rejected push as evidence that observed facts are stale.
2. The next remote operation must be observation/classification, not repetition of the same push.
3. If the newly observed state is a normal FR-24 case, continue from that case.
4. Otherwise settle to the governed Attention path.
5. Use the existing retry/backoff owner only; do not create a second race-retry subsystem.

Required proof:
- a controlled remote-advance race records observation before any second push;
- no stale push livelock occurs.

### E. SYNC-E3 — ambiguous push acknowledgement

Required implementation:

1. When push transport fails in a way that does not prove server rejection, do not infer failure.
2. Re-observe the remote before another write.
3. If the remote contains the exact local exported head, mark synchronization successful.
4. Otherwise classify the observed state through the same normal/E1 rules.

Required proof:
- simulated accepted-push/lost-response does not create another semantic commit or blind duplicate push.

### F. SYNC-E4 — temporary authentication/transport failure

Required implementation:

1. Preserve the existing local-first SQLite save semantics.
2. Reuse the existing bounded retry/backoff/reconnect ownership.
3. Ensure the platform shell/transport has a bounded remote-operation timeout appropriate to its existing mechanism so one hung operation cannot occupy synchronization indefinitely.

Required proof:

- retry/status uses the existing owner;

### G. SYNC-E5 — restart/crash between durable boundaries

Required proof:
