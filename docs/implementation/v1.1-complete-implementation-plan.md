# Jig v1.1.0 — complete implementation plan

**Status:** IN PROGRESS — implementation is underway on the v1.1 branch; J110-IMP-08 physical APK evidence and the J110-IMP-09 physical Android drag/drop gate remain mandatory before downstream gated Android work proceeds.  
**Target release:** v1.1.0.  
**Plan date:** 2026-11-18.  
**Functional authority:** docs/requirements/v1.1-mobile-functional-design.md, JIG-110-FR-01 through JIG-110-FR-31.  
**Technical authority:** docs/architecture/v1.1-mobile-technical-solution.md, JIG-110-SD-01 through JIG-110-SD-41.  
**Repository governance:** AGENTS.md after J110-IMP-01 canonical adoption.  
**Release authority:** docs/releases/README.md.  
**Current released baseline:** Jig v1.0.6 on master.

## 1. Purpose

v1.1.0 is the first Jig minor release that intentionally extends the product beyond the Linux-browser-only operating model.

The implementation must deliver, as one coherent release candidate:

1. the corrected sticky/two-row narrow header;
2. the reminder-due attention model and corrected browser notification path;
3. precise Task-card drag/drop with an explicit insertion indicator and dedicated drag handle;
4. two-phase Linux installation with in-application repository setup;
5. low-friction GitHub repository acquisition while preserving existing local-repository/provider-neutral behavior;
6. a native Android application using the same canonical Task/planning and portable Git data contracts;
7. direct local development APK installation and physical-device certification;
8. native Android reminders, offline-first persistence, Git synchronization and daily rollover;
9. F-Droid readiness as the first public Android distribution path;
10. one History/Settings destination-heading owner in the application header, with duplicate body title/subtitle removed;
11. Settings synchronization transparency that separately presents local Jig Git commit state and the credential-free configured remote repository/synchronization state.

This plan is binding implementation authority. The implementation team must not invent substitute architectures where this plan contains a stop gate.

## 2. Non-negotiable architecture

The following rules apply to every task.

- There is one canonical Task model and one TaskCommand model in src/core.
- There is one canonical planning implementation for create/edit/move/complete/reopen/delete/rollover.
- There is one portable Jig record contract and dataset identity shared by Linux and Android.
- SQLite remains local operational authority. Mobile support must not create a cloud Task store.
- The shared persistence semantics live once in TypeScript. Linux and Android provide low-level SQLite drivers only.
- Platform boundaries are imperative-shell boundaries, not new domain layers.
- Do not add DTO/ViewModel hierarchies, repository/service/use-case class stacks, workflow frameworks, parallel Task projections or a second mobile model.
- TypeScript remains strict. External values are narrowed at the smallest boundary. Do not add any, double casts, non-null assertions or unchecked assertion chains as shortcuts.
- Git remains authoritative for clone/fetch/push transport, repository topology, refs, remote history, credentials and reconciliation. Jig must not become a branch/remote/conflict manager.
- Existing local Git repositories remain provider-neutral and valid even with no remote.
- GitHub-specific behavior exists only for the optimized acquisition/authentication path.
- Android v1.1.0 is the only native mobile target. Do not add iOS build/signing/App Store work.
- F-Droid is the first public Android distribution target. Development APKs are local certification artifacts, not a second public v1.1 Android channel. Google Play is deferred.
- Keep Astryx as the UI/design-system authority. Do not add another component/theme framework.
- The Planner drag/drop implementation has one owner. Do not run dnd-kit and Pangea DnD in parallel.
- package.json.version remains 1.0.6 throughout ordinary implementation work. The version changes to 1.1.0 only in the later governed release/v1.1.0 metadata PR.
- Every ordinary implementation PR updates CHANGELOG.md [Unreleased].
- Every ordinary v1.1 implementation PR targets `master`, leaves `package.json.version` at the currently published version, and declares `SemVer impact: **minor**` plus `Target release: **1.1.0**` in the PR body so the permanent release-metadata guard can admit it.
- Local GitHub Actions rehearsal is a preflight/certification aid, not a second CI architecture. Reuse the permanent workflows with `act` wherever possible. Temporary workflow/event/secrets scaffolding must live outside the repository and must not survive into a commit, PR or release candidate.

## 3. Current-state facts that must be replaced

The implementation begins from the released v1.0.6 state.

1. docs/product/product-definition.md still says independent phone installation/synchronization is deferred.
2. docs/requirements/planning-workbench.md and AGENTS.md still govern a one-row narrow header with a <=56px total-height budget.
3. AGENTS.md and the canonical v1.0.6 UX design still declare dnd-kit and whole-card drag activation as authoritative.
4. docs/README.md still describes v1.0.6 as unreleased and says phone installation remains deferred.
5. src/shell/main.ts loads JigConfig, acquires a repository lease and opens SQLite before it can serve the application. A fresh unconfigured installation cannot start.
6. JigConfig currently contains exactly version, repository_path and http_port. v1.1 must preserve that shape; missing config is the bootstrap state.
7. scripts/install.sh currently expects --repo or --repo-url + --checkout for a normal installation.
8. ui/src/reminder.tsx uses sessionStartedAt and explicitly suppresses reminders that became due before the current browser session.
9. browser reminder delivery uses direct new Notification(...) and the browser acceptance test replaces the complete Notification constructor, so it does not prove the real production delivery path.
10. reminder card attention is not currently a time-derived Planner state.
11. src/shell/sqlite.ts directly owns canonical persistence semantics and synchronous bun:sqlite mechanics in one module.
12. Android has no native shell, SQLite driver, Git adapter, secure credential adapter, lifecycle integration or local-notification adapter.
13. current Planner drag/drop uses @dnd-kit/react and @dnd-kit/dom, treats the Task row as the pointer source, highlights the whole date drop zone, and does not expose an exact before/after insertion result.
14. the permanent Verify and Release workflows currently certify Linux only, and the repository has no committed `.actrc`, `.github/actions/` local-action harness or local-only GitHub Actions workflow. v1.1 must preserve that absence: local Actions rehearsal uses the permanent workflows plus ephemeral files outside the repository.
15. the GitHub Release asset matrix remains Linux-only and stays Linux-only for v1.1.0; Android public distribution is through F-Droid.
16. HistoryView and SettingsView currently each render a body `.jig-reference-heading` even though PlannerHeader already renders the active History/Settings destination title; v1.1 removes that duplicate and moves the existing subtitle into the header owner.
17. `ServiceStatus.repository_status` currently collapses local Jig Git commit and remote synchronization into one coarse value, while Settings shows only repository path + Local save. v1.1 replaces that presentation contract with the structured SD-41 status and shows the actual credential-free synchronization remote separately.

## J110-IMP-16 — Bounded recurring Tasks

**Closes:** JIG-110-FR-29; JIG-110-SD-39; recurrence-driven versioning portions of JIG-110-SD-11, SD-20/32 and SD-30.

**Prerequisite:** J110-IMP-05 Linux parity gate passed. This task deliberately follows the persistence-owner refactor because recurrence is a canonical schema/portable-format change and must have one shared implementation before Android SQLite certification.

**Primary files**
- src/core/task.ts and one small pure recurrence module if needed;
- src/core/planning.ts;
- src/persistence/sqlite.ts;
- portable serializer/validator;
- src/protocol.ts only where the canonical command/result contract requires it;
- ui Task workspace/editor/card presentation;
- reminder reconciliation tests/adapters only as consumers of materialized Tasks;
- schema/portable migration and cross-platform certification tests.

**Required implementation**

1. Add the canonical recurrence types from SD-39 exactly once: `Weekday`, weekly/monthly `RecurrencePattern`, `RecurrenceSeries` and the pure date enumerator/reconciler.
2. Extend canonical Task with nullable `recurrence_series_id` + `recurrence_occurrence_date`; enforce both-null/both-non-null and immutable occurrence-slot semantics.
3. Add `create.recurrence` and one `set_recurrence` command. Do not overload ordinary `edit` into an implicit multi-Task series update.
4. Materialize the complete finite occurrence set through the required inclusive end date in one canonical transaction. No virtual Task projection, lazy recurrence daemon or platform-specific generator.
5. Weekly semantics: positive whole-number `interval_weeks`, non-empty unique weekday set, Monday-based week-zero anchoring, exact every-N-weeks behavior; all seven weekdays is the daily pattern.
6. Monthly semantics: exact day `1..31`; skip months without that day rather than clamping to month-end.
7. Each generated occurrence is a normal Task with fresh ID/order/completion/reminder lifecycle. Copy seed/invoking occurrence title, priority, context, reference, note and reminder time **only when that occurrence is created**. Thereafter those fields are occurrence-local; ordinary edits must never propagate into existing sibling occurrences.
8. Ordinary complete/reopen/move/reschedule/delete is occurrence-only. Rollover changes `scheduled_date` only and never changes recurrence slot/cadence.
9. Repeat changes update the one shared series configuration from any occurrence and reconcile affected outstanding slots without rewriting ordinary Task fields on existing siblings. Preserve completed History and matching outstanding Task IDs. Newly introduced slots copy the invoking occurrence at creation time only. **Repeat-off / Stop repeating retains the invoking Task as one-off and removes every other outstanding Task in the series, including rolled/overdue siblings, in the same transaction.** Individual Delete remains occurrence-only.
10. Advance SQLite schema to v3 with recurrence-series persistence and v2→v3 migration that leaves existing Tasks non-recurring. Preserve one shared TypeScript migration for Linux and Android drivers.
11. Advance portable format to v2 with `recurrences/<uuid>.json` plus nullable Task recurrence fields. Accept portable v1 as upgrade input and emit v2 after adoption. Validate series references and unique `(series, occurrence_date)` pairs before adoption.
12. Add Repeat to the unified Task workspace on every recurring occurrence and one compact accessible recurring-card indicator/summary. Every occurrence resolves the same `RecurrenceSeries` configuration, while title/priority/context/reference/note/reminder fields remain occurrence-local. Expose a distinct Stop repeating/Remove recurrence series action beside the ordinary occurrence-only Delete. Use Astryx public primitives; no recurrence modal, destination, DTO hierarchy or second Task editor.
13. Do not create recurrence-specific reminder delivery state. Materialized Tasks use the existing reminder due/browser/Android scheduling owners; copied reminder time repeats per occurrence.
14. A successful recurrence mutation increments the durable revision once, marks sync pending once and refreshes canonical UI state because multiple Tasks may change.

**Mandatory recurrence gate**

- pure date-set tests: one/multiple/all-seven weekdays, every-four-weeks, end-date inclusion, month/year transitions, monthly 28/29/30/31 skip semantics;
- seed + complete finite materialization with canonical per-date insertion/order;
- complete/reopen/move/delete one occurrence without sibling/cadence mutation;
- rollover one occurrence while later recurrence dates remain exact;
- repeated reminder inheritance and due-state behavior;
- shared Repeat configuration is identical from every occurrence while ordinary Task-field edits remain independent;
- Stop repeating retains the invoking Task as one-off, preserves completed history and removes every other outstanding series occurrence—including rolled/overdue siblings—in one mutation;
- individual Delete remains occurrence-only and does not stop recurrence;
- SQLite v2→v3 upgrade, rollback and restart;
- portable v1→v2 adoption/export plus complete-snapshot validation;
- Linux portable round trip before Android driver work begins.

Failure means stop and repair the single canonical recurrence owner/migration. Do not introduce a separate Android recurrence implementation or virtual UI recurrence projection.

Do not infer release success from workflow color alone. After the Release workflow completes, verify the public state directly.

All of the following must be true:

- `master:package.json` reports `1.1.0`;
- `CHANGELOG.md` contains dated `[1.1.0]` and an empty `[Unreleased]`;
- `docs/releases/v1.1.0.md` exists and targets `v1.1.0`;
- the permanent Release workflow executed release jobs rather than `should_release=false`;
- annotated tag `v1.1.0` exists and resolves to the exact certified merged release commit;
- GitHub Release `v1.1.0` exists, is non-draft and is not a prerelease;
- the release contains exactly the required supported Jig assets:
  - `jig-linux-x64.tar.gz`;
  - `jig-linux-arm64.tar.gz`;
  - `jig-install.sh`;
  - `SHA256SUMS`;
- download those four assets into a clean temporary directory and run `sha256sum -c SHA256SUMS`;
- both archives contain the expected `RELEASE.json`, whose version is `1.1.0`, whose Git commit is the exact release commit and whose architecture matches the bundle;
- clean version-pinned installer smokes use `releases/download/v1.1.0/jig-install.sh` rather than `latest` and prove both (a) configured `--repo` automation reaches healthy status and (b) no-repository installation reaches the bootstrap/setup surface;
- no Android APK is present as a supported GitHub Release asset.

Only after every item above is true is **Jig v1.1.0 released**.

### J110-REL-05 — Submit and verify the F-Droid distribution

After J110-REL-04 has established the immutable public `v1.1.0` source tag:

1. derive the external F-Droid `fdroiddata` submission from the reviewed `distribution/fdroid/metadata/com.pontivus.jig.yml` candidate;
2. ensure the F-Droid recipe references the immutable `v1.1.0` source/tag, package ID `com.pontivus.jig`, `versionName 1.1.0` and governed `versionCode 1001000`;
3. rerun `fdroid lint` and `fdroid build` against the exact immutable `v1.1.0` tagged source and exact submitted metadata; this is the authoritative F-Droid source-build validation for the released version;
4. submit through the normal F-Droid contribution/review path;
5. record the external submission reference/status in release evidence/documentation without modifying immutable v1.1.0 product artifacts;
6. do not claim public Android availability until F-Droid actually publishes the package;
7. once published, verify the F-Droid listing/package identity/version corresponds to Jig `1.1.0` and update only forward/current documentation through an ordinary post-release documentation PR if a publication-status statement needs to change.

F-Droid review timing is external to Jig release validity. The Linux GitHub release may be valid before F-Droid publication, while the product must continue to describe Android availability accurately.

### Release-complete definition

The project has three deliberately distinct milestones:

1. **Implementation complete** — IMP-01..IMP-15 closed on a verified `master` candidate; package version has not yet transitioned.
2. **Jig v1.1.0 released** — REL-01..REL-04 complete; immutable tag and certified Linux GitHub Release are publicly verified.
3. **Android publicly available on F-Droid** — REL-05 external review/publication is complete and the published F-Droid package has been directly verified.

Never collapse these states into one green workflow result.

## 9. Explicit v1.1.0 non-goals

Do not add:

- iOS build/runtime/App Store support;
- Google Play publication;
- multiple active planning repositories;
- arbitrary Android filesystem repository import;
- Git branch/remote/rebase/merge/conflict UI;
- repository creation/provisioning;
- a Pontivus sync/token backend;
- GitHub Contents API as a substitute for Git;
- push-notification infrastructure;
- reminder snooze/acknowledgement;
- project-management/workflow features;
- a second Task/mobile data model;
- Room or another Task ORM/model owner;
- parallel drag libraries;
- another design system.

## 10. Completion definition

The v1.1.0 implementation is complete only when:

- IMP-01 through IMP-16 are closed;
- all four hard gates have passed;
- all 31 FRs are demonstrably satisfied;
- all 41 SD contracts are implemented or explicitly proven non-code governance constraints;
- Linux v1.0.6 upgrade behavior remains compatible;
- Android physical-device evidence exists;
- Linux↔Android portable-data interoperability passes;
- F-Droid pre-release readiness/recipe/dependency validation passes; exact `v1.1.0` tagged-source validation is a REL-05 release-distribution step;
- permanent hosted Verify has passed both Linux/browser and Android build-certification jobs;
- local Actions preflight has exercised the permanent Verify workflow and all safely emulatable changed release-certification logic;
- no temporary local GitHub Actions workflow/action/event/secrets/runner scaffolding remains in the repository;
- CHANGELOG.md [Unreleased] accurately describes the release;
- package.json.version is still 1.0.6 until the separate release/v1.1.0 metadata transition.

A partial Android demo, a browser-only green suite, or a successful implementation PR merge is not v1.1.0 completion.

Implementation completion also does not mean the version is released. Public release requires J110-REL-01 through J110-REL-04; public Android availability additionally requires J110-REL-05.
