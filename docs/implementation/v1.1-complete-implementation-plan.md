## 1. Purpose

v1.1.0 is the first Jig minor release that intentionally extends the product beyond the Linux-browser-only operating model.

The implementation must deliver, as one coherent release candidate:

1. the corrected sticky/two-row narrow header;
2. the reminder-due attention model and corrected browser notification path;
3. precise Task-card drag/drop with an explicit insertion indicator and dedicated drag handle;
4. two-phase installation with onboarding rendered inside the canonical Jig application frame from first launch on desktop and Android;
5. one-intent GitHub repository connection with automatic protocol/access/acquisition/adoption orchestration, exposing only GitHub-required consent/code entry and genuine repository choice;
6. a native Android application using the same canonical Task/planning and portable Git data contracts;
7. direct local development APK installation and physical-device certification;
8. native Android reminders, offline-first persistence, Git synchronization and daily rollover;
9. F-Droid readiness as the first public Android distribution path;
10. one History/Settings destination-heading owner in the application header, with duplicate body title/subtitle removed;
11. Settings synchronization transparency that presents planning-data home, local safety and continuity in user language while retaining exact Local Git/Remote Git/service/database facts as secondary diagnostics.

This plan is binding implementation authority. The implementation team must not invent substitute architectures where this plan contains a stop gate.

## 2. Non-negotiable architecture

The following rules apply to every task.

- There is one canonical Task model and one TaskCommand model in src/core.
- There is one canonical planning implementation for create/edit/move/complete/reopen/delete/rollover.
- There is one portable Jig record contract and dataset identity shared by Linux and Android.
- SQLite remains local operational authority. Mobile support must not create a cloud Task store.
- The shared persistence semantics live once in TypeScript. Linux and Android provide low-level SQLite drivers only.
- Platform boundaries are imperative-shell boundaries, not new domain layers.
- Do not add DTO/ViewModel hierarchies, repository/service/use-case class stacks, workflow frameworks, parallel Task projections or a second mobile model.
- TypeScript remains strict. External values are narrowed at the smallest boundary. Do not add any, double casts, non-null assertions or unchecked assertion chains as shortcuts.
- Git remains authoritative for clone/fetch/push transport, repository topology, refs, remote history, credentials and reconciliation. Jig must not become a branch/remote/conflict manager.
- Existing local Git repositories remain provider-neutral and valid even with no remote.
- GitHub-specific behavior exists only for the optimized acquisition/authentication path.
- User interaction is intent-first across desktop and Android. Internal protocol, polling, access-discovery, clone, validation, adoption, persistence and synchronization phases must not become user-operated workflow merely because they exist as implementation steps.
- Onboarding is a body state inside the one canonical Jig AppShell/header/body composition from first render. Do not create or preserve a standalone setup utility shell.
- GitHub Device Flow has one unavoidable provider interaction: the GitHub-generated 8-character user code must be visible and copyable while the user completes GitHub-owned verification. Jig owns automatic polling, access re-check, acquisition and continuation around that provider step.
- GitHub installation/repository access remains GitHub-owned. Jig may hand the user to GitHub and observe the result; it must not reproduce installation/access controls or require manual Refresh access.
- Repository/install enumeration is authoritative only after all GitHub pagination is consumed. Never infer zero/one/many eligible repositories from the first page.
- Android v1.1.0 is the only native mobile target. Do not add iOS build/signing/App Store work.
- F-Droid is the first public Android distribution target. Development APKs are local certification artifacts, not a second public v1.1 Android channel. Google Play is deferred.
- Keep Astryx as the UI/design-system authority. Do not add another component/theme framework.
- The Planner drag/drop implementation has one owner. Do not run dnd-kit and Pangea DnD in parallel.
- package.json.version remains 1.0.6 throughout ordinary implementation work. The version changes to 1.1.0 only in the later governed release/v1.1.0 metadata PR.
- Every ordinary implementation PR updates CHANGELOG.md [Unreleased].
- Every ordinary v1.1 implementation PR targets `master`, leaves `package.json.version` at the currently published version, and declares `SemVer impact: **minor**` plus `Target release: **1.1.0**` in the PR body so the permanent release-metadata guard can admit it.
- Local GitHub Actions rehearsal is an optional developer preflight, not a release-candidate closure gate and not a second CI architecture. The permanent hosted Verify/Release workflows are authoritative. If `act` is used, reuse the permanent workflows wherever possible and keep all temporary workflow/event/secrets scaffolding outside the repository.

## 3. Current-state facts that must be replaced

The implementation begins from the released v1.0.6 state.

1. docs/product/product-definition.md still says independent phone installation/synchronization is deferred.
2. docs/requirements/planning-workbench.md and AGENTS.md still govern a one-row narrow header with a <=56px total-height budget.
3. AGENTS.md and the canonical v1.0.6 UX design still declare dnd-kit and whole-card drag activation as authoritative.
4. docs/README.md still describes v1.0.6 as unreleased and says phone installation remains deferred.
5. src/shell/main.ts loads JigConfig, acquires a repository lease and opens SQLite before it can serve the application. A fresh unconfigured installation cannot start.
6. JigConfig currently contains exactly version, repository_path and http_port. v1.1 must preserve that shape; missing config is the bootstrap state.
7. scripts/install.sh currently expects --repo or --repo-url + --checkout for a normal installation.
8. ui/src/reminder.tsx uses sessionStartedAt and explicitly suppresses reminders that became due before the current browser session.
9. browser reminder delivery uses direct new Notification(...) and the browser acceptance test replaces the complete Notification constructor, so it does not prove the real production delivery path.
10. reminder card attention is not currently a time-derived Planner state.
11. src/shell/sqlite.ts directly owns canonical persistence semantics and synchronous bun:sqlite mechanics in one module.
12. Android has no native shell, SQLite driver, Git adapter, secure credential adapter, lifecycle integration or local-notification adapter.
13. current Planner drag/drop uses @dnd-kit/react and @dnd-kit/dom, treats the Task row as the pointer source, highlights the whole date drop zone, and does not expose an exact before/after insertion result.
14. the permanent Verify and Release workflows currently certify Linux only, and the repository has no committed `.actrc`, `.github/actions/` local-action harness or local-only GitHub Actions workflow. v1.1 must preserve that absence: local Actions rehearsal uses the permanent workflows plus ephemeral files outside the repository.
15. the GitHub Release asset matrix remains Linux-only and stays Linux-only for v1.1.0; Android public distribution is through F-Droid.
16. HistoryView and SettingsView currently each render a body `.jig-reference-heading` even though PlannerHeader already renders the active History/Settings destination title; v1.1 removes that duplicate and moves the existing subtitle into the header owner.
17. `ServiceStatus.repository_status` in the released baseline collapses local Jig Git commit and remote synchronization into one coarse value. The v1.1 implementation introduced the structured SD-41 status correctly, but its primary Settings presentation overexposes Local Git/Remote Git/service/path mechanics rather than the amended user-level continuity model.
18. The current v1.1 `App()` renders bootstrap through a standalone `SetupView`/`<main class="jig-setup">` branch outside the configured Astryx `AppShell`; this violates the amended requirement that onboarding is a Jig application state inside the canonical header/body shell from first render on desktop and Android.
19. The current v1.1 setup/reconnect UI exposes the GitHub technical process as user workflow: device authorization controls plus manual Refresh/Grant/Manage access progression and separate repository acquisition actions. Those controls are defect evidence, not preservation targets.
20. The current GitHub installation/repository adapters request `per_page=100` but do not consume all pages. A repository beyond the first page can therefore be omitted from the authoritative chooser/access decision.
21. Current setup/reconnect React code owns protocol progression/polling callbacks. The amended SD-29/SD-38 contract moves Device Flow/access/acquisition continuation behind the shared orchestration owner; React emits user intents and observes a coarse presentation state only.
22. Existing setup/reconnect browser tests that assert Refresh access, Grant repository access, Manage GitHub access or manual authorization refresh are regression tests for the superseded behavior and must be replaced, not preserved.

### Physical-device dependency classification

For this plan, **device-required** means a real physical Android handset. Browser tests, JVM/unit tests, Android source builds, Gradle checks and Android emulator execution are **non-device** work.

The execution order is binding:

**Phase 1 — non-device implementation and certification first**

Complete all implementation and all acceptance that can be proved without physical hardware:

| Task | Physical device required to close this task? | Rule |
|---|---:|---|
| J110-IMP-01 | No | documentation/governance only |
| J110-IMP-02 | No | core + browser reminder behavior |
| J110-IMP-03 | No | responsive/browser header and Settings/History composition |
| J110-IMP-04 | No | desktop/browser Pangea implementation; physical touch proof deferred |
| J110-IMP-05 | No | shared persistence refactor/Linux parity |
| J110-IMP-06 | No | Linux bootstrap/onboarding shell/local repository/Settings projection |
| J110-IMP-07 | No | shared GitHub orchestration + Linux/browser controlled/live-where-available acceptance; no Android handset required |
| J110-IMP-08 | No | Android shell/build/emulator development loop; physical install explicitly deferred |
| J110-IMP-10 | No | Android SQLite/rollover via automated/emulator parity |
| J110-IMP-11 | No | Android Git feasibility/implementation through automated/emulator gate |
| J110-IMP-12 | No | Android onboarding/sync implementation and emulator certification; physical provider/resume proof deferred |
| J110-IMP-13 | No | Android reminder implementation and emulator-testable scheduling/permission behavior; physical OS-delivery proof deferred |
| J110-IMP-14 | No | F-Droid/CI/release tooling |
| J110-IMP-16 | No | recurrence/schema/portable-data implementation |

No physical-device task may be used as a prerequisite for any Phase-1 task. Failure of a non-device feasibility gate returns to the relevant solution design before hardware testing.

**Phase 2 — physical-device certification only after Phase 1 is complete**

1. **J110-IMP-09** — physical Android drag/drop certification for the already implemented Pangea behavior.
2. **J110-IMP-15 physical matrix** — exact candidate APK: first launch/onboarding shell, GitHub Device Flow/provider return, native Git/private repository, app-private persistence/restart, lifecycle/resume, native reminders/permissions/exactness, safe-area/header, reconnect, uninstall/reacquisition and remaining device-only evidence.
3. **J110-IMP-15 final closure** — combine the already-green non-device evidence with the physical-device evidence and close the implementation candidate.

A physical-device failure may reopen the affected implementation/solution contract, but it must not cause unrelated non-device work to be deferred in advance.

Hard stop rules:

- If J110-IMP-10 cannot prove shared SQLite semantic parity in automated/emulator certification, stop. Do not duplicate Task persistence semantics in Kotlin.
- If J110-IMP-11 cannot prove the selected isomorphic-git adapter through the automated/emulator feasibility matrix, stop. Do not substitute JGit, libgit2, GitHub Contents API or a proxy without a reviewed technical-design amendment.
- If F-Droid dependency/build validation discovers a required non-FLOSS dependency, the dependency must be replaced or the technical design amended before Android is submission-ready.
- If the final J110-IMP-09 physical drag gate or any physical-device requirement in J110-IMP-15 fails, stop release-candidate closure and return the affected SD contract to design review. Do not add an unreviewed substitute architecture merely to pass hardware certification.

## 7. PR/wave boundaries

The work should be split into reviewable waves, but each wave must leave the repository internally coherent. **Waves A–J are non-device work and must complete before Wave K begins.** Emulator execution remains part of non-device implementation; only Wave K requires a physical Android handset.

Recommended PR boundaries:

- Wave A: IMP-01 canonical authority only.
- Wave B: IMP-02 + IMP-03 + IMP-04 user-facing desktop/browser corrections.
- Wave C: IMP-06 canonical onboarding shell/local-repository path + user-level Settings projection.
- Wave D: IMP-07 shared GitHub intent/data-flow orchestration + desktop managed acquisition.
- Wave E: IMP-08 Android shell/deterministic dev APK build only; no physical device dependency.
- Wave F: IMP-05 shared persistence refactor with Linux parity, then IMP-16 recurrence/schema/portable work.
- Wave G: IMP-10 Android SQLite/rollover with automated/emulator parity.
- Wave H: IMP-11 automated/emulator Git proof gate, then IMP-12 Android reuse of the corrected onboarding shell/orchestration + offline sync.
- Wave I: IMP-13 Android reminders with automated/emulator acceptance.
- Wave J: IMP-14 distribution/CI tooling.
- Wave K — **physical device only, after A–J are green**: IMP-09 physical drag gate, then IMP-15 remaining physical-device matrix and final certification/evidence closure. Local `act` rehearsal may be used as an optional preflight but is not a closure gate.

Do not combine a failed feasibility gate and an architectural substitute in one implementation PR. A failed gate returns to design review.

## 8. v1.1.0 release ceremony after implementation

IMP-15 closes **implementation readiness**, not publication. A valid v1.1.0 release then follows the canonical `docs/releases/README.md` ceremony exactly.

### J110-REL-01 — Freeze the exact implementation candidate on `master`

Prerequisites:

- IMP-01 through IMP-16 are closed;
- all hard gates passed;
- the final implementation/evidence PR is merged to `master`;
- the exact resulting `master` commit has a successful permanent hosted Verify run, including Linux/browser and Android build-certification jobs;
- `CHANGELOG.md [Unreleased]` contains the complete v1.1.0 public change set;
- `package.json.version` is still the previously published version;
- no temporary local Actions/test/release scaffolding remains.

Record that exact `master` SHA as the **implementation candidate SHA**. Do not add runtime/product fixes to the later release branch. Any product/code correction discovered after this point returns to an ordinary implementation PR on `master`, re-runs IMP-15 evidence as affected, and establishes a new candidate SHA.

### J110-REL-02 — Create and verify the metadata-only release PR

Create branch **`release/v1.1.0`** from the exact verified implementation candidate SHA.

The release branch changes only files admitted by `scripts/verify-release.ts`:

- `package.json`;
- `CHANGELOG.md`;
- `docs/releases/v1.1.0.md`;
- `README.md` only if current-version/current-behavior references require the release transition.

Required metadata transition:

1. set `package.json.version` to exactly `1.1.0`;
2. move the complete `[Unreleased]` body into `## [1.1.0] - YYYY-MM-DD` using the actual release-PR date;
3. recreate an empty `## [Unreleased]` section;
4. create `docs/releases/v1.1.0.md` with status/target tag `v1.1.0`, the v1.1 product changes, architecture preservation, implementation-certification evidence pointer, Android certification/F-Droid status and installation/distribution wording consistent with the final product;
5. ensure the changelog released section itself is complete because `scripts/package-release.ts` uses that section as the GitHub Release body.

Before opening/merging the release PR, prove locally:

~~~bash
bun scripts/verify-release.ts \
  --mode pr \
  --base origin/master \
  --head-ref release/v1.1.0

git diff --name-only origin/master...HEAD
~~~

The diff must contain no file outside the allowed release-metadata set.

The release PR must also run the permanent hosted Verify workflow. Its PR-body release metadata must follow repository policy; do not bypass the release verifier because the implementation candidate was already certified.

Do not merge until:

- `verify-release.ts --mode pr` passes;
- permanent Verify passes with the release PR's exact head;
- the release-PR Android Verify job proves `versionName=1.1.0` / `versionCode=1001000` and the F-Droid candidate metadata/build path remains valid under the actual version transition;
- the release diff is metadata-only;
- version, branch, changelog and release-note identifiers are exactly consistent.

### J110-REL-03 — Merge and execute the permanent Release workflow

Merge `release/v1.1.0` to `master`.

The **exact merged release-PR commit** is the release candidate. Record its 40-character SHA and verify `master:package.json` reports `1.1.0`.

The permanent `.github/workflows/release.yml` must detect the package/changelog release transition and execute the real release path. A green run whose prepare job reports `should_release=false` is a **no-op and release failure**, not successful publication.

For the exact release commit the permanent workflow must execute successfully:

- release metadata verification with `scripts/verify-release.ts --mode release-commit`;
- the v1.1 non-publishing Android release-certification job from IMP-14, proving `com.pontivus.jig`, `versionName=1.1.0` and `versionCode=1001000`;
- native Linux arm64 certification;
- frozen dependency installation;
- strict typecheck;
- core/integration/architecture tests;
- production UI build;
- real-browser acceptance;
- shell/installer certification;
- Linux x64/arm64 packaging;
- `SHA256SUMS` verification;
- packaged x64 installation smoke covering both `--repo` automation and fresh no-repository bootstrap mode;
- packaged arm64 installation smoke covering both `--repo` automation and fresh no-repository bootstrap mode;
- immutable annotated `v1.1.0` tag creation/verification;
- draft GitHub Release creation;
- complete asset upload/byte-identical reuse;
- transition of the GitHub Release from draft to published.

The publication job must depend on all mandatory certification jobs, including Android certification and native arm64 certification. No Android APK is uploaded to the GitHub Release.

#### Safe retry

If the permanent Release workflow fails before publication, fix release infrastructure only through the governed path appropriate to the failure and re-certify the exact intended release state.

For a workflow retry using `workflow_dispatch`:

- supply the exact 40-character `master` release commit;
- never move an existing `v1.1.0` tag;
- if a draft release/assets already exist, the workflow may reuse them only when existing assets are byte-identical to newly certified outputs;
- a mismatching existing asset is a release-blocking failure, not permission to overwrite published provenance;
- never force-tag or manually publish around a failing release workflow.

After a published immutable release, any product/artifact correction requires a new version rather than rebuilding `v1.1.0`.

### J110-REL-04 — Verify the published Jig release directly

Do not infer release success from workflow color alone. After the Release workflow completes, verify the public state directly.

All of the following must be true:

- `master:package.json` reports `1.1.0`;
- `CHANGELOG.md` contains dated `[1.1.0]` and an empty `[Unreleased]`;
- `docs/releases/v1.1.0.md` exists and targets `v1.1.0`;
- the permanent Release workflow executed release jobs rather than `should_release=false`;
- annotated tag `v1.1.0` exists and resolves to the exact certified merged release commit;
- GitHub Release `v1.1.0` exists, is non-draft and is not a prerelease;
- the release contains exactly the required supported Jig assets:
  - `jig-linux-x64.tar.gz`;
  - `jig-linux-arm64.tar.gz`;
  - `jig-install.sh`;
  - `SHA256SUMS`;
- download those four assets into a clean temporary directory and run `sha256sum -c SHA256SUMS`;
- both archives contain the expected `RELEASE.json`, whose version is `1.1.0`, whose Git commit is the exact release commit and whose architecture matches the bundle;
- clean version-pinned installer smokes use `releases/download/v1.1.0/jig-install.sh` rather than `latest` and prove both (a) configured `--repo` automation reaches healthy status and (b) no-repository installation reaches the bootstrap/setup surface;
- no Android APK is present as a supported GitHub Release asset.

Only after every item above is true is **Jig v1.1.0 released**.

### J110-REL-05 — Submit and verify the F-Droid distribution

After J110-REL-04 has established the immutable public `v1.1.0` source tag:

1. derive the external F-Droid `fdroiddata` submission from the reviewed `distribution/fdroid/metadata/com.pontivus.jig.yml` candidate;
2. resolve the immutable `v1.1.0` tag to its exact 40-character release commit and ensure the external F-Droid recipe uses that SHA in `Builds.commit`, with package ID `com.pontivus.jig`, `versionName 1.1.0` and governed `versionCode 1001000`; retain `v1.1.0` as the human-readable source/tag provenance rather than using the tag name as the submitted `Builds.commit` value;
3. rerun `fdroid lint` and `fdroid build` against the exact immutable `v1.1.0` tagged source and exact submitted metadata; this is the authoritative F-Droid source-build validation for the released version;
4. submit through the normal F-Droid contribution/review path;
5. record the external submission reference/status in release evidence/documentation without modifying immutable v1.1.0 product artifacts;
6. do not claim public Android availability until F-Droid actually publishes the package;
7. once published, verify the F-Droid listing/package identity/version corresponds to Jig `1.1.0` and update only forward/current documentation through an ordinary post-release documentation PR if a publication-status statement needs to change.

F-Droid review timing is external to Jig release validity. The Linux GitHub release may be valid before F-Droid publication, while the product must continue to describe Android availability accurately.

### Release-complete definition

The project has three deliberately distinct milestones:

1. **Implementation complete** — IMP-01..IMP-16 closed on a verified `master` candidate; package version has not yet transitioned.
2. **Jig v1.1.0 released** — REL-01..REL-04 complete; immutable tag and certified Linux GitHub Release are publicly verified.
3. **Android publicly available on F-Droid** — REL-05 external review/publication is complete and the published F-Droid package has been directly verified.

Never collapse these states into one green workflow result.
