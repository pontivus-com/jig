## 4. Target presentation state

Use one small presentation-state model in the application shell.

```ts
type Destination = "planner" | "history" | "settings";

type LayoutMode = "desktop" | "narrow";

interface PlannerState {
  displayedWeekStart: string; // canonical Monday local civil date
  selectedDate: string;       // invariant: one of the displayed seven dates
}

type TaskWorkspaceState =
  | { mode: "closed" }
  | { mode: "view"; taskId: string }
  | { mode: "edit"; taskId: string; draft: TaskDraft }
  | { mode: "create"; originatingDate: string; draft: TaskDraft };
```

Keep the existing Task draft type. `TaskWorkspaceState` is the single writable owner of workspace selection, mode, edit/create draft and create originating date. Do not keep parallel writable `selectedTaskId`, `workspaceMode`, `workspaceDate` or `workspaceDraft` state that can form invalid combinations.

### 4.1 Planner state laws

At application startup:

```text
today = current browser local civil date
displayedWeekStart = Monday containing today
selectedDate = today
destination = planner
```

Operations:

- **Previous week:** subtract 7 civil days from both `displayedWeekStart` and `selectedDate`.
- **Next week:** add 7 civil days to both.
- **Today:** set `displayedWeekStart` to Monday containing current local date and `selectedDate` to current local date.
- **Select visible date:** update `selectedDate` only; reject/avoid any date outside the current seven dates.
- **Jig/Home:** set destination to Planner only; preserve current in-session PlannerState.
- **History/Settings navigation:** preserve PlannerState.
- **Edit scheduled date succeeds:** keep the resulting Task selected in the contextual workspace, but do **not** implicitly change Planner temporal state. `selectedDate` and `displayedWeekStart` remain user-owned navigation state unless the user invokes a Planner date control.
- **Create succeeds:** keep the created Task selected and keep PlannerState on the originating date/week.
- **Local midnight:** if `selectedDate === previous observed today`, advance selectedDate to new today and displayedWeekStart to its week; otherwise preserve user-selected PlannerState. Always refresh canonical Tasks so rollover is observed.

No Planner state operation writes SQLite.

# 15. Definition of done

v1.0.3 implementation is done only when **behavior, architecture, and evidence agree**.

A visually similar result is a failure if it retains Day/Week state, SideNav, duplicate Task/workspace state, private Astryx overrides, or a second responsive authority.

A functionally green result is a failure if the approved centered header/date mental model, responsive composition, Drawer/BottomSheet ownership, or removal of completed Tasks from Planner is not implemented.

The implementation team is not authorized to redesign the interaction while executing this plan. If one pinned Astryx public primitive is demonstrably incompatible with a required behavior, record the exact incompatibility and use the smallest Jig-owned semantic composition built from public Astryx leaves/tokens. Do not silently alter the target UX, add another UI framework, or reach into Astryx internals.
