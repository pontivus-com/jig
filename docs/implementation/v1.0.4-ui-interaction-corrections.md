# Jig v1.0.4 — interaction correction implementation plan

**Status:** Binding, implementation-ready v1.0.4 corrective plan.  
**Baseline:** published v1.0.3 on `master`; implementation branch `fix/v1.0.4-ui-interaction-corrections`.  
**Governing functional design:** `JIG-104-FR-01…16` in `docs/requirements/planning-workbench.md` v0.10.  
**Governing technical design:** `docs/architecture/technical-solution.md` v0.14.  
**Governing UI/theme design:** `docs/design/ui-solution.md` v0.11 and `docs/design/brand-and-theme.md`.  
**Release rule:** this implementation branch keeps `package.json.version = 1.0.3` and accumulates notes under `CHANGELOG.md [Unreleased]`. Version 1.0.4 is finalized only after this implementation lands on `master`, through a dedicated `release/v1.0.4` branch.

## 1. Required outcome

v1.0.4 is a corrective UI/interaction patch over the published v1.0.3 single-Planner architecture.

The final product must have:

- reliable card-body drag-and-drop;
- no selected-day state or day selector;
- one displayed-week Planner state;
- full weekday labels (`Monday`…`Sunday`);
- per-date `+` in each date header and no bottom-of-lane Add action;
- content-driven desktop lane heights;
- global Add using a derived date inside the displayed week;
- one directly editable Task workspace for both existing and new Tasks;
- outside-click workspace dismissal;
- complete Task action menus;
- invariant application-header height across Planner/History/Settings;
- a complete, non-colliding Light/Dark semantic color system;
- `Local only` represented as healthy local durability rather than unknown grey;
- narrow/mobile as the same seven-day week expressed as stacked dated sections.
- explicit desktop `Planner · History · Settings` navigation retained in the right-side header zone;
- an open, reduced-chrome weekly canvas using whitespace/hairline separation rather than framed day panels;
- restrained Task-card surfaces and semantic iconography that improve scanning without changing information placement.

## 2. Preservation boundary

This patch is **not** a Task/domain/integration redesign.

Do not change:

- canonical Task identity or schema;
- SQLite schema or persistence ownership;
- HTTP command shapes;
- create/edit/move/complete/reopen/delete domain semantics;
- priority-assisted initial insertion;
- explicit exact-position move semantics;
- daily rollover;
- reminders;
- Git synchronization architecture;
- installer/lifecycle behavior;
- release workflow/tooling;
- pinned Astryx or dnd-kit versions.

Do not introduce:

- DTOs or mapping hierarchies;
- new service/repository layers;
- a second Task/order representation;
- another drag library;
- a second theme system;
- screen-local raw colors;
- a global state framework;
- selected-day state under another name;
- a second create/edit form.

## 3. Final presentation/state model

### 3.1 Planner

```ts
type PlannerState = {
  displayedWeekStart: LocalCivilDate; // Monday
};
```

Pure operations:

- Previous: `displayedWeekStart - 7 days`;
- Next: `displayedWeekStart + 7 days`;
- Today: Monday containing `currentLocalDate`;
- no `selectedDate`;
- no `selectDate()`.

Global Add derives, but does not store, a date:

```ts
defaultAddDate =
  addCivilDays(
    displayedWeekStart,
    weekdayOffsetFromMonday(currentLocalDate),
  );
```

Per-date `+` uses that section's explicit date directly.

### 3.2 Task workspace

```ts
type TaskWorkspaceState =
  | { mode: "closed" }
  | { mode: "task"; taskId: string; draft: TaskDraft }
  | { mode: "create"; originatingDate: LocalCivilDate; draft: TaskDraft };
```

There is no `view`, `edit`, or `move` submode.

Existing Task selection constructs an editable draft immediately. Create uses the same complete field hierarchy.

### 3.3 Responsive composition

Desktop:
- seven equal-width Planner tracks;
- minimum 160px per track;
- content-driven independent track heights;
- right Drawer overlays without reducing board width.

Narrow/mobile:
- the same displayed week;
- seven vertically stacked dated sections;
- no date strip;
- no selected-date heading/list;
- BottomSheet renders the same Task draft state.

## 4.1 Mandatory architecture compliance contract

Every implementation task below must satisfy the architecture contract **as it lands**. No task may introduce temporary DTOs, duplicate state, unchecked typing, copied business logic or a second semantic owner with the intention of removing it in a later task.

Required invariants:

- **Functional core:** planning/Task/calendar/order semantics remain pure typed functions under `src/core/**`; no browser, HTTP, SQLite, Git, filesystem or process I/O enters the core.
- **Imperative shell:** `src/shell/**` owns SQLite/HTTP/Git/filesystem/process integration and delegates Task/planning semantics to the core.
- **UI separation:** `ui/src/**` owns presentation state and command invocation only. It must not reimplement canonical validation, normalization, insertion, ordering, movement or rollover behavior.
- **Strict typing:** preserve all current strict compiler options. No new `any`, double casts, non-null assertions or unchecked `as` assertions. Untyped external/library values are narrowed through type guards, typed library generics or the smallest justified boundary adapter.
- **Canonical ownership:** one `Task`, one `TaskCommand`, one displayed-week Planner state, one TaskWorkspaceState, one TaskDraft and one semantic owner for each mapping/algorithm.
- **DRY:** repeated Task-sequence rendering/move wiring, date-header composition, status semantics, color semantics and command construction are shared rather than duplicated across desktop/narrow or Planner/History.
- **No architecture inflation:** no DTO/mapping hierarchy, service/repository class stack, workflow framework, command bus, state-management framework or parallel projection model.
- **Dependency direction:** core ← shell/UI; never UI/shell implementation dependencies flowing into core.

A third-party interop assertion is permitted only when the library typing cannot represent the verified runtime contract. It must be local to that boundary, documented by code structure/comment where necessary, and covered by tests. It must never be used to bypass canonical Task/command validation.

### J104-IMP-00 — Close existing architecture compliance breaches

**Scope**
Audit every production TypeScript/TSX module under `src/**` and `ui/src/**` against technical solution §3.0.1–3.0.2. Fix every actual breach found. Do not broaden this into unrelated feature refactoring.

**Known mandatory remediations**
1. Remove the parallel `selectedDate`/date-selection state and projection from `app.tsx`, `planner.tsx`, `week.tsx`, `planner-list.tsx` and `date-strip.tsx`; this converges with IMP-02/03 rather than creating separate machinery.
2. Replace the incompatible workspace owners (`view | edit | create` in `app.tsx` versus `task | create` in `task-workspace.tsx`) with the one discriminated TaskWorkspaceState defined by the technical solution. Invalid combinations such as `mode="task"` + `task=null` must be unrepresentable.
3. Consolidate duplicated Planner Task-list row/move wiring in `week.tsx` and `planner-list.tsx` into one shared sequence renderer/command owner used by desktop and narrow composition.
4. Remove UI-side canonical normalization from `task-editor.tsx` (`optionalText`, duplicate title trimming as command semantics). UI may show required-field errors, but canonical normalization/validation remains in `src/core/task.ts`.
5. Replace unchecked Astryx value assertions in `task-editor.tsx` and `settings.tsx` with existing type guards or minimal typed adapters. Isolate any unavoidable dnd/Astryx ref assertion at the third-party boundary.
6. Remove avoidable product-logic assertions in `src/core/task.ts` and `src/core/planning.ts`; make validated values narrow to their actual types without `as` casts where the code owns the type.
7. Review all untyped JSON/SQLite/HTTP boundaries. Runtime-validated record coercion may remain only inside a dedicated boundary helper; prohibit double-cast patterns such as `object as unknown as Task`. Repository Task import must call `validateTask(unknown)`; SQLite/HTTP must use typed generics or validate unknown values before canonical use.
8. Keep one repository-status semantic mapping owner. For v1.0.4 that owner remains in `ui/src/app.tsx` unless a smaller pure helper is extracted; do not duplicate status→label/color/icon mapping across App/Settings/CSS.
9. Keep one theme semantic owner and one icon-system owner as specified by IMP-01/10.

**Acceptance**
- `bun run typecheck` passes under the existing strict compiler options;
- production source contains no architecture-prohibited DTO/service/repository/workflow/state-framework additions;
- no unsafe double-cast to canonical Task/domain types remains;
- no duplicate Planner/workspace semantic state owner remains;
- architecture tests encode the dependency/type/ownership rules so the violations cannot silently return.
