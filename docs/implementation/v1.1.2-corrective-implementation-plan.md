## 3. Non-negotiable architecture constraints

Every task below must preserve all of these constraints.

1. Functional-core / imperative-shell dependency direction remains intact.
2. No DTO/view-model/service/repository hierarchy is introduced for presentation or platform separation.
3. No any, double casts, non-null assertions or unchecked cross-layer assertions are introduced.
4. Canonical Task/planning/workspace/navigation/synchronization semantics remain singular.
5. LayoutMode selects presentation only.
6. Raw native/platform detection selects platform mechanics only.
7. Pointer/keyboard/IME facts are observed only at the interaction/presentation boundary that needs them.
8. No global isMobile/device-class state is introduced.
9. Desktop and narrow presentation trees are never both mounted and CSS-hidden.
10. AppShell main is the sole configured application/page scroll owner.
11. Feature CSS consumes semantic/theme tokens only; no per-theme feature selectors or palette literals.
12. dnd-kit optimistic DOM sorting remains disabled.
13. Drag-over never mutates canonical Task state.
14. Git/platform work does not leak into Task/domain state.
15. Jig never force-pushes jig-data and never mutates unrelated repository history.
16. Normal synchronization root-cause correction is evidence-driven; automatic divergence recovery is a separate capability.
17. Package version remains 1.1.1 throughout implementation. Version transition belongs only to the governed release/v1.1.2 ceremony.

- ui/src/native/app-lifecycle.ts owns native activation and Back listener mechanics; app.tsx currently registers the configured native lifecycle effects.
- ui/src/drag.tsx currently uses raw useDraggable/useDroppable, explicit TaskInsertionSlot components and one simplified hand-built drag overlay.
- ui/src/planner-list.tsx currently renders insertion slots between Task rows.
- ui/src/task-row.tsx contains both the real Astryx ListItem-based Task presentation and a simplified TaskDragOverlayCard.
- all 13 theme source files currently spread one shared jigProductLocalTokens surface formula.
- JigSuccessConfirmation still uses a hard-coded animation-completion delay separate from the CSS duration token.
- Linux synchronization is owned by src/shell/sync.ts + src/core/synchronization.ts + src/shell/git.ts + src/persistence/synchronization.ts.

- persistence metadata already records revision, last_exported_revision/head, last_adopted_head and pending_sync; existing interrupted remote adoption proves a restart-safe alignment pattern that should be reused/generalized before adding new persistent synchronization state.

## J112-IMP-16 — Implement bounded crash-safe recovery for related jig-data divergence

**Type:** new bounded continuity capability.  
**Closes:** recovery portion of FR-06, FR-07; SD-06, SD-07, SD-08.

### Primary surfaces

- src/core/synchronization.ts;
- src/persistence/synchronization.ts;
- src/persistence/sqlite.ts only if existing metadata cannot safely encode the acceptance protocol;
- src/shell/git.ts;
- src/shell/sync.ts;
- ui/src/native/git.ts;
- ui/src/native/sync.ts;
- portable snapshot validators;
- Linux/Android repository tests.

### Required implementation

#### A. Shared policy

1. Recovery is considered only for lineage=diverged with:
   - exact local and remote heads;
   - one provable common ancestor;
   - matching dataset identity;
   - valid canonical ancestor/local/remote snapshots.
2. Build one three-way candidate from canonical portable records.
3. Any record/content conflict or semantically invalid complete candidate => terminal attention.
4. Validate the complete Task/order/recurrence/dataset snapshot before authoritative acceptance.
5. No force push.

#### B. Isolated candidate mechanics

6. Platform Git adapters build the candidate without moving authoritative local jig-data.
7. Keep the candidate durably reachable through one private recovery ref/mechanism until acceptance is complete so restart cannot orphan the accepted candidate.
8. The candidate commit must retain enough parent/head evidence to prove the expected local and remote inputs on resume.
9. Platform-specific Git mechanics remain private; shared synchronization policy consumes typed facts/outcomes.

#### C. Acceptance transaction

10. Before acceptance, re-check:
    - current SQLite revision equals expected revision;
    - authoritative local jig-data head equals the exact expected local head.
11. Adopt the validated candidate through the existing revision-guarded canonical snapshot path.
12. Record the accepted candidate head using the existing last-adopted/pending synchronization semantics where sufficient.
13. Advance authoritative local jig-data from the exact expected old head to candidate using compare-and-set/atomic ref semantics.
14. Mark exported only after canonical SQLite and authoritative local ref agree.
15. Remove the private recovery ref only after that agreement.
16. Push with ordinary non-force semantics, re-observe, and mark synchronized only when remote exposes the accepted head.

#### D. Restart/interruption recovery

17. Generalize/reuse the existing finishInterruptedSynchronizationAdoption pattern rather than inventing a second reconciliation subsystem.
18. On restart, if SQLite says an accepted head is pending and the durable candidate/ref proves the same canonical snapshot and expected ancestry, finish ref alignment idempotently.
19. If proof is incomplete, stop in attention without destroying either side.
20. Do not add a synchronization table or new metadata fields unless tests prove the existing revision/export/adopt metadata plus private Git recovery ref cannot encode a safe restart. Any schema change requires a separate explicit design note in this task before implementation.

#### E. Android parity

21. Android isomorphic-git implements the same effect contract:
    - prove ancestry;
    - construct isolated candidate;
    - validate;
    - expected-head acceptance;
    - restart-safe private ref;
    - non-force push/reobserve.
22. Do not duplicate the pure recovery decision policy in native code.

### Hard acceptance

- unrelated histories => no recovery;
- dataset mismatch => no recovery;
- content conflict => no recovery;
- semantic invalidity => no recovery;
- local revision changes during candidate build => abort/reclassify;
- local ref changes during candidate build => abort/reclassify;
- crash before SQLite adoption => pre-recovery state remains authoritative;
- crash after SQLite adoption before ref move => next run proves/resumes;
- crash after ref move before markExported => next run repairs bookkeeping;
- crash after local acceptance before push => next run pushes/reobserves;
- no crash boundary produces destructive repair or duplicate semantic commits;
- unrelated repository files/index/config remain byte/semantically untouched;
- no force push occurs.
