# Jig v1.0.1 — ownership-boundary and installer correction plan

**Status:** Implementation-ready corrective plan for v1.0.1.  
**Governing authority:** root `AGENTS.md`, product definition, functional design, technical solution v0.7+.  
**Purpose:** Remove v1.0.0 scope creep around external-system ownership, restore a thin Git synchronization boundary, and make installation/reinstallation reliable in ordinary developer Git environments without weakening automatic synchronization.

## 1. Correction objective

Jig remains responsible for:
- Task/planning semantics;
- SQLite local durability;
- deterministic portable Jig records;
- automatic synchronization scheduling;
- coarse synchronization outcomes;
- adopting valid existing Jig data in the selected repository.

Jig is not responsible for:
- repository migration/reorganization between data roots;
- Git lifecycle management beyond a thin installer clone handoff;
- Git topology as application state;
- Git identity/signing configuration;
- credentials;
- merge/rebase/conflict reconciliation;
- changing repository/user Git policy.

The v1.0.1 implementation must remove code and user-facing behavior that contradicts this ownership model rather than adding more machinery around it.

## 2. Required removals

### C1 — Remove Jig repository migration

Delete the repository-migration product path.

Production changes:
- remove `src/shell/migration.ts`;
- remove `jig configure --repo ...` from `src/shell/cli.ts`;
- remove `POST /api/v1/migrate` from `src/shell/http.ts`;
- remove repository-migration controls/actions from `ui/src/settings.tsx`;
- remove migration-specific configuration switching/restart behavior;
- remove migration-only writer coordination and destination validation code where it has no other owner.

Tests/docs:
- delete migration acceptance/failure-injection tests;
- replace them with Git-native continuity tests: install against an existing checkout containing valid Jig data and verify automatic adoption.

Do not replace migration with a different Jig-owned copy/move mechanism.

### C2 — Keep repository selection/acquisition thin

The installer must support both target-selection modes:
- `--repo /absolute/existing/repository`;
- `--repo-url URL --checkout /absolute/new-or-empty/path`.

URL mode is a convenience boundary only: validate the destination, delegate the clone to Git using the user's normal Git environment, then converge immediately on the same installation path as `--repo`.

Do not add branch creation, topology decisions, credential management, signing management, migration semantics, or other repository lifecycle ownership around this mode.

### C3 — Remove Git topology from Jig application configuration

Application configuration must contain only Jig-owned runtime configuration.

Target:
```json
{
  "version": 1,
  "repository_path": "/absolute/path/to/repository",
  "http_port": 47831
}
```

Remove persisted `remote_name` and `data_ref` from `src/shell/config.ts` and all consumers unless implementation evidence proves one is strictly necessary as Jig-owned configuration. Git remote/ref/worktree details must instead remain repository/adapter concerns.

No migration of repository topology into another Jig config shape is allowed.

## 3. Thin the Git adapter without removing automatic synchronization

### C4 — Define one narrow repository adapter responsibility

`src/shell/git.ts` may know Git mechanics because it is the Git integration boundary. The rest of Jig must not.

The adapter contract should be reducible to operations conceptually equivalent to:
- inspect/adopt valid Jig portable data from the selected repository;
- synchronize one complete deterministic Jig snapshot;
- report a coarse operational outcome.

No domain/shell/UI caller should need to know:
- branch names;
- refs;
- worktree paths;
- merge bases;
- ahead/behind counts;
- signing configuration;
- Git error taxonomy.

If the existing `jig-data` ref/worktree remains the smallest safe implementation for isolation, keep it private to `git.ts`. Do not expose it through application config, status UI, diagnostics or installer semantics.

### C5 — Never alter Git policy

Remove any requirement that Jig controls:
- `user.name` / `user.email`;
- `commit.gpgSign`;
- signing key;
- `gpg.format`;
- credentials;
- global or repository Git config.

For Jig-created machine synchronization commits, invoke Git so the operation is deterministic and does not require a Jig private signing key. Apply any non-signing override only to the individual Jig-owned commit operation. Never persistently change Git config.

The public installation command must not require environment-variable workarounds.

## 4. Installer correctness

### C6 — Make first initialization valid from its first observable state

The v1.0.0 sequence creates an empty bootstrap commit/ref before a valid portable snapshot exists. This violates the invariant that existing Jig data is consumable on the next installation.

Correct it so that:
- no persistent Git state is published that Jig itself considers an invalid snapshot;
- the first Jig-created portable Git state already contains a valid `format.json` and complete empty snapshot;
- a failure after local SQLite initialization cannot strand the repository in an unrecoverable Jig state;
- rerunning the installer is safe.

Do not solve this by teaching Jig a general Git repair workflow.

### C7 — Recover the exact known v1.0.0 failed-bootstrap residue

Support only the narrowly identifiable state created by v1.0.0:
- Jig-created initialization commit/residue;
- no valid `format.json`;
- no portable Task data;
- no evidence of user Jig data.

When and only when that state is unambiguous, recover automatically and continue installation.

Any other malformed/unknown portable state must remain non-destructive and produce a clear installation/synchronization error.

### C8 — One selected-checkout installation path is the continuity mechanism

For `--repo`, use the supplied checkout directly. For `--repo-url` + `--checkout`, delegate clone to Git and then enter the exact same selected-checkout path.

On that common installation path:
1. validate the selected repository;
2. locate/validate existing Jig portable data through the adapter;
3. if valid data exists and no compatible SQLite DB exists, hydrate SQLite transactionally;
4. if compatible SQLite exists, preserve/use it;
5. if no Jig data exists, initialize a new dataset;
6. install/start runtime/service;
7. begin automatic synchronization.

This common path must cover fresh install, URL-clone install, reinstall and a checkout obtained on another machine. No separate repository migration path exists.

## 5. CLI correction

### C9 — Reduce public CLI to Jig-owned operations

Required public commands:
- `jig` — start/open Jig;
- `jig status` — report service, selected repository, local save/sync status;
- `jig sync` — request an immediate synchronization attempt;
- `jig serve` — foreground fallback;
- `jig uninstall` — remove Jig runtime/config/service and preserve repository data.

`jig doctor` may remain only if it is a small Jig-health diagnostic. It must not expose or repair Git topology/configuration.

Remove:
- `jig configure --repo`;
- public `jig service check` unless it has a real user requirement; keep test-only service checks inside certification scripts instead.

Status/diagnostics must use application language, not Git-internals language.

## 6. Synchronization behavior

### C10 — Preserve the required automatic-sync contract

Do not regress:
- successful Task mutation commits to SQLite immediately;
- Git synchronization remains background/automatic;
- browser can be closed while the service synchronizes;
- transient failure retries automatically with bounded backoff;
- sync failure never rolls back a successful local Task save;
- unrelated repository content remains untouched;
- UI exposes only `local-only | pending | retrying | synchronized | sync-issue`.

The synchronization worker should depend on the thin adapter rather than repository topology.

### C11 — Simplify replica/adoption semantics to the product requirement

Retain validation of complete portable snapshots and transactional adoption.

Remove any logic whose only purpose is to maintain a Jig-owned multi-repository migration protocol.

Dataset identity may remain in the portable format if needed to prevent accidental adoption of unrelated Jig datasets. It must not justify a separate migration system.

## 7. CI and certification correction

### C12 — Add real developer Git-environment installer tests

The release is blocked until the packaged v1.0.1 installer is tested for:

1. fresh existing repository;
2. repository-URL clone into a new/empty checkout;
3. repository with unrelated staged and unstaged files;
4. `commit.gpgSign=true` with no Jig secret key;
5. SSH-signing configuration;
6. no configured/usable remote;
7. temporary transport failure;
8. interrupted/failing synchronization initialization followed by installer retry;
9. exact v1.0.0 empty-bootstrap residue;
10. existing valid Jig portable data with no local SQLite database;
11. reinstall over a valid existing Jig installation;
12. unknown malformed Jig portable state — must fail non-destructively;
13. packaged x64 release payload;
14. packaged arm64 release payload.

For every case assert:
- user Git configuration is unchanged;
- unrelated repository content/index is unchanged;
- SQLite remains valid;
- installer is rerunnable;
- automatic synchronization status is truthful.

### C13 — Replace narrow happy-path smoke assumptions

Update `tests/install/installer-smoke.sh` and repository/sync tests so they no longer certify only a clean Git environment with hand-set `user.name`/`user.email`.

Tests must exercise the ordinary installation one-liner with no Git-policy workaround.

## 8. Documentation correction

### C14 — Keep canonical docs aligned

Required current authorities:
- root `AGENTS.md`: foundational ownership rule;
- `docs/product/product-definition.md`: authority boundary + Git-native continuity;
- `docs/requirements/planning-workbench.md`: existing-repo and repository-URL installation, automatic existing-data adoption, no Jig repository migration/reorganization;
- `docs/architecture/technical-solution.md`: thin adapter, private isolation mechanics, corrected installer/config/CLI;
- this plan: v1.0.1 execution authority.

Update after implementation:
- `README.md`;
- `docs/install.md`;
- `docs/README.md`;
- `CHANGELOG.md`;
- v1.0.1 release notes.

Remove user-facing references to:
- `--remote` if remote selection is no longer Jig configuration;
- `jig configure --repo`;
- linked-worktree/ref implementation details except where explicitly documented for contributors/internal adapter design.

## 9. Required implementation order

1. Land canonical documentation/AGENTS correction.
2. Remove repository migration/reorganization paths while retaining thin `--repo` and `--repo-url` target-selection modes.
3. Simplify configuration and CLI.
4. Refactor Git knowledge behind the repository adapter.
5. Fix Jig-owned commit signing behavior without mutating Git config.
6. Fix first-snapshot initialization and v1.0.0 bootstrap recovery.
7. Align synchronization worker to the thin adapter.
8. Expand installer/sync tests.
9. Update public install/README/release documentation.
10. Build packaged v1.0.1 assets and certify both architectures.

Do not add another abstraction layer to preserve old behavior. Delete superseded code in the same changes that make it unnecessary.

## 10. Acceptance gate for v1.0.1

v1.0.1 is releasable only when all of the following are true:

- Both supported installer forms are release-certified:
  ```bash
  curl -fsSL https://github.com/pontivus-com/jig/releases/latest/download/jig-install.sh \
    | bash -s -- --repo /absolute/path/to/existing/repository
  ```
  and
  ```bash
  curl -fsSL https://github.com/pontivus-com/jig/releases/latest/download/jig-install.sh \
    | bash -s -- --repo-url git@github.com:you/planning.git --checkout /absolute/new/path/planning
  ```
- It succeeds in repositories with ordinary developer signing configuration without user workarounds.
- A failed v1.0.0 bootstrap can be recovered automatically when it is exactly the known empty Jig-created residue.
- Existing valid Jig data in a selected checkout is adopted automatically.
- Automatic synchronization remains fully automatic.
- Jig may delegate URL-mode acquisition to Git, but does not migrate, reorganize or manage repository topology.
- Jig does not modify Git configuration/policy.
- Git topology does not appear as Jig domain/configuration/UI.
- Unrelated repository content is untouched.
- Git/sync failure never invalidates a successful local Task save.
- Public CLI contains only Jig-owned operations.
- All corrected canonical docs and release documentation agree with the implementation.
