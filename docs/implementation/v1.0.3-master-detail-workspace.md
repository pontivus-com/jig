# Jig v1.0.3 — master-detail task workspace and desktop density correction

**Status:** Superseded for v1.0.3 implementation by [v1.0.3 single Planner implementation plan](v1.0.3-single-planner-implementation-plan.md). This document remains historical evidence of the earlier master-detail correction and must not govern Day/Week navigation, SideNav, Move-to-date, responsive workspace, or header/date composition.

**Status:** Binding implementation authority for the v1.0.3 UX/UI correction.  
**Governing design:** [UI solution](../design/ui-solution.md) and [canonical reference set](../design/reference/README.md).  
**Supersedes:** the rail-width, fixed Week-width and Task Dialog/editor requirements in [UI/UX conformance remediation v1.0](ui-ux-conformance-remediation-v1.0.md). All unrelated v1.0.2 requirements remain historical evidence of the prior release.

## 1. Problem statement

The v1.0.2 UI has three coupled usability defects:

1. the desktop navigation rail consumes excessive horizontal space relative to four destinations;
2. the Week board is capped to the 1440px reference width instead of using available canvas, causing unnecessary task-title wrapping;
3. task view/create/edit is split between card selection, a docked Day inspector and centered Dialog editors, producing inconsistent navigation and unnecessary modal context switches.

The correction is one coherent master-detail model rather than independent CSS patches.

## 2. Interaction contract

Task selection never changes the primary destination.

A Task workspace has exactly four presentation modes:

- **view** — inspect the selected Task;
- **edit** — edit the selected Task;
- **create** — create a Task for the initiating date;
- **move** — move the selected Task to a different date using the canonical exact-position `move` command.

The underlying canonical Task remains the only Task authority. Workspace mode and selection are presentation state only.

### 2.1 Desktop Day

Desktop Day keeps a docked right-hand Task workspace.

- Clicking a Task selects it and renders **view** in the docked workspace.
- Edit changes that same docked workspace to **edit**.
- Add task changes that same docked workspace to **create**.
- Move to date changes that same docked workspace to **move**.
- Save/Move returns the same workspace to **view** with the resulting Task selected.
- Cancel from edit/move returns to **view**; Cancel from create closes create mode and returns to the ordinary selected-Task/empty inspector state.
- No Task Dialog is mounted.

### 2.2 Desktop Week

Week owns the full available planning canvas and must not reserve a permanent inspector column.

- Clicking a Week card keeps **Week** as the current destination.
- Selection opens an Astryx `Drawer` from the inline end/right.
- The Drawer is non-modal with `hasScrim={false}` so the Week board remains visible and interactive.
- The Drawer displays **view**, **edit**, **create** and **move** modes of the same Task workspace.
- Quick add and per-day Add task open **create** in that Drawer.
- Edit opens **edit** in that Drawer.
- Move to date opens **move** in that Drawer.
- The Drawer overlays the Week board; it never reflows or narrows the seven day columns.
- Closing the Drawer clears Week workspace selection.

### 2.3 Narrow/mobile

At Jig's existing semantic mobile breakpoint:

- Task selection/create/edit/move uses the same Astryx Drawer-based workspace from the inline end/right;
- there is no centered/fullscreen Task Dialog implementation;
- the underlying planning surface remains the same destination/state;
- the Drawer uses the public Astryx responsive behavior rather than private positioning overrides.

### 2.4 Destructive confirmation

Permanent Task deletion remains the only blocking Task dialog.

- Delete is initiated from Task detail.
- The existing Astryx `AlertDialog` confirmation remains authoritative.
- No delete/trash/undo lifecycle is added.

## 3. Navigation contract

Desktop primary navigation is a compact Astryx SideNav rail:

1. **Day** — semantic icon `calendar`;
2. **Week** — semantic icon `viewColumns`;
3. **History** — semantic icon `clock`;
4. **Settings** — semantic icon `wrench`.

The governed desktop visual budget is approximately **112px** wide at the canonical 1440px viewport, with the existing 20px application inset and an Astryx-tokenized gap to content.

Use only public `SideNav` / `SideNavItem` APIs and semantic icon names. Do not install or duplicate a separate icon library. Do not style Astryx internal nav descendants.

The compact rail keeps the Jig mark but omits low-value tagline/repository copy when that copy would consume the reclaimed horizontal budget.

## 4. Week width contract

The Week board is fluid rather than capped to the old 1168px reference width.

Desktop implementation:

```css
grid-template-columns: repeat(7, minmax(10rem, 1fr));
width: 100%;
```

Product-level invariants:

- each day column has a **160px minimum**;
- all seven columns expand evenly when more horizontal canvas is available;
- at the canonical 1440px desktop viewport, all seven columns remain visible without horizontal scrolling;
- at wider viewports, the board materially expands rather than leaving unused right-side canvas;
- horizontal overflow is permitted only when the available desktop canvas is genuinely narrower than seven 160px tracks plus six gaps;
- opening the Week Task Drawer must not change board width or grid-track sizing.

Task titles keep normal word boundaries. Do not introduce `word-break: break-all`, arbitrary hyphenation or smaller-than-token typography to compensate for insufficient layout width.

## 5. Astryx ownership

Astryx owns:

- AppShell and SideNav;
- SideNav semantic icons;
- Drawer / DrawerHeader / Layout / LayoutContent;
- Button / Link / List / fields;
- AlertDialog deletion confirmation;
- public spacing, radius, type, color, focus and motion tokens.

Jig owns:

- destination state and order;
- selected Task id;
- Task workspace mode;
- seven dated Week buckets and their fluid product geometry;
- desktop Day's docked master-detail geometry;
- the Task-specific composition inside the workspace.

Forbidden:

- Task create/edit Dialogs;
- custom/private drawer or modal implementations;
- CSS reconstruction of Astryx Drawer internals;
- a second Task draft/domain model outside the local editor draft already used to construct canonical commands;
- a second icon system;
- fixed Week maximum width that leaves usable desktop canvas empty;
- destination changes caused by Task card selection.

## 6. Functional invariants preserved

This UX change must not alter canonical command semantics:

- edit with a changed `scheduled_date` uses the existing priority-guided insertion law;
- drag uses exact destination date/index;
- Move to date remains a non-drag exact-position `move` operation and appends to the chosen destination date;
- completion/reopen behavior is unchanged;
- Delete is unchanged apart from presentation entry;
- local-save/synchronization behavior is unchanged.

## 7. Browser acceptance

Permanent browser tests must prove:

1. desktop rail is approximately 112px at 1440px and nav order is Day → Week → History → Settings;
2. all four SideNav destinations render semantic icons;
3. Day remains the default destination;
4. Week board starts immediately after the compact rail and uses >1200px of the 1440px canvas;
5. Week columns are >=160px at the canonical desktop viewport;
6. at 1920px, Week board and individual columns materially expand;
7. Week card click leaves Week selected and opens the right-side non-modal Task Drawer;
8. Week board remains visible while the Drawer is open;
9. Edit switches that Drawer to the editor form rather than opening another Dialog;
10. Quick add and per-day Add task open create mode in the same Drawer;
11. desktop Day Add/Edit use the docked workspace and create no Task Dialog;
12. Move to date uses the workspace and the canonical move command;
13. narrow/mobile Task view/edit/create uses the Drawer presentation and no `.jig-editor-mobile-frame`;
14. Delete still requires the AlertDialog;
15. existing drag, completion, history, settings, theme and failure-state tests remain green.
