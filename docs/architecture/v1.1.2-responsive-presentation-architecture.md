# Jig v1.1.2 responsive presentation architecture

**Status:** BINDING architectural and placement pattern for v1.1.2 responsive UI separation.  
**Tracking issue:** #66.  
**Applies to:** configured application, onboarding and every v1.1.2 UI surface.

## 1. Architectural rule

Jig has one semantic/application state owner and **two presentation compositions** at the governed 73rem semantic layout boundary:

- **desktop / expanded presentation**;
- **narrow / mobile presentation**.

The branch is selected by Jig's existing `LayoutMode` from available layout width, not operating-system identity. A narrow Linux window renders the narrow composition. Android does not automatically mean narrow if a future Android window is wide enough for the desktop composition.

Shared state, commands and product rules remain above the presentation branch. Presentation branches may differ in hierarchy, primitive, placement, fixed/floating behavior, density, touch geometry, safe-area ownership, focus/dismissal path and motion composition.

The purpose of the split is not to duplicate the product. It is to give the same product semantics the correct interaction architecture for the available viewport.

## 2. One branch, not responsive DOM synthesis

The configured application branches once:

```tsx
return layoutMode === "desktop" ? (
  <DesktopConfiguredApplication {...sharedStateAndActions} />
) : (
  <NarrowConfiguredApplication {...sharedStateAndActions} />
);
```

Only one presentation tree is mounted.

Prohibited patterns:

- rendering desktop and narrow trees simultaneously and hiding one with CSS;
- using `display:none`, order, absolute positioning or offsets to turn one semantic hierarchy into another;
- passing `layoutMode` deep through shared leaves so they become hidden viewport-specific component systems;
- duplicating application/domain state below the branch.

CSS media queries remain valid only for genuine adaptive reflow/density/hit geometry inside a shared semantic component.

## 3. Branch at composition seams

Use a **distinct presentation owner** when desktop and narrow/mobile differ in any of:

- navigation hierarchy or location;
- overlay primitive;
- fixed/floating placement;
- action hierarchy or placement;
- master/detail composition;
- Planner structure;
- feedback placement;
- safe-area ownership;
- focus/dismissal path;
- interaction activation model where the difference changes surrounding composition.

Use one **shared adaptive component** when all of these are true:

1. semantic purpose is the same;
2. child/action hierarchy is the same;
3. state owner is the same;
4. focus and dismissal semantics are the same;
5. no viewport-specific fixed/floating placement is required;
6. no different Astryx primitive is required.

If one criterion fails, split the presentation at the smallest useful composition seam and share only the lower semantic leaves.

## 4. State and command ownership remains singular

The current application/controller owner remains responsible for:

- destination;
- Planner horizon;
- canonical Tasks and recurrences;
- selected/create/edit Task workspace state;
- operation confirmation and durable attention state;
- repository synchronization status and diagnostics;
- theme/appearance;
- setup/onboarding state;
- command callbacks.

v1.1.2 may extract focused hooks/modules, but it must not create:

- Desktop Task state and Narrow Task state;
- Desktop Planner state and Narrow Planner state;
- duplicate navigation state;
- duplicate synchronization/diagnostic state;
- desktop/mobile command mapping layers;
- desktop/mobile DTO/view-model hierarchies;
- parallel Task sequence projections.

Presentation props consume the existing typed application/core state and callbacks directly.

## 5. Target component topology

```
ui/src/
  app.tsx                         # application/controller state only
  use-layout-mode.ts              # one semantic layout-mode owner

  presentation/
    desktop/
      configured-application.tsx  # desktop AppShell-main composition
      header.tsx                  # 3-zone desktop chrome/nav/Add/status
      planner.tsx                 # seven-track desktop Planner
      feedback-region.tsx         # bounded top-end success/attention placement
      setup.tsx                   # two-region onboarding
      task-workspace.tsx          # end Drawer presentation

    narrow/
      configured-application.tsx  # narrow AppShell-main composition
      header.tsx                  # application row + Planner temporal row
      bottom-navigation.tsx       # fixed Planner/History/Settings nav + FAB owner
      planner.tsx                 # stacked dated sections
      feedback-region.tsx         # snackbar + inline attention placement
      setup.tsx                   # single-column onboarding
      task-workspace.tsx          # BottomSheet presentation

    shared/
      planner-date-section.tsx    # date heading/count/Add semantics
      planner-task-sequence.tsx   # canonical+drag-preview Task sequence projection
      task-card.tsx               # Task content/actions/states
      task-editor.tsx             # one form/validation owner
      task-action-menu.tsx        # one semantic action set
      history.tsx                 # shared reading hierarchy
      settings.tsx                # shared settings hierarchy
      diagnostics.tsx             # one diagnostic projection
      feedback-content.tsx        # message/icon/action/dismiss anatomy
      delete-confirmation.tsx     # one AlertDialog decision
      loading-state.tsx           # shared state/copy with adaptive measure
```

Exact filenames may vary, but ownership boundaries do not.

Desktop presentation modules must not import narrow presentation modules and vice versa. Both may import shared leaves.

## 6. Binding placement contract

This section defines where each product surface belongs. The [responsive interaction matrix](../design/v1.1.2-responsive-interaction-matrix.md) is the concise registry; this section is the architectural explanation.

| Surface | Desktop / expanded placement | Narrow / mobile placement | Ownership |
|---|---|---|---|
| Application shell | Full-bleed AppShell; one 44px top chrome row; AppShell main is scroll owner | Full-bleed AppShell; sticky narrow chrome; AppShell main is scroll owner with bottom-nav safe-area reservation | Shared Astryx AppShell primitive; separate configured composition |
| Identity/Home | Left zone of desktop header | Left of application row | Distinct header presenters; shared Home intent |
| Destination title | Center zone for History/Settings; Planner center is temporal group | Center of application row for Planner/History/Settings | Distinct header presenters |
| Planner temporal controls | Centered inline `Previous · range · Next · Today` in the single desktop header row | Dedicated second Planner temporal row below application row | Distinct header presenters |
| Primary navigation | Planner/History/Settings inline at desktop header end | Persistent fixed bottom navigation | Distinct presentation owners |
| Global Add | Compact primary action in desktop Planner header end zone | Planner-only bottom-end FAB above bottom nav | Distinct presentation owners; same create command |
| Sync status | Restrained text+icon control in desktop header end zone | Compact icon status at application-row end | Distinct status presentation over one status state |
| Transient success | Compact bounded top-end stack/overlay in configured desktop viewport; never page-wide | Inset snackbar above bottom navigation and safe area | Separate feedback regions; shared confirmation state/content |
| Durable attention | Bounded desktop alert region near top-end/content start; no mobile full-width banner treatment | Inline/inset available-width alert below sticky chrome and above destination content | Separate feedback regions; shared attention state/content |
| Planner | Seven equal-width dated tracks across full application canvas | Seven vertically stacked dated sections | Separate Planner presenters |
| Date header/count/Add | Inside each desktop track | At top of each narrow date section with touch geometry | Shared date-section semantics; presenter supplies geometry |
| Task sequence | Compact vertical card sequence inside each desktop track | Full-width touch sequence inside each dated section | Shared sequence semantics; presenter supplies list geometry |

| Empty Planner/date state | Inline/open-canvas orientation and optional desktop date/global action placement | Lightweight orientation; FAB remains primary global Add | Separate Planner composition decision |
| Task workspace | Non-modal end Drawer, approximately 30rem, desktop action placement | Tall BottomSheet from bottom with mobile header and persistent footer actions | Separate workspace presenters; one draft/form state |
| Task editor fields | Shared field order/validation in Drawer body | Same fields/validation in BottomSheet body with touch reflow | Shared editor leaf |
| Task action menu | Anchored desktop DropdownMenu/popover | Touch-operable adaptive menu from same action trigger | Shared semantic menu; Astryx adaptive mechanics |
| Permanent delete | Centered blocking AlertDialog | Responsive blocking AlertDialog | Shared semantic primitive/state |
| Onboarding frame | Canonical desktop application chrome + two-region body (value/context + bounded setup pane) | Canonical narrow application chrome + one-column setup flow | Separate setup presenters; shared setup state/actions |

| History | Centered continuous reading surface, max 50rem | Same semantic hierarchy using available width/insets and touch geometry | Shared adaptive view |
| Settings | Centered max-50rem reading hierarchy; rows/actions may remain horizontal | Same groups/order; rows/actions stack and touch actions may fill width | Shared adaptive view |
| Diagnostics | Compact key/value grid with bounded actions | One-column facts with touch-safe/full-width actions where needed | Shared adaptive view |
| Appearance controls | Compact controls inside Settings | Same choices with touch sizing/wrapping | Shared adaptive controls |
| Notifications settings | Horizontal-capable Settings row/group | Stacked touch-friendly group | Shared adaptive controls |
| Loading/fatal states | Bounded centered state in desktop main region | Inset available-width state | Shared state/copy with adaptive measure |
| References/links | Inline/bounded card/workspace actions | Same semantics with >=48px touch target geometry | Shared leaf |
| Motion | Same governed duration-token scale | Same governed duration-token scale | Shared tokens; composition-specific transitions |
| Reduced motion | Remove/reduce motion without changing desktop result | Remove/reduce motion without changing narrow result | Shared policy |

A surface not listed here must be added to this contract/matrix before implementation if it introduces a new placement or hierarchy decision.

## 7. Configured application frame and scrolling

Both presenters use the same Astryx `AppShell height="fill"`. AppShell main remains the sole application scroll owner.

### DesktopConfiguredApplication

Desktop composition order:

1. desktop header is supplied as AppShell top navigation;
2. desktop feedback overlay/region is positioned relative to the configured viewport without becoming a full-width layout row for transient success;
3. destination content fills the remaining AppShell main height;
4. no bottom navigation or safe-area footer reservation exists;
5. workspace Drawer overlays from the logical end.

### NarrowConfiguredApplication

Narrow composition order:

1. sticky narrow header owns application row and Planner-only temporal row;
2. durable attention is placed below sticky chrome;
3. destination content flows through AppShell main;
4. transient snackbar is positioned above the persistent bottom navigation;
5. persistent bottom navigation owns the bottom safe-area reservation;
6. Planner FAB is positioned relative to bottom navigation/safe area;
7. workspace BottomSheet overlays from the bottom.

Neither presenter introduces a second page-level `overflow:auto` container.

## 8. Planner composition and shared Task semantics

Desktop and narrow Planner presenters consume the same:

- seven displayed civil dates;
- canonical Task collection;
- recurrence metadata;
- selected Task identity;
- create/select/edit/complete/priority/delete/move commands;
- one transient drag prospective placement.

`DesktopPlanner` owns seven-track geometry. `NarrowPlanner` owns stacked-section geometry.

Shared `PlannerDateSection` owns date label/count/future-date Add semantics. Shared Task sequence derivation owns canonical ordering plus the one drag prospective placement. Shared Task-card content owns controls, metadata, priority/reminder/selection/completion presentation.

The same Task card is not required to have the same box dimensions in both modes. Desktop density and narrow touch geometry are intentional presentation differences; semantic anatomy/actions remain singular.

## 9. Workspace, overlays and focus/dismissal

A different overlay primitive is a composition difference.

- Desktop Task workspace uses Drawer.
- Narrow Task workspace uses BottomSheet.
- Permanent delete remains one adaptive AlertDialog because the blocking decision/focus semantics are unchanged.
- Task action menu remains one semantic DropdownMenu owner where Astryx provides the correct adaptive mechanics.

Workspace presenters receive one draft and one set of Save/Cancel/Delete callbacks. They may place those actions differently; they may not create separate drafts or validation.

Breakpoint changes while a workspace is open must preserve the draft and selection while replacing only the presentation primitive.

## 10. Feedback separation

Feedback has one semantic owner above the branch and two placement owners below it.

`feedback-content.tsx` may own:

- status icon;
- title/message;
- optional action;
- dismiss action;
- ARIA/live-region semantics.

It may not own top/end/fixed/inline placement.

Desktop transient success must be compact and bounded. Narrow transient success must account for the persistent bottom navigation and safe area. Durable attention may occupy flow in both modes but uses viewport-appropriate width/placement.

No Toast/snackbar state is introduced; snackbar/toast describes presentation only.

## 11. CSS ownership

Split CSS by presentation ownership rather than continuing one global responsive override block:

```
ui/src/styles/
  shared.css      # shared leaves, semantic states, product aliases
  desktop.css     # desktop presentation classes/geometry only
  narrow.css      # narrow presentation classes/geometry/safe areas only
  motion.css      # Jig keyframes and reduced-motion policy
```

Rules:

- desktop selectors target DOM rendered only by desktop presenters;
- narrow selectors target DOM rendered only by narrow presenters;
- shared CSS may use media queries only for pure reflow/density/hit geometry of a shared leaf;
- no CSS rule may hide one full presentation tree to reveal another;
- no narrow fixed surface class may appear in desktop DOM;
- no desktop header/nav composition may appear in narrow DOM;
- feature CSS consumes semantic/theme tokens, never theme-name branches.

## 12. Migration order

1. **Configured frame:** move controller state above a single desktop/narrow branch; create `DesktopConfiguredApplication` and `NarrowConfiguredApplication` with AppShell main as sole scroll owner.
2. **Feedback:** extract shared feedback content; implement desktop/narrow feedback regions and remove unconditional topNav-sibling placement.
3. **Header/navigation/Add/status:** split desktop header from narrow header/bottom-nav/FAB while retaining one destination/horizon/status owner.
4. **Task workspace:** place shared TaskEditor in Drawer vs BottomSheet presenters.
5. **Planner:** create DesktopPlanner/NarrowPlanner over shared date-section/Task-sequence/card leaves.
6. **Drag:** replace insertion slots with shared React-owned prospective placement consumed by both Planner presenters.
7. **Onboarding:** split desktop two-region and narrow one-column setup composition around one setup state machine.
8. **Secondary screens:** keep History/Settings/Diagnostics shared; remove viewport-specific hierarchy branches from them unless the audit demonstrates a true composition difference.
9. **CSS:** move layout-specific rules into desktop/narrow ownership files and delete superseded media-query overrides.
10. **Architecture gates:** enforce import direction, single mounted tree and matrix ownership.
11. **Browser evidence:** certify every matrix row in both presentation modes before release.

Migration may be staged internally, but the release candidate must not retain two competing responsive ownership systems.

## 13. Testing contract

For every distinct presentation pair:

- assert only one branch is mounted;
- verify declared placement/geometry, not only text presence;
- exercise equivalent semantic actions in desktop and narrow;
- compare resulting canonical Task/navigation/sync state to prove presentation does not fork behavior;
- verify focus/dismissal and breakpoint transition behavior.

For shared adaptive surfaces:

- prove one semantic implementation is rendered in both modes;
- certify width/reflow/hit geometry;
- reject duplicated state/data projections.

Architecture tests fail if:

- desktop imports narrow presentation modules or vice versa;
- a shared leaf imports a viewport-specific presenter;
- controller/application state is created below both branches;
- a material composition difference is implemented only through CSS hiding/reordering;
- both configured presentation trees exist simultaneously;
- AppShell main ceases to be the sole configured application scroll owner;
- a new UI surface lacks a matrix classification.

## 14. Design rationale

This architecture applies two principles simultaneously:

- **single source of truth for semantics** — shared application state, commands and domain rules stay singular;
- **explicit adaptive composition** — layout class selects the hierarchy and placement appropriate to the viewport instead of stretching a phone composition across desktop or compressing desktop composition onto touch.

This is the intended FCIS/DRY boundary for Jig: share meaning, not necessarily markup.
