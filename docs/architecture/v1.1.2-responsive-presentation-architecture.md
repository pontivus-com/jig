# Jig v1.1.2 adaptive presentation and runtime architecture

**Status:** BINDING v1.1.2 solution design for desktop/narrow presentation separation and Linux/browser versus Android/native capability separation.  
**Tracking issue:** #66.  
**Applies to:** configured application, onboarding, platform lifecycle and every v1.1.2 UI surface.

This document corrects the ambiguity in treating "desktop/mobile" as one dimension. Jig has one product and one semantic application state, but presentation geometry, runtime/platform capability and input modality are not the same concern and must not share one switch.

## 1. Governing model

Jig has three independent concerns:

### 1.1 Presentation class

`LayoutMode = "desktop" | "narrow"` is selected only from the governed **73rem / 1168px** available-width boundary.

It owns:

- hierarchy and composition;
- placement;
- desktop versus narrow navigation;
- seven-track versus stacked Planner;
- Drawer versus BottomSheet;
- desktop versus narrow feedback placement;
- responsive density/reflow where the hierarchy changes.

It does **not** own Android/browser capability.

### 1.2 Runtime capability

Runtime mechanics are selected at the imperative-shell boundary:

- **Linux/browser**;
- **Android/native**.

Runtime capability owns:

- configured transport;
- repository acquisition/storage mechanics;
- secure credential storage;
- notification delivery/scheduling;
- native lifecycle;
- native Back;
- native system bars;
- Android reminder reconciliation;
- platform synchronization opportunities.

Runtime identity does **not** select desktop/narrow markup.

### 1.3 Input/capability observation

Input facts are observed only where needed:

- mouse/pen/touch pointer type for drag activation;
- keyboard/focus behavior;
- software keyboard/IME interaction;
- coarse-pointer/touch target requirements;
- safe-area environment values.

Do not create a global `isMobile`, `deviceClass` or input-mode state store.

A narrow Linux window therefore remains Linux/browser while using narrow presentation. Android remains Android/native regardless of presentation width. A future wide Android window may use expanded presentation, but native lifecycle/notification/system-bar capabilities remain native and touch/coarse-pointer interaction requirements remain based on actual input capability.

## 2. One semantic/application owner

The following meanings remain singular above both presentation and runtime mechanics:

- destination and navigation history;
- Planner horizon;
- canonical Tasks and recurrences;
- selected/create/edit Task workspace state and draft;
- operation confirmation and durable attention state;
- repository synchronization status and diagnostics;
- theme/appearance state;
- setup/onboarding semantic state;
- command callbacks.

Do not introduce:

- Desktop Task state / Mobile Task state;
- Browser Task state / Android Task state;
- duplicate Planner sequence state;
- desktop/mobile DTOs or view-model maps;
- platform Task/Planner models;
- separate sync/diagnostic state by viewport;
- duplicated setup state machines.

Presentation and runtime adapters are controlled projections/effects around the same semantic owners.

## 3. Dependency and ownership shape

```text
                     canonical application semantics
        destination / Planner / Tasks / workspace / feedback / sync
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
        presentation selection       runtime capability selection
          LayoutMode only              adapter boundary only
                 │                           │
       ┌─────────┴─────────┐        ┌────────┴────────┐
       │                   │        │                 │
 desktop/expanded       narrow   Linux/browser    Android/native
 presentation        presentation  capabilities     capabilities
       │                   │        │                 │
       └───────── shared semantic leaves ────────────┘
                               │
                 pointer / keyboard / IME facts
                    observed only where needed
```

The arrows are one-way. Runtime adapters do not import presentation components. Presentation components do not own Git/SQLite/native mechanics.

## 4. Detection boundaries

### 4.1 Layout detection

`use-layout-mode.ts` is the one presentation-class owner.

It may use the governed media query and return only `desktop | narrow`.

No runtime adapter may use `LayoutMode` to choose Git, SQLite, credential, notification or native mechanics.

### 4.2 Platform detection

Raw `Capacitor.isNativePlatform()`, Capacitor plugin registration and native-plugin calls are confined to:

- platform adapter modules such as `runtime.ts`, `setup-http.ts`, `notification-settings.ts`;
- bounded native leaves under `ui/src/native/`;
- the composition/root integration needed to mount those effects.

Ordinary Planner, Task, History, Settings and presentation modules must not inspect native identity directly.

When user-visible choices genuinely differ, the UI consumes a typed capability result such as:

- `SetupStatus.local_repository_available`;
- `GitHubCapabilityStatus`;
- `NotificationSettingsState`.

It does not perform a second runtime test.

## 5. Presentation branch

The configured application branches once:

```tsx
return layoutMode === "desktop" ? (
  <DesktopConfiguredApplication {...sharedStateAndActions} />
) : (
  <NarrowConfiguredApplication {...sharedStateAndActions} />
);
```

Only one configured presentation tree is mounted.

Prohibited:

- rendering both trees and hiding one with CSS;
- CSS reordering/absolute positioning to transform the wrong semantic hierarchy;
- deep `layoutMode` branching through shared leaves;
- duplicating controller state below the branch.

Use a separate presenter when hierarchy, primitive, fixed/floating placement, safe-area ownership or focus/dismissal path differs. Share a leaf only when semantic child/action hierarchy and interaction ownership remain the same.

## 8. Binding runtime capability contract

Presentation class does not change the following platform ownership.

| Concern | Linux/browser runtime | Android/native runtime | Owner |

| Repository bootstrap | GitHub managed acquisition + existing-local-repository when capability available | GitHub acquisition only | `setup-http.ts` + platform setup adapter |
| Existing local repository | genuine user-selectable path | unavailable; no arbitrary device worktree import | setup capability result |
| Repository storage | deterministic managed checkout or selected existing worktree | app-private repository storage | platform Git/setup shell |

| GitHub credential storage | Secret Service | Android Keystore + app-private encrypted metadata | platform credential adapter |

## 9. Input and interaction capability contract

Input behavior must use actual input facts rather than platform labels.

### Drag

- mouse/pen: short distance threshold;
- touch: deliberate hold + movement tolerance;
- dedicated grip only;
- dnd-kit optimistic DOM sorting remains disabled;
- one React prospective placement drives both desktop and narrow presenters;
- KeyboardSensor and Move up/down remain alternatives.

A narrow Linux window using mouse therefore gets narrow layout with mouse activation. Android/touch gets touch activation independent of width.

### Touch geometry

Narrow presentation retains the governed >=48px ordinary interaction floor.

If an expanded presentation is used in a coarse-pointer/native environment, interactive controls must still satisfy the touch accessibility floor where they are expected to be tapped. Do not equate "expanded" with "fine pointer".

### Software keyboard / IME

BottomSheet/form presentation must keep:

- active field visible;
- remaining fields reachable;
- Save/Cancel reachable;
- validation/Reference/Notes unobscured;
- normal scrolling after viewport resize.

IME behavior is presentation/runtime interaction, not form/domain state.

## 10. Configured application frame and scrolling

Both presenters retain Astryx `AppShell height="fill"`.

AppShell main is the sole application/page scroll owner.

### Desktop

1. desktop header in AppShell top navigation;
2. bounded transient feedback overlay/region;
3. destination content fills remaining main region;
4. no bottom-navigation reservation;
5. Drawer overlays from logical end.

### Narrow

1. sticky application row and Planner-only temporal row;
2. durable attention below sticky chrome;
3. destination content in AppShell main;
4. transient snackbar above bottom navigation;
5. persistent bottom navigation owns bottom safe-area reservation;
6. Planner FAB relates to bottom navigation/safe area;
7. BottomSheet overlays from bottom.

Remove the current competing configured `.jig-content-frame { height: 100%; overflow:auto; }` page scroller during implementation.

## 11. Planner and Task composition

Desktop and narrow Planner presenters consume identical:

- displayed dates;
- canonical Tasks/recurrences;
- selected Task;
- command callbacks;
- one drag prospective placement.

`DesktopPlanner` owns seven-track geometry. `NarrowPlanner` owns stacked geometry.

Shared leaves own:

- date semantics;
- Task sequence/order semantics;
- Task-card content/actions;
- priority/reminder/recurrence/reference state.

The Task card may have different box dimensions, spacing and touch targets by presentation/input capability without creating a second Task component meaning.

## 12. Task workspace, forms and focus

Drawer and BottomSheet are alternate presentations of one Task workspace state.

Breakpoint changes while open:

- preserve exact draft;
- preserve selected/create mode;
- replace only the presentation primitive;
- do not save/cancel implicitly.

Desktop and narrow may place Save/Cancel/Delete differently, but the command and validation owner remains singular.

Android Back dismisses the currently open workspace through the same shared close callback. It does not maintain a native copy of workspace state.

## 13. Onboarding architecture

Onboarding has two independent differences.

### Presentation difference

- desktop: two-region body;
- narrow: one-column body.

### Runtime-capability difference

- Linux/browser may expose **Use an existing local repository** only when `local_repository_available` is true;
- Android does not expose arbitrary local worktree selection;
- both may expose the same **Connect GitHub repository** intent when GitHub onboarding is available.

Therefore setup presenter code must not use `layoutMode === "desktop"` as proof that local-repository setup exists. The genuine action is rendered from the setup capability result.

GitHub Device Flow semantics remain shared. Provider return continuation differs by runtime lifecycle but not by user workflow.

## 14. Notification and reminder UX

The Settings Notifications section is shared in section placement but capability-specific in content.

### Browser

May show:

- unsupported;
- permission not yet granted;
- granted;
- denied/blocked.

It never shows exact-alarm settings.

### Android

May show:

- notification permission required;
- granted;
- denied/blocked;
- exact timing available;
- exact timing unavailable;
- **Exact timing settings** action when that capability is relevant.

The in-app reminder-due Task state remains shared and independent from notification delivery.

No browser/Android notification state becomes canonical Task state.

## 15. Native lifecycle, Back and system bars

### Activation/resume

One native lifecycle owner handles Android activation. The ordered product effects are:

1. perform missed local-day rollover when required;
2. resume GitHub onboarding/reconnect continuation if active;
3. refresh configured canonical state;
4. reconcile Android local reminders;
5. trigger/re-observe synchronization;
6. update shared application/status state.

The implementation may split effects internally only if ordering/dependencies remain explicit and one activation registration owns the event. Feature destinations do not add their own native activation listeners.

### Back

Native Android Back order:

1. dismiss open Task workspace/owned overlay;
2. navigate shared Jig destination history when available;
3. delegate to browser/WebView history when possible;
4. exit application otherwise.

Escape/browser Back remain separate ordinary browser interactions.

### System bars

Native status/navigation bars follow active theme appearance through the bounded native system-bar effect. They do not create another Theme state.

## 16. CSS and safe-area ownership

Target CSS ownership:

```text
ui/src/styles/
  shared.css
  desktop.css
  narrow.css
  motion.css
```

Rules:

- desktop CSS targets only desktop-presenter DOM;
- narrow CSS targets only narrow-presenter DOM;
- shared media queries may alter only genuine adaptive leaf reflow/density;
- coarse-pointer rules may increase hit geometry without changing semantic hierarchy;
- no duplicated responsive trees hidden with CSS;
- no feature theme-name branches.

Safe areas have one owner per edge:

- top: narrow/native application header;
- bottom configured navigation: narrow bottom navigation;
- snackbar/FAB/BottomSheet position relative to that owned bottom inset rather than adding it independently again.

This prevents the prior duplicated safe-area regression.

## 17. Migration order

1. Extract one width-only desktop/narrow configured branch while leaving state above it.
2. Extract desktop/narrow headers, navigation, Add and status.
3. Extract desktop/narrow feedback placement with shared feedback content.
4. Extract Drawer/BottomSheet workspace presenters over shared form state.
5. Extract desktop/narrow Planner composition over shared date/Task leaves.
6. Replace insertion-slot drag with shared prospective placement consumed by both Planner presenters.
7. Split onboarding presentation from runtime capability: composition from `LayoutMode`, available repository choices from `SetupStatus`.
8. Make notification Settings consume only `NotificationSettingsState`; no raw platform detection in Settings.
9. Consolidate native activation/Back/system-bar effects at bounded root/native seams.
10. Move layout-specific CSS to desktop/narrow owners; retain shared leaf/coarse-pointer rules only.
11. Add architecture gates for platform-detection boundaries, presentation boundaries and safe-area singularity.
12. Certify every row of the adaptive matrix across required combinations.

The release candidate must not retain the current mixed model where layout, runtime and platform behavior can be inferred from each other.

## 18. Acceptance combinations

The complete matrix is not merely "desktop browser vs Android phone".

At minimum browser/UI evidence covers:

- expanded Linux/browser + fine pointer;
- narrow Linux/browser + fine pointer;
- narrow/coarse-pointer emulation where relevant;
- Android/native narrow physical/emulator acceptance.

Where the implementation permits expanded Android presentation, certify expanded Android/coarse-pointer geometry too.

For each combination verify:

- only the correct presentation tree is mounted;
- runtime capabilities/actions are correct for the platform;
- shared semantic actions produce the same canonical outcomes;
- platform-only actions never leak to the other runtime;
- touch/input activation follows actual input;
- safe-area/system-bar/IME behavior is correct;
- breakpoint changes preserve workspace/navigation/Task state.

## 19. Architecture failure conditions

The v1.1.2 implementation fails this design if any of the following exist:

- a global `isMobile` controls both platform behavior and presentation;
- `Capacitor.isNativePlatform()` appears in ordinary feature presentation;
- `LayoutMode` is used to select Git/SQLite/credential/notification mechanics;
- desktop and narrow trees are both mounted and CSS-hidden;
- Android-only notification/exact-alarm actions appear in browser state;
- local-repository onboarding is shown because a viewport is desktop rather than because the capability exists;
- native activation/Back is registered by multiple feature owners;
- safe-area inset is applied twice at one edge;
- browser/native mechanics create duplicate Task, Planner, workspace, sync or navigation state;
- a material current platform/responsive difference is absent from the binding matrix.

## 20. Design rationale

Jig applies DRY at the **meaning** level, not by forcing one markup tree or one imperative adapter to serve incompatible environments.

- share domain/application semantics;
- separate presentation when hierarchy/placement differs;
- separate platform adapters when external capabilities differ;
- observe input modality where interaction differs;
- keep each selector narrow and authoritative.

This is the FCIS/SoC boundary for Jig v1.1.2.
