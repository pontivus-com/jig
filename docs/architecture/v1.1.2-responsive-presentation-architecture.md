# Jig v1.1.2 responsive presentation architecture

**Status:** BINDING architectural pattern for v1.1.2 responsive UI separation.  
**Tracking issue:** #66.  
**Applies to:** configured application, onboarding and every future Jig UI surface.

## 1. Architectural rule

Jig has one semantic/application state owner and **two presentation compositions** at the governed semantic breakpoint:

- **desktop / expanded presentation**;
- **narrow / mobile presentation**.

The branch is selected by Jig's existing `LayoutMode` / 73rem semantic window boundary, not by operating-system identity. Linux/Desktop may render the narrow composition in a narrow window. A future larger Android window is not forced to use phone composition merely because the runtime is Android.

Shared state and product rules remain above the presentation branch. Presentation branches may differ in hierarchy, primitive, placement, density, interaction geometry and motion composition.

This is the same single-source-of-truth principle already used by React: state shared by multiple presentations lives in their nearest common owner; renderers are controlled projections of that state.

## 2. Branch at composition seams, not at every component

Use a **presentation branch** when desktop and narrow/mobile differ in one or more of:

- navigation hierarchy or location;
- overlay primitive (Drawer vs BottomSheet);
- fixed/floating placement;
- action hierarchy or placement;
- master/detail composition;
- feedback placement;
- Planner structure;
- interaction activation model;
- safe-area ownership;
- focus/dismissal path.

Use one **shared adaptive component** when:

- semantic hierarchy is the same;
- actions remain in the same relative place;
- interaction semantics are unchanged;
- only width, wrapping, spacing, density or touch target sizing changes.

CSS media queries are restricted to the latter category: pure reflow/density. They must not hide one semantic hierarchy and synthesize another.

## 3. Target component topology

```
ui/src/
  app.tsx                         # application/controller state; no viewport-specific DOM
  use-layout-mode.ts              # one semantic layout-mode owner

  presentation/
    desktop/
      configured-application.tsx  # desktop AppShell composition
      header.tsx                  # desktop 3-zone header + nav + Add
      planner.tsx                 # 7-track desktop Planner composition
      feedback-region.tsx         # bounded top-end toast/attention region
      setup.tsx                   # desktop two-region onboarding
      task-workspace.tsx          # Drawer presentation

    narrow/
      configured-application.tsx  # narrow AppShell composition
      header.tsx                  # app row + temporal row
      bottom-navigation.tsx       # bottom nav + Planner FAB
      planner.tsx                 # stacked dated-section composition
      feedback-region.tsx         # safe-area-aware snackbar/attention region
      setup.tsx                   # one-column onboarding
      task-workspace.tsx          # BottomSheet presentation

    shared/
      planner-date-section.tsx    # date heading/count/Add semantics
      task-card.tsx               # Task content/actions/priority/completion
      task-editor.tsx             # one Task form/validation owner
      task-action-menu.tsx        # shared semantic menu
      history.tsx                 # same reading hierarchy; adaptive reflow only
      settings.tsx                # same settings hierarchy; adaptive reflow only
      diagnostics.tsx             # one diagnostic state projection
      feedback-content.tsx        # message/icon/action/dismiss anatomy, no placement
      delete-confirmation.tsx     # shared AlertDialog semantics
```

Exact filenames may vary during extraction, but the ownership boundaries are binding.

## 4. Application state remains singular

The current `AppContent` owns destination, Planner horizon, canonical Task data, Task workspace state, operation feedback, repository status, diagnostics, appearance and commands. v1.1.2 may extract those concerns into focused hooks/modules, but it must not create separate desktop/mobile copies.

The presentation branch receives controlled state/callbacks from the same owner. Do **not** create:

- Desktop Task state and Mobile Task state;
- Desktop navigation state and Mobile navigation state;
- duplicated synchronization state;
- desktop/mobile command mapping layers;
- DTO/view-model translation hierarchies.

Component props are typed directly from canonical/shared application types and callbacks. Shared semantic hooks may be used where they have one owner; they must not become parallel state stores.

## 5. Branch once at the configured-application seam

The configured application should converge on this structural shape:

```tsx
return layoutMode === "desktop" ? (
  <DesktopConfiguredApplication ...sharedStateAndActions />
) : (
  <NarrowConfiguredApplication ...sharedStateAndActions />
);
```

Only one presentation branch is mounted at a time. Do not render desktop and mobile trees simultaneously and hide one with CSS.

Each configured presentation composes the same semantic destinations and state through the appropriate presentation owners.

## 6. Surface classification

### Must be separate presentation components

| Surface | Desktop owner | Narrow/mobile owner | Shared semantic owner |
|---|---|---|---|
| Application chrome | 3-zone desktop header/navigation | app row + temporal row + bottom nav/FAB | destination + Planner horizon + sync status |
| Planner composition | 7 dated tracks | stacked dated sections | displayed dates + date section semantics + Task sequences |
| Task workspace | Drawer | BottomSheet | one Task workspace draft/form/actions |
| Transient success feedback | bounded top-end toast stack | safe-area-aware snackbar | one operation-confirmation state |
| Durable attention | bounded wide-screen alert region | inline/inset narrow alert | one error/sync-attention state |
| Onboarding | two-region desktop setup | single-column narrow setup | one setup state machine/actions |

### Shared semantic component with adaptive CSS only

| Surface | Why shared |
|---|---|
| Task card content | same controls, Task semantics and ordering; only geometry/touch sizing changes |
| Task editor fields | same field order, validation and commands; outer workspace owns desktop/mobile action placement |
| History | same reading hierarchy; width and hit geometry reflow |
| Settings | same group/order/semantics; rows/actions stack only when narrow |
| Diagnostics | same facts and support action; key/value layout reflows |
| Delete confirmation | same blocking decision through adaptive Astryx AlertDialog |
| Task action menu | same actions through adaptive Astryx menu/popover primitive |
| Theme/appearance controls | same choices; touch sizing/wrapping only |

### Shared interaction engine with responsive configuration

| Interaction | Shared engine | Responsive configuration |
|---|---|---|
| Drag/drop | one dnd-kit sortable operation owner | mouse/pen threshold vs touch hold+tolerance; desktop/narrow Planner presenter supplies geometry |
| Motion | one public duration-token scale | same tempo; different surfaces may use different duration family |
| Synchronization | one sync controller/diagnostic state | only status/diagnostic presentation placement differs |

## 7. CSS ownership

Split CSS by ownership instead of growing one media-query block indefinitely:

```
ui/src/styles/
  shared.css      # tokens consumed by Jig, semantic states, shared leaves
  desktop.css     # desktop presentation classes only
  narrow.css      # narrow presentation classes only
  motion.css      # Jig-authored keyframes/reduced-motion policy
```

The build imports all files, but desktop/narrow rules target components that exist only in the corresponding render branch. Media queries remain allowed inside shared CSS only for genuine adaptive reflow where markup/interaction ownership does not change.

Do not use:
- `display:none` to switch between duplicate semantic trees;
- offset/absolute-position hacks to turn mobile DOM into desktop DOM;
- narrow-only class names on desktop shared components;
- a global media-query block as the primary owner of materially different hierarchy.

## 8. Responsive leaf rule

A component belongs in `shared/` only if all of these are true:

1. same semantic purpose;
2. same child/action hierarchy;
3. same focus and dismissal semantics;
4. same state owner;
5. no viewport-specific fixed/floating placement;
6. no different Astryx primitive required.

If any criterion fails, separate the presentation component and share only the lower semantic leaf.

Example: Task workspace fails #5/#6, therefore Drawer and BottomSheet are separate. Task editor fields satisfy all six, therefore they stay shared.

## 9. Migration order

1. **Application frame:** extract `DesktopConfiguredApplication` / `NarrowConfiguredApplication` from `app.tsx` while leaving all state/commands above the branch.
2. **Feedback:** move success/attention placement into desktop/narrow feedback regions; share message anatomy.
3. **Header/navigation:** move existing DesktopHeader and NarrowHeader/bottom navigation to presentation folders without semantic changes.
4. **Task workspace:** move existing Drawer/BottomSheet implementations into presentation folders; keep TaskEditor shared.
5. **Planner:** split board composition into DesktopPlanner and NarrowPlanner; extract shared DateSection and Task-card semantics. Desktop owns seven-track geometry; narrow owns stacked-date geometry.
6. **Onboarding:** extract desktop and narrow compositions around the existing shared setup state/actions.
7. **Secondary screens:** keep History/Settings/Diagnostics shared; remove layout-mode branching from them unless the audit finds a true semantic/composition difference.
8. **CSS:** move layout-specific rules out of the giant media-query block into desktop/narrow ownership files; retain only pure shared reflow media queries.
9. **Architecture gate:** add tests forbidding simultaneous desktop+narrow presentation trees and preventing narrow-only fixed controls/classes from appearing at desktop.

## 10. Testing contract

For every separate presentation pair:

- assert only one branch is mounted;
- test desktop and narrow behavior independently;
- share behavioral fixtures where the semantic outcome is identical;
- compare canonical Task/navigation/sync state after equivalent actions to prove presentation does not fork semantics.

For shared adaptive components:

- test one semantic implementation at both viewport classes;
- certify layout/hit geometry rather than duplicating behavioral tests.

Architecture checks should fail if:
- desktop imports a narrow presentation component or vice versa except through explicitly shared leaves;
- App/controller code imports layout-specific CSS/DOM details;
- a new semantic state store appears below the responsive branch;
- a material composition difference is implemented only through CSS hiding/reordering.

## 11. Why this pattern

This architecture combines two established principles:

- **single source of truth for state** — shared application state lives above alternate controlled presentations;
- **adaptive high-level layout** — window class selects the navigation/layout composition appropriate to available space instead of stretching one device-oriented layout across all sizes.

It preserves Jig's FCIS/DRY direction: semantics remain singular, while presentation composition is allowed to differ where the UX genuinely differs.
