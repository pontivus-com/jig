# Jig v1.1 — Android mobile, reminders and repository onboarding technical solution

**Status:** DESIGN COMPLETE — amended 2026-11-19 for the physical-mobile UX remediation and the cross-installation synchronization correction. GitHub authorization/data flow remains governed; the synchronization contract below now explicitly requires bidirectional Desktop/Linux ↔ Android remote-head observation, lineage classification and safe adoption before push decisions.  
**Functional authority:** [v1.1 mobile functional design](../requirements/v1.1-mobile-functional-design.md).  
**Baseline:** Jig v1.0.6 architecture on `master`.  
**Platform scope:** v1.1 native delivery is Android-only. iOS remains architecturally possible but is not built, certified or distributed in this release.  
**Architecture rule:** Satisfy the v1.1 functional contract with the smallest new platform boundaries. Do not create a second Task model, DTO/mapping hierarchy, repository-management subsystem or parallel planning workflow.

## 1. Decision summary

v1.1 uses the following target architecture:

1. **Shared product layer remains TypeScript/React.**
   - `src/core` remains the canonical pure Task/planning authority.
   - the existing React UI remains the primary presentation implementation.
   - portable Jig records remain exactly one cross-device continuity format.

2. **Linux remains a Bun + loopback HTTP + system-Git runtime.**
   - existing configured installations keep their current path;
   - the Linux runtime gains an explicit unconfigured bootstrap mode so the application can start before repository selection.

3. **Native Android uses Capacitor 8 as the application shell.**
   - existing Vite/React assets are embedded in an Android application;
   - native plugins/adapters own capabilities unavailable or inappropriate in the WebView: secure credentials, local notifications, native/app storage and SQLite access;
   - Android does not run the Linux Bun/systemd/loopback-server stack.

4. **GitHub is the optimized v1.1 remote-acquisition provider.**
   - a GitHub App supplies repository authorization;
   - authorization uses GitHub App Device Flow directly between Jig and GitHub with public `client_id` only;
   - the app requests only the repository permissions required for HTTP Git access;
   - provider tokens are stored in platform secure storage and are never embedded in Git remote URLs.

5. **Existing local desktop repositories stay provider-neutral.**
   - system Git and existing repository authentication/configuration continue to own those repositories;
   - no GitHub login is required for an already-usable checkout;
   - a checkout without a remote remains a valid healthy local-only Jig data home.

6. **Reminder attention becomes pure derived state.**
   - no `notified_at` or acknowledgement field is added to canonical Task;
   - notification delivery is a side effect separate from the reminder-due card state.

7. **Native Android reminder delivery uses OS local notifications.**
   - scheduled notifications must survive foreground/background transitions subject to platform policy;
   - desktop/browser delivery uses a service-worker-compatible browser Notification path while the UI is active, rather than relying only on the direct `Notification` constructor.

## 2. External capability evidence

The technical selections above are grounded in current upstream capabilities as of 2026-11-18:

- Capacitor 8 is explicitly designed to be added to an existing modern web application and targets iOS, Android and Web: https://capacitorjs.com/docs and https://capacitorjs.com/docs/getting-started
- Capacitor 8.6.2 is the current stable 8.x release used by this design; Capacitor 8 supports Android API 24+ and target SDK 36: https://www.npmjs.com/package/@capacitor/core and https://capacitorjs.com/docs/android
- AndroidX SQLite 2.7.1 provides the stable `sqlite-bundled` `BundledSQLiteDriver`, allowing one low-level SQLite engine without Room/SQLCipher: https://developer.android.com/jetpack/androidx/releases/sqlite
- Capacitor official plugins expose native filesystem, HTTP and local-notification capabilities to the web application: https://capacitorjs.com/docs/plugins and https://next.capacitorjs.com/docs/apis/local-notifications
- GitHub Apps can request `Contents` repository permission for HTTP Git access, and a GitHub App user access token can be used as the HTTP Git password. Effective access remains bounded by both the App permission and the user's own repository permission: https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app
- GitHub Device Flow starts with public `client_id` only and returns `device_code`, an 8-character `user_code`, fixed `verification_uri=https://github.com/login/device`, expiry and minimum polling interval. The user must enter the `user_code` on GitHub's provider-owned page; Jig may open that page automatically but there is no documented pre-authorized/deep-link form that removes the code-entry step. Polling must respect GitHub's interval and `slow_down` responses: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app
- GitHub's web authorization flow supports PKCE but still requires the GitHub App `client_secret` when exchanging the authorization code. Therefore it does not satisfy Jig's no-backend/no-shipped-secret public-client boundary; Device Flow is the governed v1.1 compromise despite its provider-required code-entry step.
- Device-Flow-generated user access tokens can be refreshed without `client_secret`. Expiring user access tokens are normally 8 hours and refresh tokens 6 months; using a refresh token rotates both, invalidating the previous access/refresh pair: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens
- GitHub distinguishes **authorization** from **installation**. Authorization lets the App act on behalf of the user; installation grants the App access to an account/organization and selected repositories. Either may exist without the other. Installation/access selection occurs on GitHub-owned surfaces.
- A user access token can only access the intersection of repositories available to both the user and the App installation. The authoritative discovery path is `GET /user/installations` followed by `GET /user/installations/{installation_id}/repositories`. Both endpoints are paginated with at most 100 results per page; Jig must consume all pages before deciding that an installation/repository is absent.
- GitHub installation may complete immediately or become an organization-owner request depending on account policy. The provider surface may show **Install**, **Install and request**, or **Request**; Jig cannot assume access exists merely because the browser/app returns from that surface.
- GitHub exposes APIs that can add/remove repositories from an existing installation for authorized users, but v1.1 deliberately does not use those mutation endpoints. Repository-access grants remain an explicit GitHub-owned user/organization decision rather than becoming Jig repository-management behavior.
- GitHub explicitly warns native/public clients not to embed a GitHub App private key and recommends platform-appropriate token storage: https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app
- `isomorphic-git` exposes clone/fetch/push against an injected filesystem and HTTP client and accepts OAuth/token authentication callbacks: https://isomorphic-git.org/docs/en/clone, https://isomorphic-git.org/docs/en/push and https://isomorphic-git.org/docs/en/authentication
- F-Droid main-repository inclusion requires a FLOSS application/dependency chain, public source and a source-buildable Android package; proprietary tracking/Google Play/Firebase-style dependencies are not acceptable in the main repository: https://f-droid.org/docs/Inclusion_Policy/ and https://f-droid.org/en/docs/Submitting_to_F-Droid_Quick_Start_Guide/
- F-Droid supports Gradle-based Android builds and upstream metadata, and provides fdroid build/fdroid lint tooling for packaging verification: https://f-droid.org/docs/Building_Applications/
- Android accessibility guidance recommends at least 48dp × 48dp touch targets and explicitly allows smaller precise-pointer targets; Jig therefore uses a 48 CSS px rendered mobile/WebView product floor while allowing denser desktop pointer controls: https://developer.android.com/guide/topics/ui/accessibility/apps
- Apple similarly recommends a general 44pt × 44pt button hit region and emphasizes spacing around controls; Jig's Android-first 48px floor is deliberately at least as generous rather than treating WCAG minimum conformance as the usability target: https://developer.apple.com/design/human-interface-guidelines/buttons
- WCAG 2.2 requires a non-drag single-pointer way to achieve functionality that otherwise uses dragging. Jig preserves same-date Move up/Move down and editable Date as those equivalent Task-movement paths: https://www.w3.org/TR/WCAG22/#dragging-movements
- Physical Android use of the implemented `@hello-pangea/dnd@18.0.1` path failed Jig's own SD-34/35 release gate: drag initiation/destination can become unreliable and leave a floating visual source without a committed move. Pangea is therefore rejected for v1.1 rather than patched with parallel sensors.
- The current rewritten dnd-kit packages `@dnd-kit/react@0.5.3` and `@dnd-kit/dom@0.5.3` provide Pointer Events sensors across mouse/touch/pen, per-pointer activation constraints, explicit drag handles, keyboard sensors, DragOverlay, droppable primitives and auto-scroll. The current PointerSensor also isolates the pointer that started a drag. These capabilities make it a **candidate** for Jig's dedicated-grip + explicit-insertion-slot design, subject to the mandatory desktop/physical-Android proof gate below: https://dndkit.com/react/guides/sensors/ and https://github.com/clauderic/dnd-kit/releases

These references justify capability, not application scope. Jig still owns only the v1.1 product responsibilities.

## 3. Architecture boundaries

### 3.1 Shared functional core

`src/core` remains environment-independent.

v1.1 adds the pure reminder helper defined below; `src/core` must not import:

- Capacitor;
- browser APIs;
- Bun;
- SQLite drivers;
- Git libraries;
- filesystem/process APIs.

A representative pure contract is:

~~~ts
export function isReminderDue(
  task: Task,
  now: Date,
): boolean;
~~~

This is not persisted state. It is a pure projection of the canonical Task and current local time.

`isReminderDue()` is the one reminder-due semantic owner. Callers pass the current local `Date`; the function derives today's civil date/local time using the existing date primitives. Do not create a general clock/service abstraction or another reminder predicate.

### 3.2 Shared UI

The React UI continues to render Planner, History, Settings and Task workspace.

Platform differences are limited to capabilities that genuinely differ:

- repository bootstrap/acquisition;
- persistence transport;
- Git transport;
- secure credential storage;
- notification scheduling/delivery.

Do not fork Planner into separate desktop/mobile applications.

### 3.3 Platform shells

The target runtime composition is:

~~~text
                         shared TypeScript
        ┌───────────────────────────────────────────┐
        │ src/core — Task/planning/reminder rules   │
        │ ui/      — React/Astryx presentation      │
        │ portable record serialization/validation  │
        └───────────────────┬───────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              │                           │
       Linux imperative shell      Native Android shell
       Bun + loopback HTTP         Capacitor Android
       bun:sqlite                   native SQLite adapter
       system git                   Android Git adapter
       browser notification        OS local notification
       OS secure credential        Android Keystore
~~~

The platform shell boundary is an imperative-shell boundary, not a new domain layer.

## 4. Linux two-phase bootstrap

### JIG-110-SD-01 — runtime mode

The current `src/shell/main.ts` assumes a complete `JigConfig`, acquires the repository writer lease and opens SQLite before starting HTTP. That prevents in-app setup.

v1.1 changes startup into two explicit runtime modes:

~~~text
config present + valid
        ↓
configured runtime
        ↓
existing Planner HTTP application

config absent
        ↓
bootstrap runtime
        ↓
serve UI + bootstrap endpoints only
        ↓
repository setup succeeds
        ↓
write canonical config atomically
        ↓
transition/restart into configured runtime
~~~

Do not persist an invented "unconfigured repository" object. Absence of valid configuration is the bootstrap condition.

The bootstrap process must not open a planning database or start repository synchronization before repository setup succeeds.

### JIG-110-SD-02 — bootstrap API surface

The Linux bootstrap HTTP surface must be narrow and setup-specific.

It needs only enough authority to:

- report configured/unconfigured state;
- validate/adopt an existing local repository;
- start/complete the GitHub authorization flow;
- list/select GitHub repositories available to the authorized Jig integration;
- clone the selected GitHub repository into Jig-managed storage;
- initialize/adopt Jig data;
- atomically write final `JigConfig`.

It must not expose arbitrary filesystem browsing, arbitrary Git commands, remote editing or branch management.

Existing configured Task/state/command endpoints remain unavailable until setup is complete.

### JIG-110-SD-03 — upgrade compatibility

Installer upgrade logic must preserve an existing `~/.config/jig/config.json`.

A configured v1.0.x installation must continue through the configured startup path without any config migration solely because v1.1 supports bootstrap mode.

The Linux `JigConfig` remains version 1 with exactly `version`, `repository_path`, and `http_port`. Bootstrap mode is represented by absence of the config file; provider credentials and onboarding state are not added to `JigConfig`.
### JIG-110-SD-28 — onboarding inside the canonical application frame

The React application still has two top-level runtime modes, `bootstrap` and `configured`, but they do **not** own two different application shells. The root Astryx Theme/LayerProvider/AppShell and Jig brand/header geometry are mounted for both modes. Runtime mode selects the body composition and available product actions only.

Presentation must realize `../design/reference/jig-v1.1-mobile-ux-ui-governed-reference.html` and `../design/reference/jig-v1.1-desktop-onboarding-task-form-governed-reference.html` through public Astryx primitives. Those references own the onboarding information hierarchy/responsive composition; they do not authorize a parallel setup shell, private Astryx styling, or persisted onboarding-progress state.

Desktop onboarding reuses the AppShell's existing content-scroll owner. The onboarding body must size to the remaining viewport below the 44px application header and must not create a second `height: 100%` / `overflow: auto` surface that produces an idle vertical scrollbar when the governed two-region content fits. If a genuinely short viewport or taller setup state exceeds the available body height, that same content owner may scroll so all controls remain reachable. Do not solve this by globally hiding overflow or clipping setup content.

Bootstrap header rules:
- render the canonical theme-aware Jig wordmark/identity from the first frame;
- preserve the same application background, header boundary, responsive geometry and Android safe-area ownership as configured Jig;
- do not render Planner temporal controls, Add task, Planner/History/Settings navigation or synchronization status before repository configuration exists;
- do not render a stepper, setup progress navigation or technical phase labels in the header.

Bootstrap body has one presentation owner with four user-level states:
1. **initial** — value/context orientation plus available genuine choices;
2. **connecting** — one automatic connection state whose rendered content may be GitHub device-code authorization, GitHub-owned repository-access handoff, or passive finishing progress;
3. **repository-selection** — only when more than one eligible repository requires an actual user choice;
4. **attention** — one bounded explanation/action when Jig cannot continue without user involvement.

The presentation owner has one semantic state model but two governed responsive compositions:

- **Linux/Desktop:** render the governed two-region composition. The left value/context region remains stable while the bounded right setup pane owns initial choices, GitHub authorization/access, repository selection, local-path entry and attention/recovery. Initial choices are primary **Connect GitHub repository** and secondary **Use an existing local repository**.
- **Android/narrow:** render the governed bounded single-column composition. Initial onboarding exposes only primary **Connect GitHub repository**; arbitrary device-local worktree selection is not rendered.

The local-repository choice replaces/expands only the desktop setup pane with the absolute repository-path field, validation feedback, **Use this repository** and Back/Cancel. The browser UI must not rely on the browser File System Access API to obtain a server-side POSIX path; expert CLI `--repo` remains available.

The value/context region and reassurance iconography are presentation only. They derive no new persisted state and introduce no new icon package; production glyphs remain within the Astryx/Jig icon registry.

`Connect GitHub repository` submits one intent to JIG-110-SD-29. React does not manually drive Device Flow polling, access refresh, clone, validation, adoption or initialization. While those operations run, the body remains in the single connecting semantic state unless repository selection or a genuine user-action-required condition is reached. Within that state, presentation may switch among the governed **Authorize Jig on GitHub**, repository-access handoff and passive **Getting your plan ready…** variants without persisting a step number or exposing protocol phase state to the user.

Bootstrap errors preserve any meaningful user choice, but raw Git/GitHub/SQLite/filesystem implementation details are translated to an actionable product-level message; exact diagnostics remain available to engineering logs/diagnostic surfaces.

After canonical setup succeeds, Linux writes the final `JigConfig` as today and Android completes its app-private setup. The runtime transitions directly to configured Planner without a completion screen or extra Continue action. No onboarding state is persisted in Task or portable data.

The governed first-empty-Planner activation is derived only from configured Planner state. When the displayed week is empty immediately after setup, Planner renders the normal governed empty-week projection with the Add-task activation; no setup-complete route/component is introduced. The projection is not stored as onboarding completion/progress and introduces no new domain or persistence state.

## 5. Repository onboarding implementation

### JIG-110-SD-25 — existing local desktop repository adoption

The existing `validateSelectedRepository()` and `initializeRepositoryInstallation()` semantics remain the canonical adoption path.

In-app local selection calls that same shell authority rather than introducing a second setup implementation.

Rules retained:

- absolute worktree root;
- readable/writable;
- public `pontivus-com/jig` source checkout rejected as planning data;
- existing valid portable snapshot adopted;
- SQLite/data identity consistency enforced;
- unrelated content untouched.

A repository with no remote is accepted and results in healthy `local-only`.

After canonical setup, determine synchronization mode through the existing `repositorySynchronizationMode()` / `discoverSynchronizationRemote()` authority. No-remote discovery must not fail setup, create a remote or prompt for GitHub.

A repository with an existing synchronization remote uses the current system-Git adapter and the repository's normal Git authentication. Authentication/fetch/push failure after local setup changes only the coarse repository outcome (`pending/retrying/sync-issue`); it does not roll back the locally valid Jig installation or corrupt Task data.

Jig never rewrites existing remotes, branches, upstreams, credential helpers, signing configuration or unrelated repository content during adoption.

### JIG-110-SD-26 — managed desktop GitHub checkout

The GitHub-acquisition path uses one deterministic Jig-owned checkout root that is separate from the atomically replaced application runtime:

~~~text
~/.local/share/jig-data/
  repositories/
    github/
      <owner>/
        <repository>/
          .git/
          .jig/
          ...
~~~

The canonical Linux managed checkout for GitHub repository `owner/repository` is therefore:

`~/.local/share/jig-data/repositories/github/<owner>/<repository>`

The managed root is created user-owned with no broader permissions than required by the current user. The normal onboarding UI does not ask for an alternate path. Existing expert/noninteractive `--repo` remains the path override mechanism rather than adding a second managed-checkout preference.

If the final managed path does not exist, acquisition clones to a newly-created temporary sibling under the same `<owner>` directory and moves it to the final path only after clone/remote verification succeeds. A failed clone removes only that newly-created temporary directory. It never deletes or overwrites an existing final path.

If the final path already exists, Jig does not overwrite it. It may reuse it only after `validateSelectedRepository()` succeeds and the existing GitHub remote URL normalizes to the selected `owner/repository`; otherwise setup stops with a non-destructive error.

After acquisition/reuse, the exact same `initializeRepositoryInstallation()` authority used for an existing local repository performs Jig adoption/initialization. No GitHub-specific Task, SQLite or portable-data initialization path is permitted.

### JIG-110-SD-27 — credentialed Linux clone delegation

On Linux, repository acquisition remains delegated to the system `git` executable.

For a Jig-authorized GitHub clone, construct the clone URL without credentials:

`https://github.com/<owner>/<repository>.git`

Invoke system Git with an ephemeral askpass helper/environment owned by the clone operation. The helper obtains the current GitHub access token from the device credential adapter and returns it only to Git's credential prompt. The token must not appear in the clone URL, process arguments, Git configuration, shell history, logs or portable data.

The helper/environment exists only for the Git subprocess lifetime. Normal repository remotes therefore persist the credential-free HTTPS URL.

Jig must not modify global or repository Git credential configuration. Existing local repositories continue to use their existing Git credential/topology configuration.

Clone success is not repository setup success: only after Git exits successfully, the worktree root validates, and the selected GitHub remote matches the requested repository may the temporary checkout move to its final managed path and proceed to canonical Jig adoption.

## 6. GitHub App authentication

### JIG-110-SD-04 — provider model

v1.1 optimizes only GitHub remote acquisition.

Existing local repositories remain provider-neutral and continue through system Git.

No GitLab/Bitbucket account-login integrations are required for v1.1.

### JIG-110-SD-05 — GitHub App permissions

Register one public GitHub App—**Jig Desktop & Mobile**—shared by Linux/Desktop and Android. Its repository permission set is limited to the minimum proven set needed for the selected flow.

Required baseline:

- **Contents: read & write** for HTTP Git clone/fetch/push.
- **Metadata: read-only** as GitHub's required/implicit repository metadata baseline used by repository enumeration.

All other repository permissions are **No access**, including **GitHub App installation repository access**. Do not request Issues, Pull requests, Administration, Actions/Workflows, organization, account or enterprise permissions unless an implementation proof demonstrates that a specific onboarding API requires one. Repository selection remains user-owned through GitHub's installation surface; Jig does not programmatically alter an installation's repository grant.

The onboarding flow instructs the user to install the GitHub App on only the repository/repositories they choose; Jig does not request all-repository access as its default path.

### JIG-110-SD-06 — direct GitHub Device Flow authorization

Jig v1.1 has **no Pontivus authorization server, broker, hosted redirect, token exchange service or other middle tier**. Linux and Android authorize directly against GitHub and keep resulting user credentials only on the device.

The canonical authorization mechanism for both runtimes is GitHub App **Device Flow** (OAuth 2.0 Device Authorization Grant). This is selected because it is the only GitHub-supported GitHub App user-authorization flow that simultaneously satisfies the v1.1 boundary that:

- the native client talks directly to GitHub;
- no Pontivus service participates in authentication;
- no GitHub App `client_secret` is shipped, stored or required by Jig;
- no `redirect_uri` / callback endpoint is required;
- no GitHub App private key or installation access token exists in Jig.

GitHub documents that Device Flow starts with `client_id` only, polls with `client_id` + `device_code` + the Device Flow `grant_type`, and does not require `client_secret`. GitHub also documents that refresh of a user access token originally generated through Device Flow does not require `client_secret`.

v1.1 uses one governed GitHub App registration for both runtimes:

**Jig Desktop & Mobile**
- owner: `pontivus-com`;
- App ID: `5812963` (external registration reference only; Jig runtime does not use it);
- public `app_slug`: `jig-desktop-mobile`;
- public `client_id`: `Iv23liyCoLFStLGRXgUk`;
- Expire user authorization tokens: checked;
- Request user authorization (OAuth) during installation: unchecked;
- Enable Device Flow: checked;
- Redirect URI: remove all entries;
- Setup URL: blank;
- Redirect on update: unchecked;
- Webhook → Active: unchecked;
- Where can this GitHub App be installed?: Any account.

The shared App retains the least-privilege repository permissions from JIG-110-SD-05. The user chooses repository access once through this App's GitHub installation surface; Linux/Desktop and Android then authorize independently as users/devices against the same App installation boundary.

The public registration source contains exactly one `GitHubAppRegistration` with `app_slug` and `client_id`. It must not contain `client_secret`, `redirect_uri`, GitHub App private keys, installation tokens or user tokens. Platform-specific GitHub App registrations are prohibited unless a future GitHub capability requires materially different App-level configuration.

The authorization data flow is fixed:

1. **Jig → GitHub:** `POST https://github.com/login/device/code` with the shared App's public `client_id` and `scope=offline_access`.
2. **GitHub → Jig:** `device_code`, 8-character `user_code`, fixed `verification_uri`, `expires_in` and minimum `interval`.
3. **Jig → user:** the onboarding/reconnect body remains one connecting state but must visibly present the GitHub-generated `user_code` with a compact **Copy code** affordance and automatically open `verification_uri` where the platform/browser permits. If automatic opening is blocked, the same state exposes one **Open GitHub** action. This code presentation is not technical leakage: GitHub explicitly requires the user to enter it at the provider-owned verification page.
4. **User ↔ GitHub:** the user signs in if required, enters/pastes the `user_code`, and accepts or denies the GitHub-owned authorization. Jig never receives GitHub credentials/passwords.
5. **Jig → GitHub:** while the connecting state is active, the Device Flow session polls `POST https://github.com/login/oauth/access_token` automatically, never faster than GitHub's returned `interval`. `authorization_pending` continues polling; `slow_down` increases the interval exactly as GitHub returns/requires; `access_denied` and expiry become terminal/actionable outcomes.
6. **GitHub → Jig:** on success GitHub returns the user `access_token` and, because Jig requests `offline_access`, refresh-token/expiry material. Jig validates user identity and persists only the device-local credential through JIG-110-SD-07.
7. **Normal renewal:** before a GitHub network operation, a near-expiry access token is refreshed directly through `POST https://github.com/login/oauth/access_token` using `client_id`, `grant_type=refresh_token` and the current refresh token; Device-Flow-generated credentials do not require `client_secret`. A successful refresh rotates the credential pair, so persistence must replace the old access/refresh tokens atomically.
8. **Reconnect:** if the refresh token is absent/expired/revoked or GitHub rejects the user credential, the user is asked for one product-level **Reconnect GitHub** intent and the same Device Flow starts again. Repository selection/acquisition is not repeated.

**Why v1.1 does not switch to the web authorization flow:** GitHub's web flow now supports PKCE, but the code-for-token exchange still requires the GitHub App `client_secret`. A desktop/Android public client cannot keep that secret, and Jig v1.1 deliberately has no Pontivus token-exchange backend. Device Flow is therefore the minimum direct-to-GitHub mechanism that satisfies the current architecture. Its mandatory user-code entry is accepted as a GitHub-owned authorization constraint and is designed as one bounded interruption inside the otherwise automatic Jig connection flow.

Device Flow does not prove that an arbitrary caller using the public `client_id` is an untampered Jig binary. GitHub warns that Device Flow can be abused for remote impersonation/phishing because there is no redirect binding. That is an acknowledged residual property of the serverless/no-secret architecture, not something Jig hides with another subsystem. Mitigation is limited to truthful UX: Jig directs the user only to GitHub's fixed `https://github.com/login/device` verification surface, visibly presents the provider-issued one-time `user_code`, never accepts credentials itself, and never describes Device Flow authorization as binary attestation. Polling/timing/error progression remains internal; code entry and GitHub consent are the only authorization interactions visible because GitHub requires them.

A GitHub App private key is never generated, downloaded or distributed as part of Jig runtime/release artifacts.

### JIG-110-SD-07 — platform credential storage

Provider access/refresh tokens are device-local operational secrets and have one platform adapter per runtime.

**Linux:** use the system `secret-tool` client for the freedesktop Secret Service. At Connect GitHub time, require `secret-tool` to be discoverable on `PATH` and an unlocked Secret Service collection to be available. Store one current validated JSON credential payload under label `Jig GitHub` with the stable Secret Service attributes `application=jig` and `provider=github`. The GitHub numeric user id remains inside the validated payload rather than the lookup key, so refresh/reconnect replaces the same logical item instead of deleting the previous credential before the replacement is stored. The secret JSON is supplied to `secret-tool store` through stdin and retrieved through `secret-tool lookup`; it must never appear in process arguments or logs. A Jig-managed GitHub checkout at `~/.local/share/jig-data/repositories/github/<owner>/<repository>` loads that current credential at Git-operation time. If the access token is within five minutes of its recorded expiry, Jig refreshes it directly with GitHub through the shared Device Flow registration and replaces the Secret Service payload before Git transport. Before obtaining the credential for a network Git operation, Jig re-resolves Git's canonical synchronization remote and requires every push URL for that remote to be HTTPS `github.com` and to normalize to the same `<owner>/<repository>` encoded by the managed checkout path. A changed, ambiguous or non-GitHub remote is a synchronization issue and receives no Jig credential. The resulting access token is supplied to system Git only through a short-lived `GIT_ASKPASS` helper plus process environment; the helper itself refuses username/password prompts that are not for HTTPS `github.com`. The token is never written to the remote URL, Git config or command arguments. Provider-neutral/local repositories never receive Jig's GitHub credential and continue to use their existing system Git authentication. If `secret-tool`/Secret Service is unavailable, Connect GitHub is unavailable and managed GitHub synchronization reports an operational issue; local-repository setup remains available. The installer does not install or reconfigure the user's Secret Service.

**Android:** implement one narrow Capacitor plugin, `JigSecureCredentials`, backed by Android Keystore. Generate a non-exportable 256-bit AES key with alias `com.pontivus.jig.github.credentials.v1` using `AES/GCM/NoPadding`. Store only AES-GCM ciphertext, IV and token metadata in an app-private **no-backup** SharedPreferences file. Plain access/refresh tokens exist only in process memory while being used.

The stored provider credential payload contains only the fields needed to renew/use GitHub authorization: GitHub numeric user id, access token, optional refresh token, access-token expiry and refresh-token expiry. The shared App `client_id` and `app_slug` are public registration metadata and are not part of this credential payload; `client_secret` is not used by the governed Device Flow.

Credential lookup, refresh, replacement and deletion are imperative-shell operations. A missing, malformed or GitHub-rejected managed-checkout credential becomes a synchronization issue immediately rather than consuming generic transport retry backoff. **Reconnect GitHub** reuses the same direct Device Flow state machine, replaces only the device-local credential, does not reselect/reconfigure the repository, and then retries synchronization. Revocation/expiry must never corrupt or roll back local Task data.

Provider user tokens must never be written to `JigConfig`, SQLite Task rows, portable records, repository files, Git remote URLs, logs, crash reports or process arguments.

### JIG-110-SD-29 — automatic GitHub acquisition orchestration

The GitHub onboarding state machine remains transient shell state, not persisted Jig domain state. Its internal phases may remain detailed enough for correctness:

~~~text
idle
  → authorizing
  → repository-access
  → repository-selection
  → acquiring
  → adopting
  → configured
~~~


#### Authoritative GitHub access/discovery data flow

After Device Flow produces a valid user access token, onboarding must use GitHub's authoritative user-to-App intersection rather than the user's general repository list:

~~~text
user access token
  ↓
GET /user/installations  ── all pages
  ↓
for each accessible installation
  ↓
GET /user/installations/{installation_id}/repositories  ── all pages
  ↓
eligible owner/repository choices
~~~

Rules:

1. Both list endpoints are paginated. Request up to 100 per page and follow pagination until every page has been consumed. The controller must not infer "no installation", "no repository" or "only one repository" from the first page.
2. The repository chooser is built only from this fully enumerated intersection. A repository the user can normally see on GitHub is not eligible unless the Jig App installation also grants it; conversely App installation access does not grant a user rights they do not already have.
3. If zero accessible installations exist, route the user to `https://github.com/apps/<app_slug>/installations/new`. That GitHub-owned surface chooses personal/organization account, repository access and permissions.
4. If an installation exists but the desired repository is not in the authoritative repository list, route to that installation's GitHub-owned access-management surface. Jig does not call GitHub's repository-add/remove installation APIs even when the token/user could do so; changing App grants is a GitHub/user/organization decision.
5. The installation surface may complete immediately or submit a request requiring organization-owner approval. Returning from the provider surface is therefore **not** proof of access. Jig re-runs the authoritative installation/repository queries on app/browser activation and with bounded backoff while the connecting state remains active. No manual **Refresh access** action is required.
6. If access remains absent, the UI stays in the connecting/attention presentation and says only that GitHub has not yet made the repository available. It must not falsely claim "approval pending" unless GitHub exposes evidence for that exact state.
7. Organization SSO/policy can also prevent expected resources from appearing. Jig treats the GitHub API result as authority and routes the user back to GitHub's provider-owned access surface rather than inventing local repository-access state.

#### Acquisition/adoption data flow

Once an eligible repository has been selected (or exactly one unambiguous eligible repository is available):

~~~text
owner/repository + credential-free clone_url
  ↓
managed HTTPS Git clone/fetch using device-held user access token
  ↓
worktree / app-private repository
  ↓
canonical repository validation
  ↓
portable snapshot validate/adopt OR initialize new dataset
  ↓
SQLite initialize/adopt
  ↓
configured Planner
~~~

- HTTP Git requires the App's `Contents` permission and the user's own effective access. The access token is supplied as the Git HTTP password through the platform adapter only; it must never be persisted in the clone URL/remote/config/logs.
- Linux uses the ephemeral askpass/environment boundary from SD-27. Android uses the selected native/isomorphic-git authentication callback and app-private filesystem. These are different transport adapters around the same acquisition semantics, not different onboarding workflows.
- Clone success alone does not change the application to configured state. Validation/adoption/SQLite initialization must all succeed first.
- A failure before canonical adoption leaves the application in onboarding and removes only artifacts Jig created for that failed attempt; an existing valid checkout is never deleted as recovery.

#### GitHub response classification that affects UX

The integration boundary must classify provider results before they reach presentation:

- Device Flow `authorization_pending` / `slow_down`: internal continuation only.
- Device Flow denial/expiry: one actionable authorization failure; retry restarts Device Flow with a new code.
- REST/Git `401` or an invalid/expired credential: attempt governed refresh when possible; otherwise expose **Reconnect GitHub**.
- REST `403`: permission/policy/access problem; do not retry indefinitely as transport noise. Preserve local data and route to provider access/attention when user action can help.
- repository/install listing `404` or disappearance of a previously selected repository: treat the provider resource as no longer accessible; never manufacture a local grant.
- transient network/5xx failures: remain retryable operational failures with bounded retry/backoff.

The UI receives only the user-level consequence plus optional diagnostics. It must not branch directly on raw GitHub error strings/status codes.

Those phases are **not** the presentation contract. The onboarding controller is an imperative-shell orchestration owner that advances every non-user-decision transition itself.

Its user-level inputs are deliberately small:
- **connect**;
- **select repository** when selection is genuinely required;
- **retry** after a terminal/actionable failure;
- optional cancel/back before canonical setup commits.

After **connect**, the controller starts Device Flow, opens the provider verification surface, polls at GitHub's governed cadence, persists the credential on success, queries the shared **Jig Desktop & Mobile** App installations/repositories, and continues without React issuing refresh commands.

If GitHub installation/repository access is absent, the controller routes the user to GitHub's provider-owned installation/manage-access surface as required. When the browser/app regains focus/activation, or the provider authorization result becomes available, the controller automatically re-evaluates access. There is no normal-flow Jig **Refresh access**, **Grant repository access** or **Manage GitHub access** action.

Repository selection is populated only from repositories available through the user's authorized Jig GitHub App installations. If exactly one eligible repository is available and no ambiguity exists, the controller may continue automatically. If multiple eligible repositories require a user choice, the user-level presentation becomes repository-selection and exposes only human-readable owner/repository choices. Selecting one supplies its canonical provider repository id, owner, name and credential-free HTTPS clone URL to the acquisition adapter; these remain operational inputs, not Task fields or portable records.

After selection, the controller automatically acquires the repository, delegates canonical validation/adoption/initialization and transitions directly to configured runtime. Linux acquisition delegates to JIG-110-SD-26/27. Android acquisition delegates to JIG-110-SD-12/13/14.

Failure semantics remain non-destructive:
- authorization denial/expiry produces an actionable attention state and allows retry from the one Connect intent;
- access/listing failure retains any valid credential when safe and reports only the user action actually required;
- repository-selection failure retains authorization/access state;
- clone/adoption failure leaves Jig unconfigured and removes only a temporary checkout created by that failed acquisition;
- a previously existing checkout is never deleted as recovery.

The presentation projection is intentionally coarser than the internal state machine: `initial | connecting | repository-selection | attention`, plus the minimum repository choices/error/action needed by that state. Do not surface internal phase names, installation IDs, refresh cadence, clone paths or protocol response fields through the normal UI contract.

Repository user tokens are retrieved from the platform credential adapter at Git-operation time. For Jig-managed GitHub checkouts the credential is injected only into network Git commands through the platform's ephemeral authentication mechanism; it is not applied to provider-neutral repositories and is never copied into `JigConfig` or persisted Git remote URLs.

Configured-mode **Reconnect GitHub** is the same interaction principle with a narrower orchestration: one reconnect intent starts authorization, automatic polling replaces the device-local credential, synchronization retry happens automatically, and repository installation/selection/acquisition/adoption are never repeated.

### JIG-110-SD-41 — minimal cross-installation synchronization correction

**Functional owners:** JIG-110-FR-24 and JIG-110-FR-31.

#### Root cause

The observed defect is one implementation asymmetry, not a missing synchronization product:

- Android already observes the remote `jig-data` head and distinguishes remote-ahead/local-ahead/divergence.
- Desktop/Linux currently exports from its local state and then attempts a push without first observing/adopting a valid remote advance.
- After Android advances the shared repository, Desktop can therefore remain on the older head and repeatedly receive a non-fast-forward push failure. If Desktop exports a new snapshot before observing that advance, it can unnecessarily turn a stale-client condition into real divergence.

The correction is to make the **decision order** common. It is not authority to create a broader Git state machine or planning-data reconciliation subsystem.

#### Architecture and ownership

The implementation must preserve the repository architecture rules:

1. **Functional core — one pure classifier.** A small pure function owns the synchronization decision from already-observed facts. It knows only whether a remote exists, whether local planning is unsynchronized, and the local/remote lineage/result. It has no filesystem, Git command, provider, credential, SQLite or UI dependency.
2. **Existing synchronization orchestrators — imperative sequencing only.** `src/shell/sync.ts` and the Android configured-runtime sync path obtain facts, call the same pure decision semantics, and sequence existing effects. They do not independently re-implement policy.
3. **Git adapters — mechanics only.** Desktop system Git and Android isomorphic-git expose only the narrow effects each runtime needs: observe/fetch the portable head, validate the presented portable snapshot, answer ancestry, fast-forward the private Jig head when permitted, and perform an ordinary non-forced push. The two adapters need not share an abstraction hierarchy because their imperative mechanisms are different.
4. **Persistence — existing authority only.** Reuse the existing canonical SQLite state plus `revision`, `last_exported_revision`, `last_exported_head`, `last_adopted_head` and `pending_sync`. Do not add a synchronization table, repository topology state or a second canonical model.
5. **No new layering.** No DTO/mapping hierarchy, Repository/Service/Manager classes, workflow framework, Task-level merge engine, Git merge/rebase/conflict workflow, force-push path or provider-specific synchronization domain is authorized.

Strict typing remains mandatory. The pure decision is represented as a closed discriminated result/enum-like union; no `any`, unchecked assertions, double casts or platform-shaped payload mapping are permitted.

#### Normal synchronization decision

The shared classifier has only four normal outcomes:

| Observed facts | Decision |
|---|---|
| No synchronization remote | **Local only** |
| Local head = remote head | **Synchronized** unless a newer SQLite revision still needs local export/push |
| Remote is a descendant of local, and there is no unsynchronized local SQLite change | **Adopt remote** |
| Local is a descendant of remote and represents local work that has not reached the remote | **Push local** |

Anything that is not safely one of those cases is **Attention** rather than an invitation to add reconciliation logic.

#### SYNC-E1 — both sides changed

**Functional outcome:** preserve local SQLite and remote portable state; Needs attention.

**Solution:** remote observation happens **before** creating another remote-backed local snapshot. If the remote advanced while SQLite also contains an unsynchronized local revision, stop before committing that SQLite state onto the stale local `jig-data` head. If Git heads are already divergent, the same Attention result applies. No merge/rebase/force or semantic Task merge is attempted.

#### SYNC-E2 — remote changes during push

**Functional outcome:** no stale-push loop.

**Solution:** a non-fast-forward/rejected push never causes the same push to be repeated immediately. The next operation is remote observation/classification. If the new state is equal/local-ahead/remote-ahead under the normal rules, continue from that rule; otherwise enter Attention. Repeated contention falls back to the existing retry/backoff schedule rather than adding a new retry subsystem.

#### SYNC-E3 — ambiguous push acknowledgement

**Functional outcome:** do not duplicate history because acknowledgement was lost.

**Solution:** after a push transport failure for which server acceptance is unknown, observe the remote before another push. If the remote head is the exact local exported head, synchronization succeeded. Otherwise classify the newly observed state normally.

#### SYNC-E4 — temporary authentication/transport failure

**Functional outcome:** local planning remains usable; synchronization retries/reconnects.

**Solution:** keep the existing local-first save and existing bounded retry/backoff/status model. Credentials remain provider-owned and outside the generic classifier. Network/provider failure does not mutate canonical planning or Git history in order to “repair” connectivity. Remote operations must have a bounded shell/transport timeout so a hung provider/credential operation cannot occupy the one sync cycle indefinitely; do not introduce a second timeout/retry framework.

#### SYNC-E5 — restart/crash between durable boundaries

**Functional outcome:** no accepted Task loss, stale overwrite or duplicate semantic snapshot.

**Solution:** use the existing durable facts and make remote adoption revision-checked:

1. observe and validate the remote snapshot without mutating SQLite;
2. capture the current SQLite revision;
3. apply the adopted canonical snapshot in one SQLite transaction that requires that exact revision and records `last_adopted_head`; if the revision changed, abort adoption and re-observe;
4. align the private Jig Git head to the already validated remote head;
5. mark only the exact SQLite revision actually represented by that Git head as exported.

The persistence operation must reuse the existing metadata columns; it may refine the existing snapshot-adoption function but must not create new persistence concepts.

Recovery uses the same existing evidence:
- if a local snapshot commit exists but export metadata lagged, compare the concrete snapshot to SQLite and repair metadata rather than creating another commit;
- if SQLite records an adopted remote head but the private Jig head was not yet aligned, a later cycle may finish that alignment only when the validated remote head and canonical SQLite snapshot still agree;
- a newer SQLite revision always remains pending and must never be marked exported merely because an older revision reached Git.

No network operation is performed inside a SQLite transaction.

#### SYNC-E6 — remote state is not safely consumable

**Functional outcome:** preserve both boundaries and report Needs attention.

**Solution:** the Git adapter returns Attention when a single synchronization target cannot be determined, ancestry is unknown/not fast-forward compatible, a previously synchronized remote history is deleted/rewritten, or the presented portable snapshot/dataset fails validation. The orchestrator performs no force, reset-to-remote, automatic branch recreation, dataset replacement, merge or rebase. General Git repair remains outside Jig.

A remote with no `jig-data` branch on first ordinary publication is not SYNC-E6: Jig may perform its existing ordinary non-forced first push. If another writer wins that race, the resulting rejection is handled by SYNC-E2 and then the observed state is classified normally. v1.1 does not add special cross-dataset bootstrap reconciliation.

#### Liveness and status

- one in-flight synchronization cycle per installation; triggers coalesce;
- local Task mutations remain SQLite-first and never wait for network completion;
- no SQLite transaction/application lock is held across Git/network I/O or retry delay;
- use the existing retry/backoff and healthy-poll ownership; do not add another scheduler;
- structural Attention states do not repeat write operations while the same facts remain present; later read/normal synchronization opportunities may resume automatically if the repository returns to a normal fast-forward-compatible state;
- **Saved locally** means SQLite durability;
- **Up to date** is valid only after the configured remote is observed to contain the exact current exported Jig head.

#### Verification

Repository-capable verification is limited to the governed behavior above:

- Desktop → Android → Desktop and Android → Desktop → Android ordinary alternating round trips;
- SYNC-E1 safe stop before stale-base local commit;
- SYNC-E2 push rejection followed by re-observation, not blind push retry;
- SYNC-E3 ambiguous-success re-observation;
- SYNC-E4 bounded transport/auth retry with local planning unaffected;
- SYNC-E5 revision-race and restart/bookkeeping recovery;
- SYNC-E6 ambiguous/invalid/divergent remote state is non-destructive;
- unrelated repository content and Git configuration remain untouched;
- architecture tests enforce one pure classifier, no platform policy duplication, strict typing, FC/IS direction, and absence of merge/rebase/force/DTO/service-framework additions.

Physical Android confirmation remains an acceptance gate under J110-IMP-15; it is not a reason to leave repository-capable implementation or tests incomplete.

### JIG-110-SD-39 — bounded recurring Task series and exact occurrence materialization

**Functional owner:** JIG-110-FR-29. The canonical cross-version recurrence model is defined in `technical-solution.md` §4.2.1; this section makes that design binding for v1.1 across Linux and Android.

Recurrence has one functional-core owner. It defines:

- `Weekday = MON..SUN`;
- `RecurrencePattern = weekly(interval_weeks, weekdays) | monthly(day_of_month)`;
- one finite `RecurrenceSeries` with UUID, effective/start date, required inclusive end date, pattern and timestamps;
- one pure date enumerator/reconciler used by both runtimes.

No platform shell, UI component, reminder adapter or persistence driver may independently calculate recurrence dates.

Every recurrence is finite. Weekly intervals are positive whole numbers with at least one selected weekday. The Monday-based week containing the effective/start date is week zero; active weeks recur every `interval_weeks`. Monthly recurrence uses an exact day `1..31`; months without that day are skipped rather than clamped.

v1.1 deliberately uses **eager bounded materialization**. When Repeat is enabled or changed, the canonical persistence transaction materializes/reconciles the complete occurrence set through the required end date. There is no virtual Task projection, lazy recurrence daemon, mobile-only generator or device-local recurrence schedule.

Canonical Task gains exactly two nullable fields:

~~~text
recurrence_series_id: UUID | null
recurrence_occurrence_date: YYYY-MM-DD | null
~~~

They are null together or non-null together. `recurrence_occurrence_date` is the immutable recurrence slot. `scheduled_date` remains the user's live planning date and may change through rollover or explicit movement without changing the recurrence slot/cadence.

Occurrence semantics:

- the Task on which Repeat is enabled is the seed and remains an ordinary Task;
- each later slot is a distinct ordinary Task with its own UUID, order, completion and reminder lifecycle;
- all occurrences carry the same `recurrence_series_id` link and therefore expose one shared `RecurrenceSeries` configuration from any occurrence; pattern/end-date values are not duplicated into Task rows;
- generated Tasks copy title/priority/context/reference/note/reminder time from the seed/invoking occurrence at creation time only; after materialization those ordinary Task fields are independent per occurrence and never bulk-propagate to existing siblings;
- v1.1 has exactly two **user write scopes**: **occurrence scope** for ordinary Task content/lifecycle and **series scope** for recurrence configuration/membership teardown; automatic rollover supersession is canonical maintenance, not another user scope or Task status; no "all occurrences", "this and following Task details" or template-propagation scope exists;
- ordinary edit/move/complete/reopen/delete stays occurrence-only and cannot mutate the shared series;
- a Repeat change is a series-membership reconciliation anchored at the invoking occurrence's immutable `recurrence_occurrence_date`: preserve the invoking/earlier/completed Tasks, keep later outstanding Tasks whose immutable slots remain selected without altering their Task fields, remove only later outstanding slots no longer selected, create only newly introduced later slots by snapshotting the invoking occurrence once, and update the shared series `effective_from`/pattern/end date atomically;
- **Stop repeating / Remove recurrence** from any occurrence keeps that invoking Task, clears its recurrence link so it becomes one-off, preserves completed History and removes **every other outstanding occurrence linked to the series** in one transaction, including rolled/overdue siblings; this avoids forcing individual deletion of generated cards;
- individual Delete this Task remains occurrence-only and leaves the recurrence series/sibling occurrences intact;
- daily rollover changes no recurrence slot or series rule. Before ordinary rollover, the shared planning core applies the non-accumulation exception: for each series, preserve the latest outstanding occurrence whose immutable slot is due on/before today; supersede any other outstanding sibling that is actually overdue; preserve future-scheduled siblings, including explicit future reschedules; then roll the surviving overdue occurrence to today. Superseded occurrences are deleted from the current Task set without synthesizing completion.

Persistence/versioning is one cross-platform migration:

- SQLite schema **v3** adds `recurrence_series`, `task.recurrence_series_id` and `task.recurrence_occurrence_date`; v2→v3 leaves all existing Tasks non-recurring;
- portable format **v2** adds nullable Task recurrence fields plus `recurrences/<series-id>.json` records;
- portable v1 remains accepted upgrade input and is interpreted as no recurrence; the next export emits v2;
- v2 import validates every Task recurrence reference, series UUID/date/pattern, finite end date and uniqueness of `(recurrence_series_id, recurrence_occurrence_date)` before adoption.

The command surface remains canonical and function-shaped, but the user-facing one-Save form requires one atomic command transaction rather than two sequential saves.

`create` continues to carry an optional recurrence spec for atomic seed+series creation.

For an existing Task, extend the existing `edit` command with an optional top-level recurrence change:

~~~ts
{
  type: "edit";
  task_id: string;
  changes: TaskEditChanges;                 // occurrence-local fields only
  recurrence?: RecurrenceSpec | null;       // omitted=unchanged; null=stop
}
~~~

This does **not** merge occurrence and series semantics. In one SQLite transaction the persistence owner:
1. applies `changes` to the invoking occurrence;
2. when `recurrence` is present, runs the one existing recurrence reconciler against that updated invoking Task;
3. persists the resulting Task + series set;
4. increments the durable revision once.

If recurrence reconciliation fails, the occurrence edit rolls back too. Newly introduced slots therefore copy the invoking occurrence's just-saved values exactly once, while retained siblings remain content-immutable.

Migrate every caller/test and remove `set_recurrence` from the public `TaskCommand` union; do not keep two public commands for the same existing-Task recurrence mutation. The pure recurrence reconciler remains one semantic owner.

When changing a rule from an existing occurrence, the invoking immutable slot remains the series `effective_from` anchor; preserved earlier/completed occurrences remain linked historical/exception members and are not rewritten. `CanonicalState` continues to carry `recurrences` beside `tasks` without a presentation DTO. One successful form Save produces one revision and one canonical refetch.

Reminder integration requires no second recurrence reminder model. Every materialized Task owns its copied `reminder_time`; browser/Android reminder owners continue to schedule/evaluate that occurrence exactly as today. Android local-notification reconciliation therefore sees future recurring Tasks through the same outstanding-Task scan.

UI: Repeat is part of the **same TaskEditor form** for create and existing Task states, ordered directly after Date and before Reminder. It is not a sibling `RecurrenceEditor` rendered after the Task form.

The complete presentation remains **Title → Date → Repeat → Reminder → Priority → Context → Reference → Notes** in one Drawer/BottomSheet draft. The governed v1.1 references are binding for this form composition: Repeat detail controls are progressive disclosure inside that same scrollable form, and the remaining fields stay present below them. The mobile form follows SD-22's governed >=48px interaction/scroll/action-area contract, wraps weekday controls rather than introducing a second compact/mobile recurrence composition, and preserves access to the remainder of the form under IME resize.

The initial field is one `Does not repeat | Weekly | Monthly` choice. `Does not repeat` renders no recurrence-detail controls. Weekly reveals interval + touch-sized weekday choices + required end date. Monthly reveals day-of-month + required end date. Existing series resolve their shared configuration through `recurrence_series_id`.

There is one primary Task Save. The Task draft owns the pending recurrence selection/spec alongside ordinary field draft state; Save constructs the one create/edit command above. There is no **Enable repeat**, **Save repeat** or separate second-save button. Existing Stop repeating is represented by choosing **Does not repeat** plus concise impact copy before Save.

The workspace still exposes no content-propagation scope selector: ordinary Task fields are occurrence-local; Repeat fields are series-level; the command/persistence transaction simply makes the user operation atomic. Delete this Task remains occurrence-only. The Task card keeps one compact accessible repeat summary.

Required certification:

- weekly one-day, multi-day, all-seven and every-four-weeks date sets;
- month/year boundaries plus monthly day 28/29/30/31 skip behavior;
- inclusive end-date termination and no unbounded rule;
- one occurrence complete/reopen/move/delete does not alter sibling occurrences;
- rollover preserves recurrence slot/cadence **and prevents stale recurring-card accumulation**: one/multiple missed periods select the latest due outstanding survivor, remove older overdue siblings, preserve completed History and preserve explicitly future-rescheduled/future-slot occurrences;
- repeated reminder time is copied and independently due/scheduled per occurrence;
- every occurrence resolves the same shared series configuration; Repeat edits reconcile centrally without per-card configuration drift;
- changing Repeat from any occurrence uses that occurrence's immutable slot as the reconciliation/effective anchor, preserves invoking/earlier/completed Tasks, preserves retained later sibling IDs/content, removes only excluded later outstanding slots and snapshots the invoking Task only into newly introduced slots;
- Stop repeating from any occurrence retains that Task as one-off, preserves completed history and removes all other outstanding series occurrences—including rolled/overdue siblings—in one transaction;
- individual Delete remains occurrence-only and does not stop recurrence;
- ordinary title/priority/context/reference/note/reminder edits never propagate to existing sibling occurrences; no bulk Task-content command/scope exists;
- SQLite v2→v3 migration, transaction rollback and restart;
- portable v1→v2 adoption/export and Linux↔Android v2 round trip.

- reminder present;

- reminder time is earlier than or equal to current local time.

No localStorage delivery key participates in this predicate.

### JIG-110-SD-18 — UI attention projection

Task-card presentation derives the reminder-due state from that pure owner.

Introduce one governed semantic alias for reminder attention, consumed across all themes.

The reminder indicator must combine correctly with:

- priority leading cue;
- selected surface;
- drag state;
- focus;
- today/date semantics.

No theme-specific branch or palette literal belongs in feature code.

### JIG-110-SD-19 — Linux/browser delivery

Replace the assumption that direct `new Notification(...)` is the only delivery mechanism.

For the browser UI:

- register a small Jig service worker;
- when the open application determines a reminder is newly due and permission is granted, request display through `ServiceWorkerRegistration.showNotification()`;
- retain bounded duplicate suppression for the same Task/date/time delivery attempt;
- constructor/service-worker failure must remain retryable and must not clear reminder-due attention.

The service worker is a delivery adapter only. It does not become the canonical scheduler, Task store or push subsystem.

v1.1 still does not claim remote push or guaranteed closed-browser desktop delivery.

### JIG-110-SD-20 — native Android delivery

Use **`@capacitor/local-notifications@8.3.1`** as the Android notification adapter.

On Android 13+, check/request notification permission before scheduling. For exact reminder times on Android versions that gate exact alarms, declare the required exact-alarm permission and use the plugin's exact-setting check. If exact alarms are unavailable/disabled, scheduling returns `scheduled-inexact` when the OS accepts an inexact schedule or `failed` when no schedule is accepted; Jig must not label either outcome as exact delivery.

When a future reminder-bearing Task is saved, schedule the OS local notification.

On edit/complete/delete/reschedule:
- cancel stale pending notification;
- schedule the replacement if still eligible.

On application startup/resume:
- reconcile pending OS notifications against canonical outstanding Tasks so side-effect drift cannot become permanent.

Do not persist notification-delivered state into canonical Task solely to drive the reminder-due card.

Android exact-notification policy must be handled honestly: if exact scheduling permission/settings are unavailable, the UI must not claim exact delivery. Successful exact scheduling returns `scheduled-exact`. If exact scheduling is unavailable but Android accepts an inexact schedule, the adapter returns `scheduled-inexact`; Settings exposes that exact timing is unavailable. If no schedule is accepted, it returns `failed`. The Task's in-app due state remains exact from canonical local time. Jig never reports either scheduling success as delivered/displayed.
### JIG-110-SD-31 — reminder corrective closure

The v1.0.6 browser monitor contains a concrete defect: `ui/src/reminder.tsx` records `sessionStartedAt` and skips every candidate where `dueAt < sessionStartedAt.current`. v1.1 removes that gate and removes the session-start timestamp entirely.

One pure `isReminderDue(task, now)` owner (JIG-110-SD-17) supplies both Task-card attention and delivery eligibility. On initial mount, Task change, the existing bounded timer, focus and visibility revalidation, an incomplete current-day Task whose reminder time is `<= now` is due regardless of when the current browser/app session started.

The delivery-suppression key remains device-local side-effect state keyed by Task id + scheduled date + reminder time. It suppresses duplicate notification delivery only; it must never suppress the card-level due state.

For Linux/browser catch-up, if a reminder is already due when Jig opens and no delivery-suppression key exists, Jig makes one delivery attempt when permission is granted. Permission denial, unsupported capability or delivery failure leaves the key absent so a later bounded check may retry.

For Android, native scheduling owns future delivery. Startup/resume reconciliation schedules only future reminders and cancels stale pending entries; an already-past reminder is represented immediately by the in-app due state rather than manufacturing a new past-time schedule.

Roll-forward preserves `reminder_time`; after rollover, the same pure predicate determines whether the now-current-date Task is already due.

No `notified_at`, `delivered_at`, acknowledgement flag or second Task status is added to canonical Task.

### JIG-110-SD-32 — notification delivery adapters and outcome semantics

`ui/src/browser-notifications.ts` becomes the browser permission/delivery adapter instead of exposing permission only. It owns:

- capability/permission inspection;
- permission request from the existing explicit Settings user gesture;
- service-worker registration/readiness;
- `showNotification()` delivery;
- a typed operational outcome such as `displayed | permission-required | denied | unsupported | failed`.

The browser ReminderMonitor marks its duplicate-suppression key only after the delivery adapter resolves `displayed`. A thrown/rejected service-worker notification remains `failed` and is retryable. Direct `new Notification(...)` is removed as the production delivery path.

The service worker is static application infrastructure only: no push subscription, remote scheduler, Task store or canonical reminder state is added.

Android uses the native local-notification adapter from JIG-110-SD-20. Its one scheduling result contract is `scheduled-exact | scheduled-inexact | permission-required | denied | failed`. UI wording must distinguish **scheduled** from **delivered/displayed**, must expose inexact scheduling honestly, and must never claim an OS notification was observed merely because scheduling succeeded.

Because the Android notification API requires platform notification identifiers, the native notification adapter keeps a device-local non-portable schedule registry in an app-private **no-backup SharedPreferences** file owned by that adapter. `task_id` is the unique semantic key, with the allocated platform notification id and reminder fingerprint (`scheduled_date|reminder_time`). The registry is not part of canonical SQLite, Task state or portable Git data and must be rebuilt/repaired by startup/resume reconciliation from outstanding Tasks plus the platform pending-notification list whenever it is missing or inconsistent.

Completion, delete, reminder removal/change and date change cancel the registered pending notification before/after the canonical Task transaction as an imperative side effect; failure to cancel is recorded diagnostically and corrected by next startup/resume reconciliation without rolling back the already-durable Task mutation.

### JIG-110-SD-36 — one UI reminder clock

A due predicate does not cause React to render by itself. The UI therefore has one presentation-clock owner in `ui/src/reminder.tsx`:

~~~ts
export function useReminderClock(): Date;
~~~

`App` calls this hook exactly once. It updates the current local `Date` on mount, every 30 seconds, on window focus, and when document visibility changes to visible. The returned `now` is passed to the Planner/Task-row presentation and to `ReminderMonitor`.

Task-card attention calls only `isReminderDue(task, now)`; no Task row creates its own timer. `ReminderMonitor` performs delivery attempts from the same `now` value, so visual attention and notification eligibility cannot disagree because they sampled different clocks.

Crossing a reminder boundary while Jig remains open therefore produces the card attention state on the next bounded clock tick without navigation or Task mutation.

### JIG-110-SD-37 — Android daily rollover lifecycle

Android invokes the same canonical `rollForwardOutstanding` persistence transaction as Linux. That shared transaction now includes recurrence non-accumulation and returns both moved and superseded Task identities for atomic persistence/revision decisions; Android adds no recurrence-specific rollover branch.

For a configured Android runtime:

1. on initial application activation, run rollover for the current local civil date **before** returning the first Planner state;
2. on every transition from background/inactive to active, run rollover before canonical state refresh, reminder reconciliation and synchronization;
3. while the application remains foregrounded, schedule one timer for the next local-day boundary and run rollover at that boundary;
4. after a rollover that moves Tasks, mark synchronization pending, refresh canonical UI state, then reconcile native reminders for the resulting current-day Tasks.

A backgrounded/killed Android app is not required to wake itself at midnight solely for rollover. The first subsequent activation performs the missed rollover before presenting the plan.

Time-zone/local-date changes are naturally corrected by the next active-state rollover check; no separate time-zone domain state is persisted.

- inter-card spacing therefore remains a real target rather than dead whitespace;
- cross-date target additionally receives the subtle governed target background;
- no Task content is reordered in React merely to manufacture a preview.

dnd-kit's droppable target is the sole sensor/collision authority; Jig maps the targeted slot's typed date/index directly to `TaskDropIntent`. Jig must not implement a second geometric collision algorithm.

On drag end, apply the existing canonical move command exactly once when:
- the operation was not canceled;
- a valid **current-or-future** slot is targeted;
- index is within `0..filteredDestination.length`;
- destination differs from the no-op source position.

Past-date slots use the same date/index geometry but are marked unavailable from the existing local-date owner. Dropping on one performs no move and projects the canonical active-scheduling error through the existing operation-feedback owner. This UI affordance is advisory only: the pure core scheduling guard is authoritative and is also reused by Date-field create/edit.

No canonical mutation occurs on drag-over. Cancel/outside/pointercancel is a no-op.

Keep Move up/Move down and editable Date as the non-drag alternatives.

#### Required validation

Before IMP-04 closes, browser tests and the physical proof cover:

1. repeated initiation/release (at least 20 sequential drags) without stranded overlay/source state;
2. first↔middle↔last same-date reorder;
3. first/middle/last cross-date insertion;
4. empty-date insertion;
5. unequal card heights;
6. every inter-card slot remains targetable without oscillation;
7. target slot and visible insertion rule always agree;
8. API/canonical state remains unchanged until drop;
9. final persisted date/index equals the last visible slot;
10. cancel, pointercancel, outside drop and interruption restore exactly;
11. Task-body vertical scroll never initiates drag;
12. checkbox/menu/reference/card-open never initiate drag;
13. grip and completion checkbox remain vertically centered in the Task card while preserving independent hit areas;
14. past-date target is visibly unavailable, drop produces concise feedback and canonical state is unchanged;
15. long Planner auto-scroll preserves a valid slot;
16. keyboard movement remains operable;
17. 320/360/390/414 browser geometry and the physical Android device pass.

No release candidate may be declared until this proof has passed with the same implementation owner that ships.

## 14. Installer and deployment

### JIG-110-SD-23 — Linux installer phase one

Normal Linux installation installs only application/runtime/service assets.

Repository arguments become optional for the ordinary interactive installation path.

If `--repo` or the backwards-compatible `--repo-url` + `--checkout` automation inputs are supplied, installation performs canonical repository setup immediately and produces a configured installation.

Without repository input:

- install application/runtime;
- install/start service;
- service starts in bootstrap mode;
- `jig` opens the setup UI.

### JIG-110-SD-24 — local Android development build and F-Droid-first distribution

v1.1 builds and certifies Android artifacts only. No iOS project, build, signing or App Store release path is part of this release.

The implementation workflow must support a fast Android loop independent of any store:

1. use the repository-pinned Capacitor 8.6.2 / Android SDK 36 / Gradle-Android toolchain defined by JIG-110-SD-08;
2. build the Android development APK locally and in permanent verification;
3. exercise all implementation behavior that does not require physical hardware through unit/integration tests and an Android emulator where platform execution is required;
4. defer `adb install -r`, physical launch/log inspection and hardware-specific interaction/OS validation to one final physical-device certification wave;
5. repeat implementation builds without requiring F-Droid or Google Play publication.

Before Android implementation begins, verify the non-device toolchain required to build and run the emulator path: JDK, Android SDK/platform/build tools and Gradle wrapper/Android plugin inputs. Device bridge tooling and the physical debugging path must be verified and recorded before final physical-device certification, not as a prerequisite to non-device implementation.

The development APK uses the standard Gradle debug keystore/signing configuration and application ID `com.pontivus.jig`. It is a local development/certification artifact, not a second public distribution channel. The F-Droid build uses the same application ID, canonical data model and repository protocol.

**F-Droid is the first public Android application-repository target.** F-Droid compatibility is therefore an implementation constraint, not post-release packaging work.

The Android build must:

- be buildable from the public Jig source tree with a FLOSS-compatible Android/Gradle toolchain accepted by F-Droid;
- keep all Android runtime/build dependencies compatible with F-Droid main-repository inclusion;
- contain no required proprietary Google Play Services, Firebase, Crashlytics, advertising/tracking SDKs or any other non-FLOSS runtime dependency;
- expose one stable Android application/package ID that is also retained for any later Google Play publication;
- keep the native Android project/build inputs required for a source build available and current in the repository;
- provide the metadata/build information required to prepare and validate an F-Droid submission;
- support local F-Droid packaging verification with `fdroid lint` and `fdroid build` against the v1.1 metadata/recipe before release certification.

The permanent verification/certification path must also certify:

- a locally buildable development APK for direct physical-device validation;
- Android `versionName`/derived `versionCode` and package identity consistency with Jig release metadata;
- native dependency lock integrity;
- Android device/emulator acceptance for bootstrap, GitHub acquisition, persistence, notification and sync.

The GitHub Release asset matrix remains Linux-only in v1.1. Android public distribution is through F-Droid; do not upload a separately signed Android APK to the GitHub Release as a v1.1 public channel.

F-Droid inclusion itself is controlled by F-Droid's external review and eligibility process. Android implementation completion requires an F-Droid-submission-ready build and exercised submission path; it does not pretend to control the date on which F-Droid publishes the app.

Google Play publication is deferred to a later Jig version. The v1.1 design must not depend on Google Play services merely to make that later publication possible.

Distribution mechanics remain release-engineering concerns rather than Task/planning domain.

## 15. Security constraints

The following are release blockers:

- GitHub App private key embedded in any client/runtime artifact;
- any GitHub App `client_secret`, Redirect URI or private key embedded in a client/runtime artifact;
- provider token persisted in Git remote URL;
- provider token in `config.json`, SQLite Task data, portable records or logs;
- arbitrary shell command construction from repository/user input;
- bootstrap endpoint permitting arbitrary filesystem writes beyond explicit repository setup;
- Android WebView exposing unrestricted native filesystem paths;
- a second GitHub authorization path that bypasses the governed Device Flow;
- GitHub/provider-specific state in the generic service protocol or generic synchronization owner;
- generic synchronization receiving provider tokens, askpass paths or process-environment authentication material;
- configured reconnect depending on repository selection/acquisition/configuration machinery;
- duplicate Device Flow state/polling owners or parallel shell/UI GitHub snapshot contracts;
- repository clone destination escaping its managed root;
- Android Git adapter touching unrelated repository content during Jig synchronization;
- custom TLS bypasses or disabled certificate verification.

## 18. Android release-channel boundary

## 20. Explicit architectural non-decisions

This document does **not** authorize:

- rewriting Jig in Kotlin;
- replacing React/Astryx;
- moving canonical Task semantics into native code;
- remote/cloud Task storage;
- a Pontivus-hosted synchronization backend;
- GitHub API writes as a replacement for Git repository synchronization;
- a general Git provider abstraction framework;
- multiple active repositories;
- application-owned Git merge/rebase/conflict resolution;
- a DTO/ViewModel hierarchy;
- a generic repository/service/use-case architecture;
- retaining the current dnd-kit implementation as a second/parallel Planner drag-drop owner or mixing multiple production drag libraries/sensor stacks.

If an implementation proposal requires one of these, it requires separate product/architecture review rather than being inferred from mobile support.
