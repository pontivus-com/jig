# Jig v1.1 — Android mobile, reminders and repository onboarding technical solution

**Status:** Draft technical solution for review on branch `v1.1`.  
**Functional authority:** [v1.1 mobile functional design](../requirements/v1.1-mobile-functional-design.md).  
**Baseline:** Jig v1.0.6 architecture on `master`.  
**Platform scope:** v1.1 native delivery is Android-only. iOS remains architecturally possible but is not built, certified or distributed in this release.  
**Architecture rule:** Satisfy the v1.1 functional contract with the smallest new platform boundaries. Do not create a second Task model, DTO/mapping hierarchy, repository-management subsystem or parallel planning workflow.

## 1. Decision summary

v1.1 uses the following target architecture:

1. **Shared product layer remains TypeScript/React.**
   - `src/core` remains the canonical pure Task/planning authority.
   - the existing React UI remains the primary presentation implementation.
   - portable Jig records remain exactly one cross-device continuity format.

2. **Linux remains a Bun + loopback HTTP + system-Git runtime.**
   - existing configured installations keep their current path;
   - the Linux runtime gains an explicit unconfigured bootstrap mode so the application can start before repository selection.

3. **Native Android uses Capacitor 8 as the application shell.**
   - existing Vite/React assets are embedded in an Android application;
   - native plugins/adapters own capabilities unavailable or inappropriate in the WebView: secure credentials, local notifications, native/app storage and SQLite access;
   - Android does not run the Linux Bun/systemd/loopback-server stack.

4. **GitHub is the optimized v1.1 remote-acquisition provider.**
   - a GitHub App supplies repository authorization;
   - authorization uses a GitHub-supported public-client user authorization flow protected with PKCE/state;
   - the app requests only the repository permissions required for HTTP Git access;
   - provider tokens are stored in platform secure storage and are never embedded in Git remote URLs.

5. **Existing local desktop repositories stay provider-neutral.**
   - system Git and existing repository authentication/configuration continue to own those repositories;
   - no GitHub login is required for an already-usable checkout;
   - a checkout without a remote remains a valid healthy local-only Jig data home.

6. **Reminder attention becomes pure derived state.**
   - no `notified_at` or acknowledgement field is added to canonical Task;
   - notification delivery is a side effect separate from the reminder-due card state.

7. **Native Android reminder delivery uses OS local notifications.**
   - scheduled notifications must survive foreground/background transitions subject to platform policy;
   - desktop/browser delivery uses a service-worker-compatible browser Notification path while the UI is active, rather than relying only on the direct `Notification` constructor.

## 2. External capability evidence

The technical selections above are grounded in current upstream capabilities as of 2026-11-18:

- Capacitor 8 is explicitly designed to be added to an existing modern web application and targets iOS, Android and Web: https://capacitorjs.com/docs and https://capacitorjs.com/docs/getting-started
- Capacitor 8.6.2 is the current stable 8.x release used by this design; Capacitor 8 supports Android API 24+ and target SDK 36: https://www.npmjs.com/package/@capacitor/core and https://capacitorjs.com/docs/android
- AndroidX SQLite 2.7.1 provides the stable `sqlite-bundled` `BundledSQLiteDriver`, allowing one low-level SQLite engine without Room/SQLCipher: https://developer.android.com/jetpack/androidx/releases/sqlite
- Capacitor official plugins expose native filesystem, HTTP and local-notification capabilities to the web application: https://capacitorjs.com/docs/plugins and https://next.capacitorjs.com/docs/apis/local-notifications
- GitHub Apps can request `Contents` repository permission for HTTP Git access, and a user/installation token can be used as the HTTP Git password: https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app
- GitHub App user authorization supports PKCE and repository restriction, and GitHub documents both web-application and device flows for user access tokens: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app
- GitHub explicitly warns native/public clients not to embed a GitHub App private key and recommends platform-appropriate token storage: https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app
- `isomorphic-git` exposes clone/fetch/push against an injected filesystem and HTTP client and accepts OAuth/token authentication callbacks: https://isomorphic-git.org/docs/en/clone, https://isomorphic-git.org/docs/en/push and https://isomorphic-git.org/docs/en/authentication
- F-Droid main-repository inclusion requires a FLOSS application/dependency chain, public source and a source-buildable Android package; proprietary tracking/Google Play/Firebase-style dependencies are not acceptable in the main repository: https://f-droid.org/docs/Inclusion_Policy/ and https://f-droid.org/en/docs/Submitting_to_F-Droid_Quick_Start_Guide/
- F-Droid supports Gradle-based Android builds and upstream metadata, and provides fdroid build/fdroid lint tooling for packaging verification: https://f-droid.org/docs/Building_Applications/

These references justify capability, not application scope. Jig still owns only the v1.1 product responsibilities.

## 3. Architecture boundaries

### 3.1 Shared functional core

`src/core` remains environment-independent.

v1.1 adds the pure reminder helper defined below; `src/core` must not import:

- Capacitor;
- browser APIs;
- Bun;
- SQLite drivers;
- Git libraries;
- filesystem/process APIs.

A representative pure contract is:

~~~ts
export function isReminderDue(
  task: Task,
  now: Date,
): boolean;
~~~

This is not persisted state. It is a pure projection of the canonical Task and current local time.

`isReminderDue()` is the one reminder-due semantic owner. Callers pass the current local `Date`; the function derives today's civil date/local time using the existing date primitives. Do not create a general clock/service abstraction or another reminder predicate.

### 3.2 Shared UI

The React UI continues to render Planner, History, Settings and Task workspace.

Platform differences are limited to capabilities that genuinely differ:

- repository bootstrap/acquisition;
- persistence transport;
- Git transport;
- secure credential storage;
- notification scheduling/delivery.

Do not fork Planner into separate desktop/mobile applications.

### 3.3 Platform shells

The target runtime composition is:

~~~text
                         shared TypeScript
        ┌───────────────────────────────────────────┐
        │ src/core — Task/planning/reminder rules   │
        │ ui/      — React/Astryx presentation      │
        │ portable record serialization/validation  │
        └───────────────────┬───────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              │                           │
       Linux imperative shell      Native Android shell
       Bun + loopback HTTP         Capacitor Android
       bun:sqlite                   native SQLite adapter
       system git                   Android Git adapter
       browser notification        OS local notification
       OS secure credential        Android Keystore
~~~

The platform shell boundary is an imperative-shell boundary, not a new domain layer.

## 4. Linux two-phase bootstrap

### JIG-110-SD-01 — runtime mode

The current `src/shell/main.ts` assumes a complete `JigConfig`, acquires the repository writer lease and opens SQLite before starting HTTP. That prevents in-app setup.

v1.1 changes startup into two explicit runtime modes:

~~~text
config present + valid
        ↓
configured runtime
        ↓
existing Planner HTTP application

config absent
        ↓
bootstrap runtime
        ↓
serve UI + bootstrap endpoints only
        ↓
repository setup succeeds
        ↓
write canonical config atomically
        ↓
transition/restart into configured runtime
~~~

Do not persist an invented "unconfigured repository" object. Absence of valid configuration is the bootstrap condition.

The bootstrap process must not open a planning database or start repository synchronization before repository setup succeeds.

### JIG-110-SD-02 — bootstrap API surface

The Linux bootstrap HTTP surface must be narrow and setup-specific.

It needs only enough authority to:

- report configured/unconfigured state;
- validate/adopt an existing local repository;
- start/complete the GitHub authorization flow;
- list/select GitHub repositories available to the authorized Jig integration;
- clone the selected GitHub repository into Jig-managed storage;
- initialize/adopt Jig data;
- atomically write final `JigConfig`.

It must not expose arbitrary filesystem browsing, arbitrary Git commands, remote editing or branch management.

Existing configured Task/state/command endpoints remain unavailable until setup is complete.

### JIG-110-SD-03 — upgrade compatibility

Installer upgrade logic must preserve an existing `~/.config/jig/config.json`.

A configured v1.0.x installation must continue through the configured startup path without any config migration solely because v1.1 supports bootstrap mode.

The Linux `JigConfig` remains version 1 with exactly `version`, `repository_path`, and `http_port`. Bootstrap mode is represented by absence of the config file; provider credentials and onboarding state are not added to `JigConfig`.
### JIG-110-SD-28 — bootstrap UI composition and transition

The React application has exactly two top-level runtime presentations: `bootstrap` and `configured`. The shell reports this state before the application attempts to load Planner data.

Linux bootstrap renders one setup surface with exactly two primary choices:

1. **Use a repository already on this computer**
2. **Connect GitHub**

`Use a repository already on this computer` opens one form containing an absolute repository-path text field, validation feedback and Continue/Cancel. The Linux browser UI must not rely on the browser File System Access API to obtain a server-side POSIX path, because a browser directory handle is not the canonical repository path consumed by the Bun shell. Users may paste/type the worktree root; expert CLI `--repo` remains available.

`Connect GitHub` enters the provider flow owned by JIG-110-SD-29.

Android bootstrap exposes only **Connect GitHub** in v1.1; arbitrary device-local worktree selection is not rendered.

Bootstrap errors remain on the bootstrap surface with the entered/selected choice intact. Planner/History/Settings, Task commands and repository sync are not mounted until canonical repository setup succeeds.

After setup writes the final Linux `JigConfig`, the service restarts or transitions once into configured runtime and the UI reloads canonical state. There is no persisted onboarding step/state machine in Task or portable data.

## 5. Repository onboarding implementation

### JIG-110-SD-25 — existing local desktop repository adoption

The existing `validateSelectedRepository()` and `initializeRepositoryInstallation()` semantics remain the canonical adoption path.

In-app local selection calls that same shell authority rather than introducing a second setup implementation.

Rules retained:

- absolute worktree root;
- readable/writable;
- public `pontivus-com/jig` source checkout rejected as planning data;
- existing valid portable snapshot adopted;
- SQLite/data identity consistency enforced;
- unrelated content untouched.

A repository with no remote is accepted and results in healthy `local-only`.

After canonical setup, determine synchronization mode through the existing `repositorySynchronizationMode()` / `discoverSynchronizationRemote()` authority. No-remote discovery must not fail setup, create a remote or prompt for GitHub.

A repository with an existing synchronization remote uses the current system-Git adapter and the repository's normal Git authentication. Authentication/fetch/push failure after local setup changes only the coarse repository outcome (`pending/retrying/sync-issue`); it does not roll back the locally valid Jig installation or corrupt Task data.

Jig never rewrites existing remotes, branches, upstreams, credential helpers, signing configuration or unrelated repository content during adoption.

### JIG-110-SD-26 — managed desktop GitHub checkout

The GitHub-acquisition path uses one deterministic Jig-owned checkout root that is separate from the atomically replaced application runtime:

~~~text
~/.local/share/jig-data/
  repositories/
    github/
      <owner>/
        <repository>/
          .git/
          .jig/
          ...
~~~

The canonical Linux managed checkout for GitHub repository `owner/repository` is therefore:

`~/.local/share/jig-data/repositories/github/<owner>/<repository>`

The managed root is created user-owned with no broader permissions than required by the current user. The normal onboarding UI does not ask for an alternate path. Existing expert/noninteractive `--repo` remains the path override mechanism rather than adding a second managed-checkout preference.

If the final managed path does not exist, acquisition clones to a newly-created temporary sibling under the same `<owner>` directory and moves it to the final path only after clone/remote verification succeeds. A failed clone removes only that newly-created temporary directory. It never deletes or overwrites an existing final path.

If the final path already exists, Jig does not overwrite it. It may reuse it only after `validateSelectedRepository()` succeeds and the existing GitHub remote URL normalizes to the selected `owner/repository`; otherwise setup stops with a non-destructive error.

After acquisition/reuse, the exact same `initializeRepositoryInstallation()` authority used for an existing local repository performs Jig adoption/initialization. No GitHub-specific Task, SQLite or portable-data initialization path is permitted.

### JIG-110-SD-27 — credentialed Linux clone delegation

On Linux, repository acquisition remains delegated to the system `git` executable.

For a Jig-authorized GitHub clone, construct the clone URL without credentials:

`https://github.com/<owner>/<repository>.git`

Invoke system Git with an ephemeral askpass helper/environment owned by the clone operation. The helper obtains the current GitHub access token from the device credential adapter and returns it only to Git's credential prompt. The token must not appear in the clone URL, process arguments, Git configuration, shell history, logs or portable data.

The helper/environment exists only for the Git subprocess lifetime. Normal repository remotes therefore persist the credential-free HTTPS URL.

Jig must not modify global or repository Git credential configuration. Existing local repositories continue to use their existing Git credential/topology configuration.

Clone success is not repository setup success: only after Git exits successfully, the worktree root validates, and the selected GitHub remote matches the requested repository may the temporary checkout move to its final managed path and proceed to canonical Jig adoption.

## 6. GitHub App authentication

### JIG-110-SD-04 — provider model

v1.1 optimizes only GitHub remote acquisition.

Existing local repositories remain provider-neutral and continue through system Git.

No GitLab/Bitbucket account-login integrations are required for v1.1.

### JIG-110-SD-05 — GitHub App permissions

Register a GitHub App whose repository permission set is the minimum proven set needed for the selected flow.

Required baseline:

- **Contents: read & write** for HTTP Git clone/fetch/push.

Do not request Issues, Pull requests, Administration, Actions/Workflows or organization permissions unless an implementation proof demonstrates that a specific onboarding API requires one. Repository enumeration uses only the GitHub App's implicit/read-only metadata visibility plus the required Contents permission; it must not request a broader permission solely for listing.

The onboarding flow instructs the user to install the GitHub App on only the repository/repositories they choose; Jig does not request all-repository access as its default path.

### JIG-110-SD-06 — public-client authorization

The Linux/Android client must not contain a GitHub App private key and must not generate installation tokens locally.

Use GitHub App **user authorization**.

The authorization-code flow is fixed as follows:

1. generate cryptographically random `state` and PKCE `code_verifier`;
2. derive the `S256` `code_challenge`;
3. request GitHub App user authorization with `offline_access` so expiring access + refresh tokens are available;
4. validate exact returned `state` before exchanging the code;
5. exchange with the original `code_verifier`;
6. persist tokens only through JIG-110-SD-07.

Linux uses a temporary loopback callback listener at **`http://127.0.0.1:47832/setup/github/callback`**, registered as a GitHub App callback URL and separate from Jig's configurable application port (default 47831). The listener exists only during authorization. If 47832 cannot be bound, Linux falls back to GitHub App device flow for that attempt rather than changing Jig's application port.

Android registers **`com.pontivus.jig://oauth/github`** as the second GitHub App callback URL and handles it through `@capacitor/app`'s URL-open event. The returned URI must match scheme/host/path exactly before state/code processing.

The GitHub App installation itself is restricted by the user to selected repositories. The user access token is not treated as a Jig authorization boundary beyond the permissions/repository access GitHub grants.

Public clients cannot protect a GitHub App client secret/private key. No GitHub private key or trusted client secret is shipped in Linux/Android artifacts. PKCE, state validation, GitHub's own installation authorization and platform secure token storage are the controls.

Device flow is enabled only for the Linux bind-failure fallback; Android never uses device flow in v1.1.

### JIG-110-SD-07 — platform credential storage

Provider access/refresh tokens are device-local operational secrets and have one platform adapter per runtime.

**Linux:** store the GitHub credential in the freedesktop Secret Service (`org.freedesktop.secrets`) default collection under label `Jig GitHub` and attributes `application=jig`, `provider=github`, and the authorized GitHub numeric user id. The implementation uses the Secret Service protocol; it must not fall back to plaintext files, `git-credential-store`, environment persistence or `config.json`. If no unlocked Secret Service collection is available, **Connect GitHub cannot complete** and the setup UI reports that secure credential storage is unavailable; **Use a repository already on this computer** remains available.

**Android:** implement one narrow Capacitor plugin, `JigSecureCredentials`, backed by Android Keystore. Generate a non-exportable 256-bit AES key with alias `com.pontivus.jig.github.credentials.v1` using `AES/GCM/NoPadding`. Store only AES-GCM ciphertext, IV and token metadata in an app-private **no-backup** SharedPreferences file. Plain access/refresh tokens exist only in process memory while being used.

The stored provider credential payload contains only the fields needed to renew/use GitHub authorization: GitHub numeric user id, access token, optional refresh token, access-token expiry and refresh-token expiry. It contains no repository/Task data.

Credential lookup, refresh, replacement and deletion are imperative-shell operations. Revocation/expiry produces an authentication/synchronization issue and offers **Reconnect GitHub**; it must not corrupt or roll back local Task data.

Credentials must never be written to `JigConfig`, SQLite Task rows, portable records, repository files, Git remote URLs, logs, crash reports or process arguments.

### JIG-110-SD-29 — GitHub acquisition orchestration

The GitHub onboarding flow is transient presentation/shell state, not persisted Jig domain state. Its complete progression is:

~~~text
idle
  → authorizing
  → repository-selection
  → acquiring
  → adopting
  → configured
~~~

Failure in `authorizing` returns to Connect GitHub. Failure in repository listing/selection keeps the valid authorization and returns to repository selection. Failure in acquisition/adoption preserves any valid credential but leaves Jig unconfigured; only the temporary checkout created by the failed acquisition may be removed.

The repository-selection list is populated only from repositories available to the authorized GitHub App/user. Selecting a repository supplies its canonical `owner`, `name`, clone URL and provider repository identifier to the acquisition adapter; these values are operational inputs, not Task fields or portable records.

Linux acquisition delegates to JIG-110-SD-26/27. Android acquisition delegates to JIG-110-SD-12/13/14.

After a clone exists, provider-specific onboarding ends. Repository validation/adoption, dataset identity, SQLite initialization and portable snapshot handling use the same canonical Jig authorities as every other checkout.

Repository credentials are retrieved from the platform credential adapter at Git-operation time. They are never copied into `JigConfig` or `.git/config` remote URLs.

## 7. Native Android application shell

### JIG-110-SD-08 — pinned Android application platform

Use Capacitor **8.6.2** for the v1.1 Android shell and pin the exact versions in the repository lockfile:

- `@capacitor/core@8.6.2`;
- `@capacitor/android@8.6.2`;
- `@capacitor/cli@8.6.2`;
- `@capacitor/app@8.1.2` for Android lifecycle/deep-link events;
- `@capacitor/filesystem@8.1.5` for app-owned filesystem access used by the Android Git adapter;
- `@capacitor/local-notifications@8.3.1` for native reminder scheduling.

The Android application ID/package name is **`com.pontivus.jig`** and is stable across development, direct-release APK, F-Droid and any later Google Play publication. Debug/release signing keys differ; application identity and data contracts do not.

Android baseline:

- `minSdkVersion = 24` (Android 7);
- `compileSdkVersion = 36`;
- `targetSdkVersion = 36`;
- Capacitor CLI build environment uses Node.js 22+ as required by Capacitor 8;
- Android development environment uses Android Studio 2025.2.1 or newer compatible tooling and SDK Platform 36.

The native project lives in the repository `android/` directory and is committed source, not generated only in a developer workstation. It contains only the Capacitor host and narrow native adapters required by this design.

No Google Services Gradle plugin, Firebase SDK, Play Services dependency or proprietary analytics/crash SDK is permitted in the v1.1 Android dependency graph.

The native project is a build/runtime adapter, not an alternate product source.

### JIG-110-SD-09 — mobile application state

Native Android has the same two application states:

~~~text
unconfigured
    → GitHub onboarding
    → repository acquired/adopted
configured
    → Planner/History/Settings
~~~

Unlike Linux, Android does not require a loopback HTTP service to represent that transition.

The React application calls a small platform runtime boundary whose web/Linux implementation uses the existing HTTP API and whose native implementation invokes the mobile imperative shell.

Do not create transport-specific Task copies. Inputs and outputs use canonical `Task`, `TaskCommand`, `CanonicalState`, repository status and diagnostics meanings already owned by the codebase.

### JIG-110-SD-10 — exact platform runtime boundary

The runtime boundary remains function-shaped and reuses existing canonical/protocol types; it does not create platform DTOs, ViewModels, service classes or repository classes.

Create `ui/src/runtime.ts` as the configured UI capability owner. It exposes the same five configured operations/signatures already consumed from `ui/src/http.ts`:

- `readCanonicalTasks(): Promise<CanonicalState>`;
- `readStatus(): Promise<ServiceStatus>`;
- `readDiagnostics(): Promise<Diagnostics>`;
- `submitTaskCommand(command: TaskCommand, expectedRevision: number): Promise<CommandResult>`;
- `triggerSync(): Promise<RepositoryStatus>`.

The Linux/web implementation delegates those functions to the existing HTTP adapter. The Android implementation calls the native persistence/Git shell while consuming/returning the same existing `TaskCommand`, `CanonicalState`, `CommandResult`, `Diagnostics`, `ServiceStatus` and `RepositoryStatus` types from `src/core` / `src/protocol`.

Bootstrap/onboarding capabilities remain separate from configured runtime calls and are available only while unconfigured. Reminder scheduling/reconciliation is an imperative side effect invoked from Task mutation/app lifecycle handling, not another general service layer.

No new domain-to-transport mapping hierarchy is authorized.

## 8. Mobile SQLite

### JIG-110-SD-11 — one schema, two drivers

Android requires native durable SQLite but cannot use Bun's `bun:sqlite`.

The schema, migration numbers, invariants and SQL semantics remain one authority.

Refactor only the minimum reusable persistence material necessary so Linux and mobile cannot drift on:

- table/schema definition;
- canonical row validation;
- transaction boundaries for Task commands;
- metadata/dataset identity;
- portable-format revision tracking;
- rollover semantics.

Linux continues using `bun:sqlite`.

Android uses a Jig-owned narrow Capacitor plugin named **`JigSqlite`** backed by **`androidx.sqlite:sqlite-bundled:2.7.1`** / `BundledSQLiteDriver`.

Do not use Room, SQLCipher or `@capacitor-community/sqlite` for v1.1. Room would introduce a second schema/model owner; SQLCipher is not required by the product; and the Jig adapter needs only a small low-level SQL boundary.

`JigSqlite` exposes only generic persistence mechanics needed by the existing TypeScript persistence owner:

- open/close a database at the Jig-owned app path;
- execute schema/migration SQL;
- execute a statement with positional bind values and return affected-row/insert metadata;
- query rows as validated primitive column values;
- begin/commit/rollback a transaction.

The plugin does not define Task classes, Task tables, migrations or repository semantics. Those remain generated/owned by the shared TypeScript persistence definition. A transaction begun for one canonical command is committed only after all affected writes succeed and is rolled back on any failure.

The Android database path is the same semantic location inside the app-owned checkout as Linux: `<repository>/.jig/local/jig.sqlite`. Because the entire Android checkout is app-private, no external-storage permission is required.

Release certification must prove schema/migration parity, constraint behavior, rollback behavior, WAL/restart durability and dataset/revision metadata parity against the Linux `bun:sqlite` implementation.
### JIG-110-SD-30 — one canonical Task, command and portable-data contract

Android support does not introduce a second planning model.

The Android runtime imports and executes the same `src/core` Task types/rules and the same canonical command semantics used by Linux. Platform transport boundaries may adapt invocation mechanics, but they must not define duplicate Task/command shapes.

The current portable Jig snapshot serializer/validator and dataset identity remain the single cross-device interchange authority. v1.1 mobile support does **not** change the portable record format merely to accommodate Android. Any future portable-format change requires its own explicit versioned design/migration decision.

Linux and Android persistence drivers execute the same governed schema/migration definition. Driver-specific code owns SQL execution/transaction mechanics only; canonical row validation, Task invariants, revision/dataset metadata semantics and rollover rules remain shared.

Cross-platform interoperability is accepted only when the same repository/dataset can round-trip Linux → Android → Linux without conversion and with unrelated repository content unchanged.

## 9. Mobile Git transport

### JIG-110-SD-12 — repository storage

The Android Git working tree lives in private application-owned persistent storage.

The user is not prompted for a path.

The checkout and SQLite database are local cache/operational state; the remote repository's portable Jig records remain the continuity mechanism across installations.

### JIG-110-SD-13 — selected Android Git adapter

The v1.1 Android Git adapter is **`isomorphic-git@1.44.16`** with:

~~~text
isomorphic-git@1.44.16
+ Jig Node-like fs adapter over @capacitor/filesystem@8.1.5
+ Jig native HTTP adapter (Capacitor/native networking; no browser CORS proxy)
+ GitHub access token supplied only through isomorphic-git onAuth
~~~

The filesystem adapter implements only the Node-like filesystem operations required by isomorphic-git against the private app-owned repository root and flushes all pending filesystem writes before a Git operation is reported successful.

The HTTP adapter performs Git smart-HTTP directly through native Android networking. **No external CORS proxy, Pontivus proxy or cloud synchronization service is permitted.**

This selection has the mandatory feasibility gate in JIG-110-SD-14 before feature implementation builds on it.

### JIG-110-SD-14 — Android Git feasibility gate

A disposable proof must demonstrate on Android:

1. authorize a test GitHub App user;
2. clone a private selected repository over HTTPS into app-owned storage;
3. open/restart and read the same Git repository;
4. fetch;
5. create/update only Jig-owned portable files through the existing isolation policy;
6. commit with the required Jig synchronization identity semantics;
7. push;
8. authenticate through a callback without persisting the token in the remote URL;
9. handle offline/auth failure as a coarse sync outcome;
10. leave unrelated repository files unchanged;
11. recover after application restart;
12. interoperate with a repository subsequently synchronized by desktop system Git.

The proof must specifically validate that the chosen Capacitor/native HTTP path can carry Git smart-HTTP traffic without browser CORS dependence and that the filesystem adapter provides the semantics required by `isomorphic-git`.

If any mandatory gate item fails, **stop Android Git implementation and amend this technical solution before proceeding**. The implementation team is not authorized to substitute JGit, libgit2, a server-side proxy, GitHub Contents API writes or another transport on its own. Failure of the selected adapter is a design-blocking finding, not permission to broaden the architecture.

## 10. Synchronization scheduling on Android

### JIG-110-SD-15 — local save first

A Task mutation commits to Android SQLite before remote synchronization is attempted, matching desktop local-first semantics.

The mutation marks synchronization work pending and returns local success independently of network availability.

### JIG-110-SD-16 — sync opportunities

At minimum, Android attempts synchronization:

- after a local mutation with bounded debounce;
- when the application becomes active/resumes;
- after successful repository acquisition;
- after connectivity becomes available while the application is active;
- on explicit user Retry/Sync action.

Do not promise arbitrary continuous background execution that Android cannot guarantee.

If later platform background-run APIs are used, they are an optimization of sync opportunity, not a new correctness requirement. Local pending data must remain safe until the next permitted execution opportunity.

## 11. Reminder architecture

### JIG-110-SD-17 — pure due-state owner

Add one pure reminder-due predicate in the functional core.

It consumes canonical Task + explicit local clock values.

It returns true only when:

- incomplete;
- reminder present;
- scheduled date equals current local date;
- reminder time is earlier than or equal to current local time.

No localStorage delivery key participates in this predicate.

### JIG-110-SD-18 — UI attention projection

Task-card presentation derives the reminder-due state from that pure owner.

Introduce one governed semantic alias for reminder attention, consumed across all themes.

The reminder indicator must combine correctly with:

- priority leading cue;
- selected surface;
- drag state;
- focus;
- today/date semantics.

No theme-specific branch or palette literal belongs in feature code.

### JIG-110-SD-19 — Linux/browser delivery

Replace the assumption that direct `new Notification(...)` is the only delivery mechanism.

For the browser UI:

- register a small Jig service worker;
- when the open application determines a reminder is newly due and permission is granted, request display through `ServiceWorkerRegistration.showNotification()`;
- retain bounded duplicate suppression for the same Task/date/time delivery attempt;
- constructor/service-worker failure must remain retryable and must not clear reminder-due attention.

The service worker is a delivery adapter only. It does not become the canonical scheduler, Task store or push subsystem.

v1.1 still does not claim remote push or guaranteed closed-browser desktop delivery.

### JIG-110-SD-20 — native Android delivery

Use **`@capacitor/local-notifications@8.3.1`** as the Android notification adapter.

On Android 13+, check/request notification permission before scheduling. For exact reminder times on Android versions that gate exact alarms, declare the required exact-alarm permission and use the plugin's exact-setting check. If exact alarms are unavailable/disabled, scheduling returns an explicit inexact/failure outcome; Jig must not label it exact.

When a future reminder-bearing Task is saved, schedule the OS local notification.

On edit/complete/delete/reschedule:
- cancel stale pending notification;
- schedule the replacement if still eligible.

On application startup/resume:
- reconcile pending OS notifications against canonical outstanding Tasks so side-effect drift cannot become permanent.

Do not persist notification-delivered state into canonical Task solely to drive the reminder-due card.

Android exact-notification policy must be handled honestly: if exact scheduling permission/settings are unavailable, the UI must not claim exact delivery. If exact scheduling is unavailable, Android schedules the reminder inexactly and returns `scheduled-inexact`; Settings exposes that exact timing is unavailable. The Task's in-app due state remains exact from canonical local time. Jig never reports `scheduled-inexact` as exact delivery.
### JIG-110-SD-31 — reminder corrective closure

The v1.0.6 browser monitor contains a concrete defect: `ui/src/reminder.tsx` records `sessionStartedAt` and skips every candidate where `dueAt < sessionStartedAt.current`. v1.1 removes that gate and removes the session-start timestamp entirely.

One pure `isReminderDue(task, now)` owner (JIG-110-SD-17) supplies both Task-card attention and delivery eligibility. On initial mount, Task change, the existing bounded timer, focus and visibility revalidation, an incomplete current-day Task whose reminder time is `<= now` is due regardless of when the current browser/app session started.

The delivery-suppression key remains device-local side-effect state keyed by Task id + scheduled date + reminder time. It suppresses duplicate notification delivery only; it must never suppress the card-level due state.

For Linux/browser catch-up, if a reminder is already due when Jig opens and no delivery-suppression key exists, Jig makes one delivery attempt when permission is granted. Permission denial, unsupported capability or delivery failure leaves the key absent so a later bounded check may retry.

For Android, native scheduling owns future delivery. Startup/resume reconciliation schedules only future reminders and cancels stale pending entries; an already-past reminder is represented immediately by the in-app due state rather than manufacturing a new past-time schedule.

Roll-forward preserves `reminder_time`; after rollover, the same pure predicate determines whether the now-current-date Task is already due.

No `notified_at`, `delivered_at`, acknowledgement flag or second Task status is added to canonical Task.

### JIG-110-SD-32 — notification delivery adapters and outcome semantics

`ui/src/browser-notifications.ts` becomes the browser permission/delivery adapter instead of exposing permission only. It owns:

- capability/permission inspection;
- permission request from the existing explicit Settings user gesture;
- service-worker registration/readiness;
- `showNotification()` delivery;
- a typed operational outcome such as `displayed | permission-required | denied | unsupported | failed`.

The browser ReminderMonitor marks its duplicate-suppression key only after the delivery adapter resolves `displayed`. A thrown/rejected service-worker notification remains `failed` and is retryable. Direct `new Notification(...)` is removed as the production delivery path.

The service worker is static application infrastructure only: no push subscription, remote scheduler, Task store or canonical reminder state is added.

Android uses the native local-notification adapter from JIG-110-SD-20. Scheduling returns `scheduled | permission-required | denied | failed`; UI wording must distinguish **scheduled** from **delivered/displayed** and must never claim an OS notification was observed merely because scheduling succeeded.

Because the Android notification API requires platform notification identifiers, keep a device-local non-portable schedule registry in the Android operational SQLite database: `task_id` is the unique semantic key, with the allocated platform notification id and reminder fingerprint (`scheduled_date|reminder_time`). This registry exists only to cancel/replace pending OS side effects. It is not canonical Task state, is never exported to Git and must be rebuilt/repaired by startup/resume reconciliation from outstanding Tasks plus the platform pending-notification list whenever the registry is missing or inconsistent.

Completion, delete, reminder removal/change and date change cancel the registered pending notification before/after the canonical Task transaction as an imperative side effect; failure to cancel is recorded diagnostically and corrected by next startup/resume reconciliation without rolling back the already-durable Task mutation.

## 12. Android/desktop sticky header implementation

### JIG-110-SD-21 — persistent header owner

There must be one vertical scroll owner for application content.

Required composition:

~~~text
application viewport
├── persistent/sticky header
│   ├── application row
│   └── Planner temporal row (Planner only)
└── content scroller
    └── Planner / History / Settings
~~~

The current `ui/src/app.tsx` already renders `PlannerHeader` as the Astryx `AppShell.topNav` sibling of `.jig-content-frame`. Keep that semantic ownership.

Apply stickiness at the Jig header itself for narrow/mobile mode: `.jig-app-header-narrow { position: sticky; inset-block-start: 0; z-index: 1; }`. The content frame remains the vertical content scroller. Do not move Planner/History/Settings content into the header scroll context.

Do not use absolute offsets, duplicated responsive DOM or CSS transforms to fake persistence.

Native safe-area top inset must be consumed through the supported platform/CSS environment integration.

### JIG-110-SD-22 — touch geometry

Remove the v1.0.6 narrow `height: 3.5rem` / `<=56px` requirement.

The Android header's height is content-driven from its two rows and Astryx touch-appropriate component sizes.

The implementation plan must define and test a product-level minimum interactive target budget of at least 44 CSS px per primary Android control/menu row unless the selected Astryx public component is larger by default.

Widths 320, 360, 390 and 414px are mandatory acceptance viewports.
### JIG-110-SD-33 — narrow-header corrective closure

The current `NarrowHeader` in `ui/src/planner-header.tsx` renders brand, temporal navigation, Add, sync and menu in one grid row, and `ui/src/styles.css` hard-codes `.jig-app-header-narrow` to `height: 3.5rem`. `tests/browser/ui-conformance.spec.ts` then locks that defect with `narrowHeight <= 56`.

v1.1 replaces only the narrow composition; desktop header composition and its `<=44px` budget remain unchanged.

The narrow JSX hierarchy becomes:

~~~text
<header .jig-app-header-narrow>
  <div .jig-header-mobile-application-row>
    BrandHome
    [Planner only: Add task]
    compact sync status
    destination menu
    [History/Settings: active destination title]
  </div>
  [Planner only:
    <div .jig-header-mobile-temporal-row>
      Previous / week range / Next / Today
    </div>
  ]
</header>
~~~

`DESTINATIONS` remains the one typed owner for Planner/History/Settings menu items. Do not duplicate destination arrays for Android.

`.jig-app-header-narrow` is content-height rather than fixed-height and is the single sticky unit: `position: sticky; inset-block-start: 0; z-index: 1`. It retains an opaque semantic application background and bottom hairline so scrolling Task content cannot paint through it. Native Android top padding consumes `env(safe-area-inset-top, 0px)` at this header owner.

The two child rows use Astryx public controls and at least 44 CSS px primary interaction height. They must not use absolute positioning or negative offsets to fit the old 56px envelope.

The old browser assertion `narrowHeight <= 56` is deleted. Replacement acceptance scrolls long Planner, History and Settings content and asserts the header's viewport top remains constant; Planner asserts two rendered rows, History/Settings one rendered application row, and all required controls remain non-overlapping at 320/360/390/414px.

## 13. Installer and deployment

### JIG-110-SD-23 — Linux installer phase one

Normal Linux installation installs only application/runtime/service assets.

Repository arguments become optional for the ordinary interactive installation path.

If `--repo` or the backwards-compatible `--repo-url` + `--checkout` automation inputs are supplied, installation performs canonical repository setup immediately and produces a configured installation.

Without repository input:

- install application/runtime;
- install/start service;
- service starts in bootstrap mode;
- `jig` opens the setup UI.

### JIG-110-SD-24 — local Android development build and F-Droid-first distribution

v1.1 builds and certifies Android artifacts only. No iOS project, build, signing or App Store release path is part of this release.

The implementation workflow must support a fast local Android loop independent of any store:

1. use the repository-pinned Capacitor 8.6.2 / Android SDK 36 / Gradle-Android toolchain defined by JIG-110-SD-08;
2. build the Android development APK locally;
3. install/update it directly on a connected physical Android device through the standard Android development tooling (for example `adb install -r` or the equivalent IDE/device action);
4. exercise the real application on-device;
5. repeat without requiring F-Droid or Google Play publication.

Before Android implementation begins, verify the development environment has the required JDK, Android SDK/platform/build tools, Gradle wrapper/Android plugin inputs, device bridge tooling and a usable physical-device debugging path. Do not assume their presence merely because Android tooling has been used previously; record the verified versions as implementation evidence.

The development APK uses the standard Gradle debug keystore/signing configuration and application ID `com.pontivus.jig`. The governed release APK uses the release signing key but the same application ID, canonical data model and repository protocol; signing mode must not create a separate Jig product or data format.

**F-Droid is the first public Android application-repository target.** F-Droid compatibility is therefore an implementation constraint, not post-release packaging work.

The Android build must:

- be buildable from the public Jig source tree with a FLOSS-compatible Android/Gradle toolchain accepted by F-Droid;
- keep all Android runtime/build dependencies compatible with F-Droid main-repository inclusion;
- contain no required proprietary Google Play Services, Firebase, Crashlytics, advertising/tracking SDKs or equivalent non-FLOSS runtime dependency;
- expose one stable Android application/package ID that is also retained for any later Google Play publication;
- keep the native Android project/build inputs required for a source build available and current in the repository;
- provide the metadata/build information required to prepare and validate an F-Droid submission;
- support local F-Droid packaging verification with `fdroid lint` and `fdroid build` against the v1.1 metadata/recipe before release certification.

The Jig release pipeline must also certify:

- a governed signed Android release APK suitable for direct installation and release attachment;
- app version/package identity consistency with Jig release metadata;
- native dependency lock integrity;
- Android device/emulator acceptance for bootstrap, GitHub acquisition, persistence, notification and sync.

F-Droid inclusion itself is controlled by F-Droid's external review and eligibility process. v1.1 release certification requires an F-Droid-submission-ready build and exercised submission path; it does not pretend to control the date on which F-Droid publishes the app.

Google Play publication is deferred to a later Jig version. The v1.1 design must not depend on Google Play services merely to make that later publication possible.

Distribution mechanics remain release-engineering concerns rather than Task/planning domain.

## 14. Security constraints

The following are release blockers:

- GitHub private key embedded in client binary;
- provider token persisted in Git remote URL;
- provider token in `config.json`, SQLite Task data, portable records or logs;
- arbitrary shell command construction from repository/user input;
- bootstrap endpoint permitting arbitrary filesystem writes beyond explicit repository setup;
- Android WebView exposing unrestricted native filesystem paths;
- provider authorization callback without state/PKCE validation;
- repository clone destination escaping its managed root;
- Android Git adapter touching unrelated repository content during Jig synchronization;
- custom TLS bypasses or disabled certificate verification.

## 16. Implementation sequence constraints

Design approval should lead to implementation in this order:

1. pure reminder-due semantics + UI attention state;
2. sticky/two-row Android header and touch geometry;
3. Linux bootstrap mode + in-app existing-local repository setup;
4. GitHub App registration/authentication proof and desktop managed clone;
5. Capacitor shell proof using current React UI;
6. local development APK build + direct physical-device install loop;
7. Android SQLite certification;
8. Android Git feasibility gate;
9. native reminder scheduling;
10. F-Droid packaging/submission validation;
11. full cross-device synchronization and release certification.

Do not begin large-scale Android shell implementation before the Git/SQLite feasibility gates are proven.

## 17. Android release-channel boundary

F-Droid is the first Android app-store/repository target for v1.1.

The application and build graph must remain eligible for F-Droid's FLOSS/source-build model. In particular, core planning, Git synchronization, repository onboarding, secure credential handling and reminder delivery must not depend on proprietary Google Play services, Firebase or another proprietary mobile backend/SDK.

The governed Jig release also publishes a signed APK so users are not blocked by F-Droid's external review/publication timing.

Google Play integration/publication is a later-version concern and must be additive release engineering rather than a prerequisite for core Android behaviour.

iOS/App Store work is explicitly deferred.

## 19. Explicit architectural non-decisions

This document does **not** authorize:

- rewriting Jig in Kotlin;
- replacing React/Astryx;
- moving canonical Task semantics into native code;
- remote/cloud Task storage;
- a Pontivus-hosted synchronization backend;
- GitHub API writes as a replacement for Git repository synchronization;
- a general Git provider abstraction framework;
- multiple active repositories;
- application-owned Git merge/rebase/conflict resolution;
- a DTO/ViewModel hierarchy;
- a generic repository/service/use-case architecture.

If an implementation proposal requires one of these, it requires separate product/architecture review rather than being inferred from mobile support.
