# Jig v1.1.2 corrective technical design

**Status:** BINDING implementation design for JIG-112-FR-01..12.  
**Target release:** 1.1.2.  
**Tracking issue:** #66.

## Verified investigation baseline

The following repository facts are implementation inputs, not optional interpretations:

- The pinned Astryx `AppShell height="fill"` already establishes a `100dvh` shell and makes its main `LayoutContent` the fill-mode scroll region. The viewport defect is below that boundary: Jig currently adds a second `.jig-content-frame { height: 100%; overflow: auto; }` while feedback and content are sibling children.
- The current drag implementation uses raw `useDraggable`, N+1 insertion-slot droppables, a fading source card and a hand-built simplified overlay. That implementation produces the rejected insertion-line UX.
- Jig v1.0.5 used the same pinned `@dnd-kit/react@0.5.3` / `@dnd-kit/dom@0.5.3` generation and eliminated a React `NotFoundError: removeChild` reconciliation crash by suppressing dnd-kit's optimistic DOM sorting with `event.preventDefault()` during drag-over. v1.1.2 must not re-enable that failure mechanism.
- The 13 theme sources do not share one tonal topology. Several upstream themes intentionally alias body/surface/card or surface/card roles. Therefore one shared `color-mix` formula cannot be the final chrome/canvas/card authority.
- The Desktop synchronization controller already observes remote state before its normal decision path and re-observes after push. The reported Desktop `Needs attention` root cause is therefore unproven until structured runtime diagnostics identify the first failing boundary.
- Current responsive behavior is split across shared components, `app.tsx`, `planner-header.tsx` and a large media-query CSS owner. v1.1.2 replaces that mixed ownership with the binding desktop/narrow composition contract in [v1.1.2 responsive presentation architecture](v1.1.2-responsive-presentation-architecture.md).

## JIG-112-SD-01 — explicit per-theme chrome / canvas / card roles

The public product aliases remain:

- `--jig-chrome-surface`;
- `--jig-planner-surface`;
- `--jig-task-surface`.

The values are **explicit theme-authoring inputs**, not values produced by one universal formula.

Each of Jig's 13 authored theme sources supplies one Light/Dark surface-role triad through the typed theme-authoring path. A shared helper may enforce the shape, but it must receive explicit role values from each theme; it must not infer all three roles from `--color-background-body`, `--color-background-surface`, `--color-background-card` using one fixed mix.

Theme investigation/authoring rules:

- the default Jig theme selects roles from Jig's own paper/ink palette;
- Astryx-derived wrappers select reviewed stops/semantic roles from that theme family, including additional theme-local stops when upstream body/surface/card aliases would collapse a role;
- community themes may reuse their explicit body/surface/card palette roles only when the rendered triad passes the same separation review;
- where a community palette has only two adequately separated source surfaces, define one explicit theme-local mix/value in the theme source rather than adding feature CSS;
- feature CSS never branches on theme name and never contains theme-specific literals;
- generated CSS/built themes remain Astryx CLI output and are never hand-edited.

Certification renders every 13 × 2 combination and records the computed three fills. An automated perceptual-distance floor prevents accidental equality/near-equality, while reviewed browser evidence remains the authority for whether the hierarchy reads correctly.

## JIG-112-SD-02 — AppShell main is the single viewport and scroll owner

Retain Astryx `AppShell height="fill"`; do not add another `100dvh` owner.

The configured presentation under AppShell main uses one fill chain:

1. AppShell root owns `100dvh`;
2. AppShell main/`LayoutContent` owns application scrolling;
3. the configured presentation wrapper has `min-block-size: 100%`, `display: flex`, `flex-direction: column` and `min-height: 0`;
4. viewport-specific feedback regions occupy only their required block size/overlay layer;
5. the destination content region is the remaining flexible region (`flex: 1 1 auto; min-height: 0`);
6. Planner surface fills that region when its own content is short.

The current configured `.jig-content-frame` must not remain a nested `overflow:auto` application scroller. Shared secondary screens may constrain their content measure, but they do not create a second page scroll owner.

Narrow/mobile reserves persistent bottom-navigation and safe-area space inside `NarrowConfiguredApplication`; desktop has no bottom reservation.

Browser acceptance must prove one scrolling element for configured application content, full-height empty/short Planner paint, normal overflowing Planner scrolling and preserved sticky/fixed narrow chrome.

## JIG-112-SD-03 — dnd-kit mechanics with React-owned live placement

Retain the pinned dnd-kit packages. Do **not** add a second drag framework.

Replace the current raw `useDraggable` + N+1 `TaskInsertionSlot` protocol with dnd-kit sortable/group mechanics, but **keep dnd-kit's optimistic DOM sorting disabled**.

Required architecture:

- every outstanding Task is one `useSortable` entity;
- date is the sortable group/container;
- each date list remains a valid droppable group even when empty;
- `onDragOver` calls `event.preventDefault()` so dnd-kit does not mutate the DOM behind React;
- one small strictly typed interaction state records only the active Task and current prospective `destinationDate` / `destinationIndex`; it is ephemeral UI state, not canonical Task state, not a transport DTO and not a second durable ordering model;
- each desktop/narrow Planner presenter derives its visible Task sequences from canonical Tasks plus that one prospective placement;
- when the prospective placement changes, React removes the active Task footprint from its prior projected location and inserts a **card-sized footprint** at the new location, causing surrounding cards to reflow through the existing public animated-layout path;
- there is no insertion line and no N+1 insertion-slot component family;
- one `DragOverlay` renders the shared Task-card presentation with interaction disabled, preserving title, metadata, priority, reminder/recurrence presentation, theme, dimensions and typography rather than a hand-built fake checkbox/menu card;
- the old source position must not remain as a misleading faded duplicate after the projected placement moves;
- on successful drag end, submit exactly one existing canonical move command using the last visible prospective date/index;
- on cancel, invalid release, pointer cancel, interruption or failed move, clear the prospective placement and restore the canonical projection;
- canonical Task state is never mutated on drag-over.

The source Task's measured block size may be retained for the projected footprint so variable-height cards do not collapse to a generic slot height. Destination width remains owned by the destination list geometry.

This design intentionally reuses dnd-kit collision/sensor/sortable metadata while rejecting its default DOM-reordering mechanism that previously conflicted with React.

## JIG-112-SD-04 — pointer-specific activation and mobile drag arbitration

Use the existing dnd-kit pointer/keyboard sensor system with pointer-type-specific activation:

- mouse/pen: short distance threshold;
- touch: deliberate delay approximately 200–300ms with small movement tolerance.

Only the dedicated grip binds the drag activator. Interactive descendants carry the existing Jig exclusion marker and never activate drag.

Touch behavior must preserve ordinary vertical Planner scrolling until the hold activates. After activation, dnd-kit auto-scroll is enabled/verified for long lists and cross-date movement. The narrow Planner geometry supplies the scrollable destination lists; no Android-specific drag engine is introduced.

Preserve KeyboardSensor and existing non-drag Move up/down and Date-edit alternatives.

All terminal paths clear overlay/prospective state on drag end, cancellation, pointer cancellation and interruption.

## JIG-112-SD-05 — synchronization phase and failure reason are separate evidence axes

The synchronization controller owns a small strict operational diagnostic state alongside the existing coarse user-level status. It is not Task/domain state and is never persisted into portable records.

Minimum **phase** set:

- `idle`;
- `local-reconcile`;
- `observe-remote`;
- `classify`;
- `adopt-remote`;
- `export-local`;
- `push`;
- `verify-remote`;
- `recover-divergence`.

Minimum **failure reason** set:

- `local-export-failed`;
- `transport`;
- `authentication`;
- `remote-ambiguous`;
- `remote-absent-after-sync`;
- `remote-rewritten`;
- `diverged`;
- `ancestry-unknown`;
- `invalid-snapshot`;
- `dataset-mismatch`;
- `semantic-conflict`;
- `ref-race`;
- `unknown`.

The reason is nullable when a phase is healthy/in progress. Do not encode phases such as `local-export` as failure reasons.

The shell/native adapters capture sanitized command/adapter summaries at the boundary where they occur. Sanitization removes credentials, URL userinfo, query/fragment, authorization headers and provider secrets and never includes canonical Task content.

`Diagnostics` exposes phase, reason, retry facts, abbreviated heads/lineage and recovery outcome plus a stable plain-text Copy diagnostics projection. Primary header and Data & sync copy remain concise.

### Desktop root-cause evidence gate

Before changing the ordinary Desktop synchronization decision policy to fix the reported `Needs attention` defect, reproduce it with this evidence and identify the **first** incorrect phase/result. Current observe-before-write and post-push re-observation behavior must be preserved unless evidence identifies a concrete defect in those paths.

Bounded divergence recovery under SD-06 is independently authorized continuity behavior; it is not evidence of the reported root cause.

## JIG-112-SD-06 — isolated, validated and resumable three-way recovery

For a `diverged` Jig-owned `jig-data` state:

1. prove exact local and remote heads and one common ancestor;
2. read and validate ancestor, local and remote portable snapshots against the configured dataset;
3. create the merge result as an isolated candidate commit while the authoritative local `jig-data` ref remains unchanged;
4. keep the candidate reachable only through adapter-private temporary recovery mechanics until acceptance completes;
5. if content merge reports conflict, discard the candidate and retain both authoritative heads;
6. validate the complete candidate through canonical portable, Task/planning and recurrence validators;
7. re-check the expected SQLite revision and expected local `jig-data` head before acceptance so a concurrent mutation/ref change cannot be overwritten;
8. adopt the validated candidate through the existing revision-guarded canonical snapshot path, recording enough existing/recovery metadata to finish an interrupted acceptance without guessing;
9. atomically advance the authoritative local `jig-data` ref from the exact expected local head to the candidate; if the process stops between canonical adoption and ref alignment, the next synchronization run must prove the candidate snapshot/head and resume that alignment rather than creating another candidate;
10. mark the accepted head exported and remove the temporary recovery reference/mechanism only after canonical SQLite and local `jig-data` agree;
11. push with ordinary non-force semantics;
12. re-observe and mark synchronized only after the remote exposes the accepted result.

If candidate construction/validation fails, no authoritative local ref or canonical SQLite state changes.

The interrupted-recovery path must be tested explicitly. A crash at every acceptance boundary must converge either to the pre-recovery state or the fully accepted candidate; it may not leave an unclassified mixed authority that requires destructive repair.

Linux/system Git and Android/isomorphic-git may use different imperative mechanics, but both implement this shared effect contract. Platform mechanics remain below the synchronization policy and never become application/domain state.

## JIG-112-SD-07 — auto-recoverable lifecycle matrix

- **transport retry:** no Git-history mutation; bounded backoff.
- **credential refresh:** provider transport owner refreshes, then synchronization re-observes.
- **push rejected:** re-observe; never blindly retry stale push.
- **ambiguous push:** remote contains local head => synchronized; otherwise reclassify from the new observation.
- **remote ahead + local clean:** validate and adopt.
- **local ahead:** ordinary non-force push.
- **related divergence:** one SD-06 recovery attempt.
- **internal worktree stale/interrupted:** rebuild/realign Jig-owned worktree only when durable SQLite/ref evidence proves the target.
- **remote rewrite/deletion, dataset mismatch, unsafe snapshot, ambiguous remote, unresolved merge or unknown ancestry:** terminal attention with diagnostics.

No force push is authorized.

## JIG-112-SD-08 — corrective acceptance

Add browser/unit/integration/architecture coverage that proves the functional audit.

Drag acceptance must observe intermediate React-owned card placement before release and persisted final order after release. It must include at least 20 sequential same-date/cross-date cycles, variable-height cards, empty dates, scrolling/auto-scroll, cancellation/interruption and a browser runtime-error trap. Any React/DOM reconciliation exception, stranded overlay/footprint or mismatch between last visible placement and persisted date/index fails the candidate.

Synchronization tests must prove:

- phase/reason evidence for each failure family;
- the diagnosed ordinary Desktop defect and its causal correction once reproduced;
- safe recovery acceptance;
- crash/interruption recovery at each SD-06 acceptance boundary;
- every unsafe condition preserves authoritative local/remote data and yields an actionable diagnostic reason;
- unrelated repository history is untouched.

Theme and responsive acceptance is further specified in SD-11/SD-12 and the binding responsive matrix.

## JIG-112-SD-09 — one public motion-token scale

Define one shared `jigMotionTokens` core-token override and apply it to every one of Jig's 13 theme sources through Astryx's public theme-token API.

Initial values are exactly 2× the prior common Astryx defaults:

- `--duration-fast-min: 190ms`
- `--duration-fast: 250ms`
- `--duration-fast-max: 330ms`
- `--duration-medium-min: 450ms`
- `--duration-medium: 600ms`
- `--duration-medium-max: 800ms`
- `--duration-slow-min: 1050ms`
- `--duration-slow: 1400ms`
- `--duration-slow-max: 1870ms`

Y2K's current source tempo is faster than the common baseline; v1.1.2 intentionally normalizes all Jig theme presets to the governed Jig motion scale so presentation tempo does not change when the user changes Theme.

Do not modify private Astryx variables such as `--_astryx-motion-tempo` or generated theme CSS by hand.

Because Astryx components consume the same public duration tokens, Drawer/BottomSheet/Menu/Dialog and animated-layout behavior inherit the same Jig tempo instead of diverging from Jig-authored CSS.

Remove hard-coded animation completion clocks where they duplicate CSS duration. In particular, success-confirmation dismissal completes from the actual animation event (or one shared typed motion constant only if the primitive cannot expose completion), not the current separate 175ms literal.

Reduced-motion CSS remains an explicit override to no/reduced motion.

## JIG-112-SD-10 — one feedback state owner, two placement owners

Operation confirmation/error/synchronization attention state remains singular above the responsive branch.

Presentation is split:

- `DesktopFeedbackRegion` owns compact top-end placement for transient success and the bounded desktop durable-attention region;
- `NarrowFeedbackRegion` owns safe-area-aware snackbar placement for transient success and inline/inset durable attention below narrow sticky chrome.

Shared feedback-content leaves own message/icon/action/dismiss anatomy and accessibility semantics only; they do not own viewport placement.

The current unconditional placement of `JigSuccessConfirmation` and durable banners directly under AppShell topNav is superseded.

Do not create desktop/mobile message models, separate dismissal state or an Android-native feedback subsystem.

## JIG-112-SD-11 — responsive placement registry and architecture enforcement

[The v1.1.2 responsive interaction matrix](../design/v1.1.2-responsive-interaction-matrix.md) is the binding placement/ownership registry.

Architecture/browser tests must ensure:

- only one `DesktopConfiguredApplication` or `NarrowConfiguredApplication` tree is mounted at the 73rem semantic boundary;
- desktop-only components never render in narrow mode;
- narrow-only fixed/floating controls never render in desktop mode;
- desktop header/nav/Add/status, narrow app-row/temporal-row/bottom-nav/FAB, Drawer/BottomSheet, desktop/narrow feedback regions, Planner compositions and onboarding compositions remain distinct owners;
- shared adaptive History/Settings/Diagnostics/Task semantic leaves do not acquire duplicate state/data projections;
- shared components do not import desktop/narrow presentation components;
- desktop and narrow presentation folders do not cross-import each other;
- material hierarchy changes are not implemented by rendering both structures and hiding/reordering them with CSS;
- one AppShell main remains the scrolling authority in both modes.

Every new v1.1.2 UI surface must be classified in the matrix before implementation.

## JIG-112-SD-12 — motion/theme/responsive browser acceptance

Browser acceptance measures computed duration/surface tokens and representative rendered transitions rather than checking CSS class presence.

At minimum verify:

- every 13 × 2 theme combination has three distinct rendered product surface roles and passes reviewed visual hierarchy;
- public duration tokens equal or exceed the governed Jig scale;
- destination transition, success feedback, attention feedback and Task-card displacement remain perceptible;
- Drawer and BottomSheet inherit the same Jig motion scale while retaining distinct placement;
- reduced-motion disables/reduces governed animation immediately;
- no application-owned normal transition/animation retains a legacy hard-coded sub-190ms duration;
- desktop and narrow screenshots/geometry prove the matrix-declared placement rather than merely the presence of equivalent labels.

## JIG-112-SD-13 — branch composition, share semantics

The binding [responsive presentation architecture](v1.1.2-responsive-presentation-architecture.md) governs all v1.1.2 UI extraction.

At the 73rem semantic layout boundary:

- application/controller state remains singular above the branch;
- one `LayoutMode` decision selects exactly one configured presentation tree;
- material hierarchy, primitive, placement, fixed/floating behavior, safe-area ownership or focus/dismiss differences use separate presentation components;
- shared leaves are permitted only where semantic child hierarchy, state ownership, focus/dismiss semantics and interaction ownership remain the same;
- CSS media queries own only pure reflow/density/hit-geometry adjustments inside shared leaves, not semantic hierarchy substitution.

Required distinct composition owners include:

- configured application frame;
- application chrome/navigation;
- Planner board/list composition;
- Task workspace;
- operation feedback;
- onboarding.

Shared semantic/adaptive owners include:

- Task-card content/actions;
- Task editor fields/validation;
- History;
- Settings;
- Diagnostics;
- delete-confirmation semantics;
- Task action-menu semantics;
- theme/appearance controls.

Presentation props consume existing typed application/core state and callbacks directly. Do not introduce desktop/mobile DTOs, mapping layers, duplicate state stores, command models or parallel projections of canonical Tasks.

The detailed placement contract, component topology, CSS ownership and migration order are authoritative in the responsive presentation architecture document.
