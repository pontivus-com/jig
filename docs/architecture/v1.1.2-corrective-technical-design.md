# Jig v1.1.2 corrective technical design

**Status:** BINDING implementation design for JIG-112-FR-01..08.  
**Target release:** 1.1.2.  
**Tracking issue:** #66.

## JIG-112-SD-01 — explicit chrome / canvas / card theme aliases

One typed product-token owner defines the three surface roles. Do not derive all roles from mixes that can collapse when source theme tokens are equal.

The Jig theme and every Astryx/community theme source must compile values for:

- `--jig-chrome-surface`;
- `--jig-planner-surface`;
- `--jig-task-surface`.

Theme certification computes the rendered values in Light and Dark and rejects equality/insufficient perceptual separation between any pair. Generated theme artifacts remain compiler-owned.

## JIG-112-SD-02 — one full-height configured layout chain

The AppShell/content hierarchy establishes one explicit viewport-height chain. The configured content owner consumes the remaining viewport below the header; Planner then uses that available block size rather than relying on an unanchored percentage `min-height`.

Desktop has one scroll owner. Narrow/mobile applies its bottom-navigation/safe-area reservation inside that same ownership model.

## JIG-112-SD-03 — dnd-kit sortable is the drag owner

Retain pinned dnd-kit. Do **not** add a second drag framework.

Replace the current raw `useDraggable` + N+1 `TaskInsertionSlot` protocol with `useSortable` from `@dnd-kit/react/sortable`.

Key behavior:

- every outstanding Task is one sortable entity;
- date is the sortable group;
- dnd-kit's optimistic sorting is allowed to perform transient DOM reordering during the gesture;
- React does not mirror that transient order in canonical Task state on every drag-over;
- one `DragOverlay` renders the same Task-card presentation as the source;
- the source/placeholder occupies card geometry so the visible prospective result is card placement, never a line;
- on successful drag end, derive final group/index from dnd-kit's sortable operation and submit one existing canonical move command;
- on cancel/failure, canonical state is unchanged and the transient sortable state resets;
- use the public sortable type guards; no drag DTO, `any`, double casts or parallel order model.

If useful, add the matching pinned `@dnd-kit/helpers` package only for its typed `move` reconciliation helper. Do not introduce another drag package.

## JIG-112-SD-04 — pointer-specific mobile activation

Use the existing PointerSensor with pointer-type-specific activation:

- mouse/pen: short distance threshold;
- touch: deliberate delay (approximately 200–300 ms) with small movement tolerance.

Only the dedicated grip binds the drag handle on touch. Interactive descendants carry the existing Jig exclusion marker and never activate drag. Preserve KeyboardSensor/non-drag alternatives.

Enable/verify dnd-kit auto-scroll for long lists and cross-date movement. Gesture termination must clear overlay feedback on `dragend`, cancel, pointer cancel and interruption.

## JIG-112-SD-05 — structured synchronization failure evidence

The sync controller owns a small strict discriminated diagnostic state alongside the existing coarse user-level status. It is operational evidence, not Task/domain state and is never persisted into portable records.

Minimum diagnostic classification:

- `local-export`;
- `transport`;
- `authentication`;
- `remote-ambiguous`;
- `remote-absent-after-sync`;
- `remote-rewritten`;
- `diverged`;
- `ancestry-unknown`;
- `invalid-snapshot`;
- `dataset-mismatch`;
- `semantic-conflict`;
- `ref-race`;
- `unknown`.

The shell adapter captures sanitized command/adapter failure summaries at the boundary where they occur. Sanitization removes credentials/userinfo/query/fragment/auth headers and never includes canonical Task content.

`Diagnostics` exposes the current sync evidence plus a stable plain-text copy projection. The primary header/Data & sync copy remains concise.

## JIG-112-SD-06 — isolated three-way recovery transaction

The synchronization decision order remains observe-before-write.

For a diverged `jig-data` state:

1. prove local/remote heads and a common ancestor;
2. read/validate ancestor, local and remote portable snapshots against the configured dataset;
3. create the merge candidate in an isolated/temporary Git operation without first moving the authoritative local ref;
4. if the Git merge reports conflict, abort and retain both heads;
5. validate the complete candidate through the canonical portable + planning + recurrence validators;
6. if semantic validation fails (including duplicate/non-contiguous positions), discard the candidate and report `semantic-conflict`;
7. only after validation, create the Jig-owned merge result with local+remote parentage and atomically advance the local `jig-data` ref;
8. reconcile/adopt the validated candidate into SQLite using the existing revision/stale-revision guard;
9. push with ordinary non-force semantics;
10. re-observe and mark synchronized only after the remote exposes the accepted result.

Linux/system Git and Android/isomorphic-git may use different imperative merge mechanics, but they must satisfy this one shared effect contract. isomorphic-git's merge API supports dry-run/no-update behavior; system Git may use an equivalent temporary-tree/worktree operation. Platform mechanics must not leak into core synchronization policy.

## JIG-112-SD-07 — auto-recoverable lifecycle matrix

- **transport retry:** no Git-history mutation; bounded backoff.
- **credential refresh:** provider transport owner refreshes, then sync re-observes.
- **push rejected:** re-observe; never blindly retry stale push.
- **ambiguous push:** remote contains local head => synchronized; otherwise reclassify.
- **remote ahead + local clean:** adopt.
- **local ahead:** push.
- **related divergence:** one SD-06 recovery attempt.
- **internal worktree stale/interrupted:** rebuild/realign Jig-owned worktree only when durable SQLite/ref evidence proves the target.
- **remote rewrite/deletion, dataset mismatch, unsafe snapshot, ambiguous remote, unresolved merge or unknown ancestry:** terminal attention with diagnostics.

No force push is authorized.

## JIG-112-SD-08 — acceptance

Add browser/unit/integration/architecture coverage that proves the functional audit. A screenshot or presence assertion is insufficient for drag; tests must observe intermediate sortable placement before release and persisted final order after release.

Synchronization tests must prove both the accepted recovery path and that every unsafe condition leaves local/remote authoritative refs unchanged and yields an actionable diagnostic classification.

## JIG-112-SD-09 — one public motion-token scale

Define one shared `jigMotionTokens` core-token override and apply it to every one of Jig's 13 theme sources through Astryx's public theme-token API.

Initial values are exactly 2× the current Astryx defaults:

- `--duration-fast-min: 190ms`
- `--duration-fast: 250ms`
- `--duration-fast-max: 330ms`
- `--duration-medium-min: 450ms`
- `--duration-medium: 600ms`
- `--duration-medium-max: 800ms`
- `--duration-slow-min: 1050ms`
- `--duration-slow: 1400ms`
- `--duration-slow-max: 1870ms`

Do not modify private Astryx variables such as `--_astryx-motion-tempo` or generated theme CSS by hand.

Because Astryx components consume the same public duration tokens, Drawer/BottomSheet/Menu/Dialog and animated-layout behavior inherit the same Jig tempo instead of diverging from Jig-authored CSS.

Remove hard-coded animation completion clocks where they duplicate CSS duration. In particular, success-confirmation dismissal must complete from the actual animation event (or one shared typed motion constant if the primitive cannot expose completion), not a separate 175ms literal.

Reduced-motion CSS remains an explicit override to no/reduced motion.

## JIG-112-SD-10 — responsive feedback owner

Create one semantic operation-feedback state owner with viewport-specific renderers:

- `DesktopFeedbackRegion`: bounded top-end stack for short-lived success confirmation and bounded durable attention;
- `NarrowFeedbackRegion`: safe-area-aware flow/snackbar presentation coordinated with sticky header and bottom navigation.

Do not fork the underlying confirmation/error/synchronization state. Do not create desktop/mobile message models.

The current unconditional placement of `JigSuccessConfirmation` and durable banners directly under AppShell topNav is superseded.

## JIG-112-SD-11 — responsive interaction matrix enforcement

`docs/design/v1.1.2-responsive-interaction-matrix.md` is the presentation ownership registry.

Architecture/browser tests must ensure:
- desktop-only components do not render below the breakpoint;
- narrow-only fixed controls do not render at desktop;
- declared distinct primitives (Drawer vs BottomSheet, desktop header vs narrow header/bottom nav, desktop vs narrow feedback region) remain singular;
- shared adaptive screens (History, Settings, Diagnostics, Task card semantics) do not acquire duplicate state or duplicate data projections.

The matrix is updated whenever v1.1.2 introduces another responsive composition difference.

## JIG-112-SD-12 — motion acceptance

Browser acceptance measures computed duration tokens and representative rendered transitions rather than merely checking CSS class presence.

At minimum verify:
- public duration tokens equal or exceed the 2× baseline;
- destination transition, success feedback, attention feedback and Task-card/sortable displacement remain visible for the governed duration family;
- Drawer and BottomSheet inherit the Jig motion token scale;
- reduced-motion disables/reduces those animations immediately;
- no application-owned transition/animation retains a legacy hard-coded sub-190ms duration.
