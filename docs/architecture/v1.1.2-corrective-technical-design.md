# Jig v1.1.2 corrective technical design

**Status:** BINDING implementation design for JIG-112-FR-01..15; JIG-112-SD-01..17.  
**Target release:** 1.1.2.  
**Tracking issue:** #66.

## Verified investigation baseline

The following repository facts are implementation inputs, not optional interpretations:

- The pinned Astryx `AppShell height="fill"` already establishes a `100dvh` shell and makes its main `LayoutContent` the fill-mode scroll region. The viewport defect is below that boundary: Jig currently adds a second `.jig-content-frame { height: 100%; overflow: auto; }` while feedback and content are sibling children.
- The current drag implementation uses raw `useDraggable`, N+1 insertion-slot droppables, a fading source card and a hand-built simplified overlay. That implementation produces the rejected insertion-line UX.
- Jig v1.0.5 used the same pinned `@dnd-kit/react@0.5.3` / `@dnd-kit/dom@0.5.3` generation and eliminated a React `NotFoundError: removeChild` reconciliation crash by suppressing dnd-kit's optimistic DOM sorting with `event.preventDefault()` during drag-over. v1.1.2 must not re-enable that failure mechanism.
- The 13 theme sources do not share one tonal topology. Several upstream themes intentionally alias body/surface/card or surface/card roles. Therefore one shared `color-mix` formula cannot be the final chrome/canvas/card authority.
- The Desktop synchronization controller already observes remote state before its normal decision path and re-observes after push. The reported Desktop `Needs attention` root cause is therefore unproven until structured runtime diagnostics identify the first failing boundary.
- Current responsive behavior is split across shared components, `app.tsx`, `planner-header.tsx` and a large media-query CSS owner. v1.1.2 replaces that mixed ownership with the binding desktop/narrow composition contract in [v1.1.2 responsive presentation architecture](v1.1.2-responsive-presentation-architecture.md).

## JIG-112-SD-01 — explicit per-theme chrome / canvas / card roles

**Governs:** JIG-112-FR-01 and the theme portion of JIG-112-FR-08.

The public product aliases remain:

- `--jig-chrome-surface`;
- `--jig-planner-surface`;
- `--jig-task-surface`.

The values are **explicit theme-authoring inputs**, not values produced by one universal formula.

Each of Jig's 13 authored theme sources supplies one Light/Dark surface-role triad through the typed theme-authoring path. One shared `jigProductLocalTokens(surfaceRoles: JigSurfaceRoles)` helper enforces the shape and receives the exact role values from each theme source; it does not infer the three roles.

Theme investigation/authoring rules:

- the default Jig theme selects roles from Jig's own paper/ink palette;
- Astryx-derived wrappers select reviewed stops/semantic roles from that theme family, including additional theme-local stops when upstream body/surface/card aliases would collapse a role;
- the six community themes use their exact `palette.body`, `palette.surface` and `palette.card` pairs as fixed by the binding table below;
- where a community palette has only two adequately separated source surfaces, define one explicit theme-local mix/value in the theme source rather than adding feature CSS;
- feature CSS never branches on theme name and never contains theme-specific literals;
- generated CSS/built themes remain Astryx CLI output and are never hand-edited.

## JIG-112-SD-02 — AppShell main is the single viewport and scroll owner

**Governs:** JIG-112-FR-02 and the viewport portion of JIG-112-FR-08.

Retain Astryx `AppShell height="fill"`; do not add another `100dvh` owner.

The configured presentation under AppShell main uses one fill chain:

1. AppShell root owns `100dvh`;
2. AppShell main/`LayoutContent` owns application scrolling;
3. the configured presentation wrapper has `min-block-size: 100%`, `display: flex`, `flex-direction: column` and `min-height: 0`;
4. viewport-specific feedback regions occupy only their required block size/overlay layer;
5. the destination content region is the remaining flexible region (`flex: 1 1 auto; min-height: 0`);
6. Planner surface fills that region when its own content is short.

The current configured `.jig-content-frame` must not remain a nested `overflow:auto` application scroller. History and Settings keep the existing centered `min(available width, 50rem)` content measure; Diagnostics remains within Settings. None creates a second page scroll owner.

Narrow/mobile reserves persistent bottom-navigation and safe-area space inside `NarrowConfiguredApplication`; desktop has no bottom reservation.

Browser acceptance must prove one scrolling element for configured application content, full-height empty/short Planner paint, normal overflowing Planner scrolling and preserved sticky/fixed narrow chrome.

## JIG-112-SD-03 — dnd-kit mechanics with React-owned live placement

**Governs:** JIG-112-FR-03 and the live-placement portion of JIG-112-FR-08.

Retain the pinned dnd-kit packages. Do **not** add a second drag framework.

Replace the current raw `useDraggable` + N+1 `TaskInsertionSlot` protocol with dnd-kit sortable/group mechanics, but **keep dnd-kit's optimistic DOM sorting disabled**.

Required architecture:

- every outstanding Task is one `useSortable` entity;
- date is the sortable group/container;
- each date list remains a valid droppable group even when empty;
- `onDragOver` calls `event.preventDefault()` so dnd-kit does not mutate the DOM behind React;
- one small strictly typed interaction state records only the active Task and current prospective `destinationDate` / `destinationIndex`; it is ephemeral UI state, not canonical Task state, not a transport DTO and not a second durable ordering model;
- each desktop/narrow Planner presenter derives its visible Task sequences from canonical Tasks plus that one prospective placement;
- when the prospective placement changes, React removes the active Task footprint from its prior projected location and inserts a **card-sized footprint** at the new location, causing surrounding cards to reflow through the existing public animated-layout path;
- there is no insertion line and no N+1 insertion-slot component family;
- one `DragOverlay` renders the shared Task-card presentation with interaction disabled, preserving title, metadata, priority, reminder/recurrence presentation, theme, dimensions and typography rather than a hand-built fake checkbox/menu card;
- the old source position must not remain as a misleading faded duplicate after the projected placement moves;
- on successful drag end, submit exactly one existing canonical move command using the last visible prospective date/index;
- on cancel, invalid release, pointer cancel, interruption or failed move, clear the prospective placement and restore the canonical projection;
- canonical Task state is never mutated on drag-over.

The drag owner measures the active Task card's border-box block size once at drag start and stores that pixel value as ephemeral drag measurement state. The projected footprint uses exactly that measured block size until the gesture ends; it is cleared on every terminal path. Destination inline size always comes from the destination list and is never copied from the source column.

This design intentionally reuses dnd-kit collision/sensor/sortable metadata while rejecting its default DOM-reordering mechanism that previously conflicted with React.

## JIG-112-SD-04 — pointer-specific activation and mobile drag arbitration

**Governs:** JIG-112-FR-04 and the touch/input portion of JIG-112-FR-08.

Use the existing dnd-kit pointer/keyboard sensor system with pointer-type-specific activation:

- mouse/pen: exactly **6 CSS px movement threshold**;
- touch: exactly **250ms activation delay** with **8 CSS px movement tolerance** before activation.

Only the dedicated grip binds the drag activator. Interactive descendants carry the existing Jig exclusion marker and never activate drag.

Touch behavior must preserve ordinary vertical Planner scrolling until the hold activates. After activation, dnd-kit auto-scroll is enabled/verified for long lists and cross-date movement. The narrow Planner geometry supplies the scrollable destination lists; no Android-specific drag engine is introduced.

Preserve KeyboardSensor and existing non-drag Move up/down and Date-edit alternatives.

All terminal paths clear overlay/prospective state on drag end, cancellation, pointer cancellation and interruption.

## JIG-112-SD-05 — synchronization phase and failure reason are separate evidence axes

**Governs:** JIG-112-FR-05, the evidence/root-cause portion of JIG-112-FR-06, and synchronization evidence under JIG-112-FR-08.

The synchronization controller owns a small strict operational diagnostic state alongside the existing coarse user-level status. It is not Task/domain state and is never persisted into portable records.

Minimum **phase** set:

- `idle`;
- `local-reconcile`;
- `observe-remote`;
- `classify`;
- `adopt-remote`;
- `export-local`;
- `push`;
- `verify-remote`;
- `recover-divergence`;
- `resolve-conflict`.

Minimum **failure reason** set:

- `local-export-failed`;
- `transport`;
- `authentication`;
- `remote-ambiguous`;
- `remote-absent-after-sync`;
- `remote-rewritten`;
- `diverged`;
- `ancestry-unknown`;
- `invalid-snapshot`;
- `dataset-mismatch`;
- `semantic-conflict`;
- `ref-race`;
- `unknown`.

The reason is nullable when a phase is healthy/in progress. Do not encode phases such as `local-export` as failure reasons.

The shell/native adapters capture sanitized command/adapter summaries at the boundary where they occur. Sanitization removes credentials, URL userinfo, query/fragment, authorization headers and provider secrets and never includes canonical Task content.

The synchronization diagnostic contract is exactly:

```ts
type SynchronizationDiagnosticPhase =
  | "idle"
  | "local-reconcile"
  | "observe-remote"
  | "classify"
  | "adopt-remote"
  | "export-local"
  | "push"
  | "verify-remote"
  | "recover-divergence"
  | "resolve-conflict";

type SynchronizationFailureReason =
  | "local-export-failed"
  | "transport"
  | "authentication"
  | "remote-ambiguous"
  | "remote-absent-after-sync"
  | "remote-rewritten"
  | "diverged"
  | "ancestry-unknown"
  | "invalid-snapshot"
  | "dataset-mismatch"
  | "semantic-conflict"
  | "ref-race"
  | "unknown";

type SynchronizationRecoveryOutcome =
  | "accepted"
  | "refused"
  | "resumed"
  | "failed";

interface SynchronizationDiagnostics {
  readonly phase: SynchronizationDiagnosticPhase;
  readonly reason: SynchronizationFailureReason | null;
  readonly retryable: boolean | null;
  readonly attempt_count: number;
  readonly last_attempt_at: string | null;
  readonly next_retry_at: string | null;
  readonly local_head: string | null;
  readonly remote_head: string | null;
  readonly last_adopted_head: string | null;
  readonly lineage: SynchronizationLineage | null;
  readonly remote_name: string | null;
  readonly remote_location: string | null;
  readonly recovery_attempted: boolean;
  readonly recovery_outcome: SynchronizationRecoveryOutcome | null;
  readonly error_summary: string | null;
}
```

The existing top-level `Diagnostics` interface keeps its current service/database/repository fields and adds exactly one property:

```ts
readonly synchronization: SynchronizationDiagnostics;
```

No synchronization diagnostic fields are duplicated at the top level.

Contract rules:

- `attempt_count=0` outside a failing/retrying cycle; the first failed attempt is 1 and later retries increment it;
- `last_attempt_at` and `next_retry_at` are UTC ISO instants or null; `next_retry_at` is derived from the exact existing retry schedule `5, 10, 20, 40, 80, 160, 300` seconds;
- non-null heads are exactly the first **12 lowercase hexadecimal characters** of the full object id;
- `lineage` uses the existing `SynchronizationLineage` union;
- `remote_location` is produced by the existing credential-removing remote-location sanitizer and contains no userinfo/query/fragment;
- `recovery_attempted=false` requires `recovery_outcome=null`; `recovery_attempted=true` with `recovery_outcome=null` means the recovery attempt is still in progress or its accepted local candidate is awaiting remote verification;
- `accepted` means a newly built candidate completed local acceptance **and** remote verification;
- `resumed` means an interrupted already-accepted candidate was proved, completed, and remote verification then succeeded;
- `refused` means recovery was considered/attempted but the governing safe-recovery predicate or semantic merge rejected it; `reason` carries the exact refusal reason;
- `failed` is reserved for an adapter/internal failure while attempting recovery; `reason` is the classified adapter failure or `unknown`;
- `error_summary` is null when no failure exists.

The stable **Copy diagnostics** projection emits these fields in the interface order above as `name: value` lines, writes null as `-`, writes booleans as `true|false`, and emits no additional free-form fields. Primary header and Data & sync copy remain concise.

## JIG-112-SD-06 — isolated, validated and resumable three-way recovery

**Governs:** the related-divergence portion of JIG-112-FR-06, JIG-112-FR-07, and recovery acceptance under JIG-112-FR-08.

### Deterministic reconciliation semantics

Recovery operates on validated parsed canonical records, not an unconstrained Git text merge.

The common ancestor is accepted only when the platform adapter returns **exactly one** merge base for the exact local and remote heads. Zero or more than one merge base is `ancestry-unknown` and is not auto-recovered.

Task identity is Task `id`; recurrence identity is recurrence-series `id`. For each identity, compare the canonical serialized record in ancestor (A), local (L) and remote (R):

1. L == R => take that value, including both-absent;
2. L == A and R != A => take R;
3. R == A and L != A => take L;
4. identity absent in A and present on exactly one side => take the present addition;
5. identity absent in A and present identically on both sides => take the identical addition;
6. identity present in A and absent on one side while the other side still equals A => take deletion;
7. every other case is `semantic-conflict`: different concurrent modifications, modify-versus-delete, or different same-ID concurrent additions.

Record equality is equality of the canonical record serialization, including `position`, recurrence links and timestamps. There is deliberately no field-by-field merge and no last-writer-wins rule.

After Task and recurrence record selection, create the candidate only by calling the current canonical `serializeSnapshot` path with the configured dataset id. The resulting current portable format is then revalidated with `validateSnapshot`, `assertTaskSet` and `assertRecurrenceState`. If individually valid inputs combine into non-contiguous ordering, duplicate recurrence slots, dangling recurrence links or another canonical-state violation, classify `semantic-conflict` and do not modify authoritative state. Invalid input snapshots are `invalid-snapshot`; mismatched dataset is `dataset-mismatch`.

### Deterministic candidate commit and private recovery ref

The private ref is exactly `refs/jig/recovery/<dataset-id>`, where `<dataset-id>` is the existing canonical UUID already validated by `assertUuid`; use the persisted hyphenated UUID text verbatim, preserving its case. No escaping, hashing or alternate ref naming is introduced.

The candidate commit is deterministic for a given pair of heads and merged snapshot:

- tree contains only canonical `format.json`, `tasks/*.json` and `recurrences/*.json`, with normal file mode `100644`;
- parents are the two exact pre-recovery heads sorted lexicographically by full object id, so local/remote role reversal cannot change parent order;
- author and committer are exactly `Jig <jig@local.invalid>`;
- author and committer timestamp are exactly one second after the greater committer timestamp of the two parent commits, with UTC offset `+0000`;
- commit message is exactly `Reconcile Jig data`.

Linux constructs the commit without checking out or moving `refs/heads/jig-data`; Android does the equivalent through isomorphic-git object/ref APIs. Both write/update only the private recovery ref until acceptance.

Because the candidate object is deterministic, two supported Jig installations reconciling the same two heads produce the same candidate object id rather than sibling merge commits.

### Acceptance metadata and resume contract

v1.1.2 does **not** add synchronization tables or metadata columns.

The existing metadata is sufficient and is mandatory:

- revision-guarded `adoptCanonicalSnapshot(..., candidateHead, expectedRevision)` records `last_adopted_head = candidateHead` and leaves `pending_sync = 1`;
- the private recovery ref keeps the candidate reachable;
- authoritative local-ref advancement is compare-and-set from the exact expected local head to candidate;
- Linux uses `git update-ref <jig-data> <candidate> <expected-local>`;
- Android performs the equivalent under the single in-process synchronization writer: resolve the current app-private `jig-data` ref, require exact equality with expected local head, then write the candidate ref; mismatch is `ref-race` and triggers re-observation.

On restart:

- private recovery ref exists but `last_adopted_head != candidate` => candidate was never accepted; delete the private ref and re-observe;
- `last_adopted_head == candidate`, canonical SQLite serializes byte-identically to candidate, and local head is one candidate parent => advance local head to candidate and continue;
- same facts with local head already candidate => run `markExported` and continue;
- any mismatch => do not guess; retain authoritative state, classify attention, and expose diagnostics.

After `markExported` succeeds, delete the private recovery ref, perform ordinary non-force push, and re-observe.

The execution order is therefore fixed: prove one merge base -> validate three inputs -> apply the canonical-record merge -> serialize/validate candidate -> write deterministic private candidate -> re-check revision/head -> adopt canonical snapshot -> compare-and-set local ref -> mark exported -> delete private ref -> non-force push -> re-observe.
If candidate construction/validation fails, no authoritative local ref or canonical SQLite state changes.

The interrupted-recovery path must be tested explicitly. A crash at every acceptance boundary must converge either to the pre-recovery state or the fully accepted candidate; it may not leave an unclassified mixed authority that requires destructive repair.

After JIG-112-SD-17, Linux implements the contract through the decomposed `src/shell/git/remote.ts`, `portable-store.ts`, `process.ts` and recovery-only `recovery.ts` system-Git effects; Android implements it through the existing `ui/src/native/git.ts` isomorphic-git effects. Those adapters own command/API mechanics only; the merge decision, acceptance ordering, ref names, candidate identity and observable outcomes above are fixed and shared.

## JIG-112-SD-07 — auto-recoverable lifecycle matrix

**Governs:** JIG-112-FR-06, JIG-112-FR-07, and synchronization lifecycle coverage under JIG-112-FR-08.

- **transport retry:** no Git-history mutation; bounded backoff.
- **credential refresh:** provider transport owner refreshes, then synchronization re-observes.
- **push rejected:** re-observe; never blindly retry stale push.
- **ambiguous push:** remote contains local head => synchronized; otherwise reclassify from the new observation.
- **remote ahead + local clean:** validate and adopt.
- **local ahead:** ordinary non-force push.
- **related divergence:** one SD-06 automatic recovery attempt; if and only if it reaches semantic-conflict after the safe-resolution preconditions are proved, expose the SD-16 user-assisted resolver.
- **internal worktree stale/interrupted:** rebuild/realign Jig-owned worktree only when durable SQLite/ref evidence proves the target.
- **remote rewrite/deletion, dataset mismatch, unsafe snapshot, ambiguous remote or unknown ancestry:** terminal attention with diagnostics; no conflict resolver is exposed.

No force push is authorized.

## JIG-112-SD-10 — one feedback state owner, two placement owners

**Governs:** JIG-112-FR-11.

Presentation is split:

- `DesktopFeedbackRegion` owns compact top-end placement for transient success and the bounded desktop durable-attention region;
- `NarrowFeedbackRegion` owns safe-area-aware snackbar placement for transient success and inline/inset durable attention below narrow sticky chrome.

Placement geometry is fixed for v1.1.2:

- `DesktopFeedbackRegion` is a non-scrolling overlay layer anchored to the configured AppShell-main wrapper. ## JIG-112-SD-16 — bounded user-assisted Jig-data conflict resolution

**Governs:** JIG-112-FR-07, JIG-112-FR-08 and JIG-112-FR-15.

### Why this is not a terminal

Android's managed checkout is app-private and its Git implementation is the existing isomorphic-git adapter. v1.1.2 does not add a system Git binary, PTY, command interpreter or broad filesystem access merely to imitate a shell.

The supported expert escape hatch is therefore **read-only technical evidence plus a bounded semantic resolver**, not arbitrary command execution.

### Central FC/IS and DRY ownership

The recovery feature has one policy owner: new pure module `src/core/synchronization-recovery.ts`.

That module is part of the functional core even though it sits beside `portable.ts`: it imports canonical `Task`/`RecurrenceSeries` values and `PortableSnapshot`/portable validation helpers, and imports **no** SQLite, filesystem, Git process/API, HTTP, Capacitor, React or presentation module.

`src/core/synchronization.ts` remains the small ordinary synchronization classifier. It does not acquire record-merge/conflict-resolution responsibilities.

`src/core/synchronization-recovery.ts` is the sole owner of:

- automatic canonical-record three-way selection;
- recurrence connected-component conflict extraction;
- `ReconciliationSide`, `JigDataConflict`, `JigDataConflictCase`, `JigDataConflictChoice`, `JigDataDateOrder` and `JigDataResolution`;
- strict JSON-boundary validators for the conflict case and final resolution;
- applying whole-side conflict choices;
- deriving and validating affected-date order;
- producing the final resolved `PortableSnapshot` through the existing canonical serializer/validators;
- deterministic recovery commit **policy facts**: parent ordering, identity, timestamp and automatic-versus-user-resolved commit message.

The exact pure entry points are:

The imperative shells own effects only:

- `src/shell/sync.ts` and `ui/src/native/sync.ts` gather exact heads/revision/snapshots, call the **same exported pure functions from `src/core/synchronization-recovery.ts`**, and sequence persistence/Git effects; neither shell may reimplement merge selection, conflict grouping, resolution validation, date-order rules or commit-policy calculation;
- Linux `src/shell/git/recovery.ts` plus narrow `remote.ts`/`portable-store.ts` effects, and Android `ui/src/native/git.ts`, prove ancestry/read objects/write the deterministic candidate/CAS refs/push, consuming `RecoveryCommitSpec` rather than independently re-encoding commit policy;
- `src/persistence/synchronization.ts` owns revision-guarded adoption/export bookkeeping;
- Linux HTTP and Android native runtime expose the same central operational types; they do not define parallel request/response models.

There is one presentation-neutral draft owner above the desktop/narrow branch: `ui/src/sync-conflict-state.ts`. It owns only ephemeral `JigDataResolutionDraft` reducer state and converts that draft into the central `JigDataResolution` type. It contains no Git, persistence, dataset, merge or validation policy. Desktop/narrow workspaces receive that same state and callbacks.

This gives a strict dependency direction:

```text
desktop/narrow presenters
        |
ui sync-conflict draft state
        |
configured runtime seam
        |
Linux / Android imperative synchronization shells
        |
src/core/synchronization-recovery.ts  <-- pure policy/validation
        |
canonical Task / recurrence / portable semantics
```

Platform adapters may depend on the pure recovery owner. The pure recovery owner must never depend outward on a platform, persistence or presentation layer.

### Strict typing boundary

No new recovery file may use `any`, a double cast, a non-null assertion or an unchecked JSON assertion.

The Linux HTTP boundary parses resolution JSON as `unknown` and calls `validateJigDataResolution`; the browser `readSynchronizationConflict()` response is parsed as `unknown` and calls `validateOptionalJigDataConflictCase`, which returns `null` only for literal JSON `null` and otherwise delegates to `validateJigDataConflictCase`. The validators:

- require exact object keys and reject extras;
- accept only the `local | remote` discriminant;
- require unique conflict keys;
- require unique date-order dates;
- require unique Task ids within each date order and validate Task ids with the existing UUID rule;
- validate nested canonical Tasks/recurrence series through the existing canonical validators;
- never repair, default or coerce malformed boundary data.

Android calls the same typed functions directly and does not create native-only request/response types.

### Eligibility gate

A resolver case exists only when the current synchronization attempt has already proved all of the following:

1. exact local and remote jig-data heads;
2. exactly one merge base;
3. matching configured dataset identity;
4. valid canonical ancestor, local and remote snapshots;
5. automatic SD-06 record reconciliation stopped specifically with semantic-conflict;
6. the exact local head and SQLite revision used to build the case are still observable.

Every other reason returns no resolver case. In particular ancestry-unknown, dataset-mismatch, invalid-snapshot, remote-rewritten, remote-ambiguous, transport/authentication failure and unknown adapter state remain Diagnostics/Retry/Reconnect states.

### Shared conflict model

Conflict extraction is a pure functional-core operation over the already validated ancestor/local/remote snapshots.

Do not create transport DTO copies of Task or recurrence records. The central operational types use canonical core values directly:

    type ReconciliationSide = "local" | "remote";

    type JigDataConflict =
      | {
          readonly kind: "task";
          readonly task_id: string;
          readonly ancestor: Task | null;
          readonly local: Task | null;
          readonly remote: Task | null;
        }
      | {
          readonly kind: "recurrence-family";
          readonly recurrence_series_ids: readonly string[];
          readonly ancestor: {
            readonly series: readonly RecurrenceSeries[];
            readonly tasks: readonly Task[];
          };
          readonly local: {
            readonly series: readonly RecurrenceSeries[];
            readonly tasks: readonly Task[];
          };
          readonly remote: {
            readonly series: readonly RecurrenceSeries[];
            readonly tasks: readonly Task[];
          };
        };

    interface JigDataConflictCase {
      readonly ancestor_head: string;
      readonly local_head: string;
      readonly remote_head: string;
      readonly expected_revision: number;
      readonly conflicts: readonly JigDataConflict[];
    }

Recurrence-family extraction is exact and handles reassociation across sides:

1. across ancestor/local/remote, build a bipartite graph whose nodes are Task ids and non-null recurrence-series ids;
2. add an edge from a Task id to each recurrence_series_id that the Task carries in any of the three snapshots;
3. any connected component containing at least one recurrence-series id and at least one conflicting Task or conflicting series record becomes one recurrence-family conflict;
4. recurrence_series_ids is the component's distinct series ids sorted lexicographically;
5. each side contains every series record in that id set plus every Task node in the component that exists on that side.

A conflicting Task is standalone only when its graph component contains no recurrence-series id. This prevents a user from resolving a recurrence definition independently from occurrence records and also handles a Task being reassociated from one recurrence series to another on different sides.

Non-conflicting records continue to use the exact automatic SD-06 selection rules.

### User resolution state

Resolver choices are ephemeral application/presentation state owned only by `ui/src/sync-conflict-state.ts` and are never persisted before final confirmation:

    interface JigDataConflictChoice {
      readonly conflict_key: string;
      readonly side: ReconciliationSide;
    }

    interface JigDataDateOrder {
      readonly date: string;
      readonly task_ids: readonly string[];
    }

    interface JigDataResolution {
      readonly ancestor_head: string;
      readonly local_head: string;
      readonly remote_head: string;
      readonly expected_revision: number;
      readonly choices: readonly JigDataConflictChoice[];
      readonly date_orders: readonly JigDataDateOrder[];
    }

    interface JigDataResolutionDraft {
      readonly choices: ReadonlyMap<string, ReconciliationSide>;
      readonly date_orders: ReadonlyMap<string, readonly string[]>;
    }

The choice key is task:<task-id> for a standalone Task conflict. For a recurrence-family conflict it is recurrence:<series-id-1>+<series-id-2>+... using the already lexicographically sorted recurrence_series_ids. Connected components are disjoint, so this key is unique within the case.

For every conflict the user chooses exactly one whole side:

- local means take the complete local record/family, including absence/deletion;
- remote means take the complete remote record/family, including absence/deletion.

There is no field-level merge editor, free-form JSON edit or last-writer-wins shortcut.

### Order-review stage

After all record/family choices exist, build the provisional merged Task set.

The resolver requires explicit date-order review for the union of:

- every scheduled_date appearing in ancestor/local/remote for a standalone conflicting Task;
- every scheduled_date of every Task in a conflicting recurrence family;
- every date whose provisional surviving Task positions are not exactly unique contiguous 0..n-1.

For each required date, build the initial editable sequence deterministically:

1. surviving Tasks present in the local snapshot, in local canonical position order;
2. then surviving Tasks not already present, in remote canonical position order;
3. any remaining surviving Task ids, lexicographically by id.

The user must confirm the order for every required date. Normal Jig Task ordering interaction and Move up/down accessibility controls edit only this draft sequence.

At candidate construction, rewrite only the position fields of surviving Tasks on reviewed dates to exactly 0..n-1 according to the confirmed sequence. No other Task field is synthesized.

### Responsive recovery workspace

`ui/src/sync-conflict-state.ts` owns only the active case reference, current step, side choices, date-order draft, disclosure state and confirmation intent. All reconciliation, completeness checks and candidate validation are delegated to the central pure `src/core/synchronization-recovery.ts` functions; the UI state owner does not implement recovery policy.

Presentation is explicit:

- desktop/expanded: DesktopSyncConflictWorkspace in an Astryx end Drawer with width 40rem, `hasScrim={true}` and modal focus containment; the governed desktop width is therefore `min(40rem, 100dvw)` through Astryx's viewport-aware Drawer behavior;
- narrow: NarrowSyncConflictWorkspace in an Astryx BottomSheet with `height="tall"`, modal scrim/focus containment and the available height above safe areas, keeping the primary action reachable with IME;
- both consume shared SyncConflictContent leaves and the same resolution state/actions.

The workspace contains, in order:

1. heading **Resolve sync conflict**;
2. concise explanation: both installations changed the same planning data; local work is still saved;
3. progress **Conflict N of M**;
4. conflict presentation in planning language;
5. two explicit whole-side choices **This device** and **Remote**; delete-versus-change labels become **Keep deleted** and **Keep changed Task/series** on the relevant side;
6. changed user-visible fields only in the normal comparison view;
7. subsequent affected-date order review;
8. final resolution summary;
9. **Use this resolution** primary action and **Cancel** secondary action.

**Technical details** is collapsed by default and may expose the exact reason, 12-character ancestor/local/remote heads and read-only/copyable canonical JSON for the currently displayed conflict. It never exposes credentials, auth material, unrelated repository data or an editable command surface.

### Astryx, theme and responsive presentation contract

The resolver introduces no parallel component system and no theme-specific styling.

Public primitive ownership is fixed:

- desktop host: Astryx `Drawer` + `Layout`/Layout regions, modal with `hasScrim={true}`;
- narrow host: Astryx `BottomSheet height="tall"` + `Layout`/Layout regions, modal;
- whole-side choice: Astryx `RadioList` + two `RadioListItem` choices whose values are exactly `local` and `remote`; rich labels render the shared comparison content;
- primary/secondary actions and copy actions: Astryx `Button`/`IconButton` as appropriate;
- Technical details disclosure: Astryx `Collapsible`;
- affected-date order: Astryx `List`/`ListItem` composition plus the existing Jig ordering affordance and Move up/down semantics; it does not create a second Task mutation model.

Do not build custom selectable cards, custom radio/focus/pressed state, a parallel modal shell, raw native controls or private Astryx selector overrides.

Resolver CSS follows the v1.1.2 stylesheet split:

- semantic/shared content geometry lives only in `styles/shared.css`;
- Drawer-only spacing/measure lives only in `styles/desktop.css`;
- BottomSheet/touch/safe-area/IME geometry lives only in `styles/narrow.css`;
- Drawer/BottomSheet/RadioList/Collapsible/Button motion remains Astryx-owned and consumes the global v1.1.2 motion tokens; no resolver-local duration is introduced.

All resolver paint uses the active Astryx theme and public semantic/product tokens. There are no raw color literals, theme-name selectors or resolver-specific Light/Dark branches. Modal surfaces are painted by Astryx; Jig-owned comparison/order regions consume public background/border/text/status tokens and, where Task-card visual identity is intentionally reused, the existing `--jig-task-surface` alias rather than a new color role.

Local and Remote are **not** encoded as success/error colors. Selected state is the public RadioList selected/focus state; delete/change meaning is carried by labels and content, not red/green side identity.

The complete resolver states—unselected choice, local selected, remote selected, delete-versus-change, validation-disabled confirmation, order review, Technical details expanded and final summary—must remain legible and semantically distinguishable in every 13 Theme × Light/Dark combination and under reduced motion.

If `LayoutMode` changes while the resolver is open, the same conflict index, choices, date-order drafts and Technical-details disclosure state survive the Drawer↔BottomSheet presenter replacement. Neither presenter owns or resets the draft.

### Runtime ports

The existing configured runtime seam gains exactly two operations on both Linux HTTP and Android native implementations:

    readSynchronizationConflict(): Promise<JigDataConflictCase | null>;

    resolveSynchronizationConflict(
      resolution: JigDataResolution,
    ): Promise<RepositorySynchronizationStatus>;

`JigDataConflictCase`, `JigDataResolution` and their nested choice/order types are the one strict synchronization operational model in the functional core. The Linux HTTP boundary serializes/deserializes those exact types without a second DTO/mapping type; Android passes the same values directly to the native controller. Linux exposes the same semantics through its loopback protocol/handler and Android calls the native controller directly.

### Confirmation and stale-case handling

Before constructing any user-resolved candidate, resolveSynchronizationConflict must re-check:

- current SQLite revision equals expected_revision;
- current local head equals local_head;
- current observed remote head equals remote_head;
- the unique merge base still equals ancestor_head.

Any mismatch rejects the draft without changing SQLite or authoritative refs, re-observes synchronization and tells the UI that synchronization changed while the user was resolving it. The UI discards the stale draft and loads a newly derived case if one remains eligible.

While the resolver is open, automatic synchronization remains quiescent for that controller instance. The modal Astryx Drawer/BottomSheet makes the configured application behind it inert, so Task editing cannot change the frozen case through the same UI. External/rollover changes are still detected by the revision/head re-check rather than silently overwritten.

### Candidate construction and acceptance

Apply the selected whole-record/family choices plus confirmed date orders to the non-conflicting automatic merge result, then run the complete validateSnapshot, assertTaskSet and assertRecurrenceState validation path.

The user cannot confirm a candidate that fails validation.

A confirmed candidate uses the same isolated private ref and SD-06 crash-safe acceptance transaction, with these deterministic commit differences:

- parents remain the two exact pre-recovery heads sorted lexicographically;
- author/committer remain Jig <jig@local.invalid>;
- timestamp remains one second after the greater parent committer timestamp, UTC +0000;
- commit message is exactly **Resolve Jig sync conflict**.

Identical heads plus identical user choices/date orders therefore produce the same candidate object id.

Cancellation or process death before candidate construction changes no authoritative state. Interruption after candidate construction/adoption uses the existing SD-06 private-ref/resume protocol.

### Safety boundary

The resolver may only choose between already validated local/remote canonical Jig records and explicitly reorder surviving Tasks on affected dates.

It must never:

- accept raw Git conflict-marker text;
- execute arbitrary Git/shell commands;
- edit unrelated branches/files/config;
- resolve unknown ancestry or rewritten history by user fiat;
- choose across different dataset identities;
- force push;
- bypass complete candidate validation.

- shared GitHub integration is spread across loose root files `src/github.ts`, `src/github-auth.ts`, `src/github-device-flow.ts`, `src/github-onboarding.ts`, `src/github-reconnect.ts` and `src/github-registration.ts`.
- `src/github.ts` mixes provider model/state transitions with boundary parsers.
- GitHub repository-URL normalization is currently owned by Linux setup code even though Linux and Android/provider mechanics consume the same meaning.
- synchronization scheduling constants are exported from the Git adapter even though polling/debounce/retry scheduling is synchronization-controller policy rather than Git process mechanics.

v1.1.2 resolves this debt as part of the synchronization work. This is an ownership refactor, not permission to add a generic repository/service/integration framework.

### Functional core ownership

`src/core/portable.ts` is the sole portable-format semantic owner. Move the current `src/portable.ts` implementation there without changing the portable format. It owns:

- `PortableSnapshot`;
- canonical Task/recurrence record serialization;
- `serializeSnapshot`;
- `validateSnapshot`;
- `portableSnapshotsEqual`;
- portable-format validation errors/version semantics.

It imports only other `src/core/**` modules and standard language APIs. It imports no persistence, Git, HTTP, filesystem, process, React or platform code.

`src/core/synchronization.ts` remains the ordinary pure synchronization classifier and shared pure synchronization timing policy. Move the cross-platform mutation debounce to this owner as exactly:

```ts
export const SYNCHRONIZATION_MUTATION_DEBOUNCE_MS = 3_000;
```

Linux and Android both consume that constant. Linux-only healthy polling/max-flush/retry scheduling remains in the Linux synchronization shell rather than the Git adapter.

`src/core/synchronization-recovery.ts` is the SD-16 pure recovery/conflict owner already defined by this design. It imports `./portable`, Task/recurrence/core validation and no outward layer.

### Architecture-neutral runtime contract

Move `src/protocol.ts` to `src/protocol/runtime.ts`.

This module owns only the strict architecture-neutral configured-runtime envelopes shared between Linux HTTP and Android/native presentation adapters, including `RepositorySynchronizationStatus`, `CanonicalState`, command results, service status and Diagnostics. It may import canonical core types but contains no I/O, Git mechanics, persistence implementation or presentation state.

Do not create protocol DTO mirrors of Task, recurrence, recovery conflict or recovery resolution types. Where an API transmits those canonical operational types, the protocol boundary validates/serializes those exact types.

### Shared GitHub provider boundary

`src/github/**` is a concrete GitHub provider boundary shared by Linux and Android. It is not functional-core planning state and not a generic integrations framework.

Ownership is exact:

- `model.ts`: GitHub provider value types plus pure Device Flow state transitions and the pure `normalizedGitHubRepository` URL-to-`owner/name` helper moved from `src/shell/setup.ts`;
- `parsing.ts`: all strict `unknown` -> GitHub capability/onboarding/reconnect snapshot parsers currently mixed into `src/github.ts`;
- `auth.ts`: GitHub HTTP protocol operations currently in `src/github-auth.ts`, with injected `GitHubFetch`; no Node/Capacitor/filesystem/Git dependency;
- `device-flow.ts`: shared Device Flow session/wakeup orchestration;
- `onboarding.ts`: shared onboarding orchestration;
- `reconnect.ts`: shared reconnect orchestration;
- `registration.ts`: the governed public GitHub App registration only.

`src/github/**` may depend on sibling GitHub modules, standard Web APIs/types and pure value helpers. It must not import `src/shell/**`, `src/persistence/**`, `ui/**`, Capacitor, system Git, filesystem or SQLite.

Linux-specific GitHub HTTP routing, managed checkout, askpass, Secret Service and system-Git transport remain under `src/shell/**`. Android-specific secure storage, native lifecycle, app-private checkout and isomorphic-git mechanics remain under `ui/src/native/**`.

### Linux system-Git boundary

Delete the monolithic `src/shell/git.ts`. Its responsibilities move exactly as follows.

#### `src/shell/git/process.ts`

Own only system-Git subprocess execution:

- `GitCommandResult`;
- `GitAdapterError`;
- `runGit`;
- a sibling-only `requireGit` helper.

It owns `Bun.spawn`, process timeout/termination and stdout/stderr collection. It owns no repository policy, portable serialization, remote selection or synchronization scheduling.

#### `src/shell/git/repository.ts`

Own repository-local mechanics that are not portable-data or remote-sync policy:

- `GitAdapterConfig`;
- configured repository-path validation;
- `repositoryCommonDir`;
- `ensureJigLocalExclude`;
- Jig managed worktree path derivation needed by sibling Git modules.

It may call `process.ts`; it does not know Task/PortableSnapshot semantics.

#### `src/shell/git/portable-store.ts`

Own the local Linux system-Git representation of canonical portable state:

- `PortableSnapshotCandidate`;
- initial `refs/heads/jig-data` creation/admission;
- legacy empty-bootstrap compatibility;
- managed Jig worktree creation/verification;
- `readSnapshotAtRef`;
- `readCurrentPortableSnapshot`;
- `inspectPortableCandidate`;
- `writeSnapshotToWorktree`;
- canonical snapshot commit;
- `ensurePortableData`;
- `writePortableSnapshot`;
- fast-forward/CAS `alignPortableDataRef`.

It imports `src/core/portable.ts` directly. It never re-exports portable-core symbols.

#### `src/shell/git/remote.ts`

Own remote-selection/observation mechanics:

- `SynchronizationRemote`;
- `SynchronizationAuthority`;
- `PortableRemoteObservation`;
- `RepositorySynchronizationResult`;

- sanitized remote location;

It imports snapshot admission from `portable-store.ts` and process/repository mechanics from sibling modules. It does not own retry/debounce/poll scheduling.

#### `src/shell/git/recovery.ts`

Own only the Linux **imperative Git effects** needed by JIG-112-SD-06/16:

- prove exactly one merge base for exact heads;
- read parent commit timestamps required by `RecoveryCommitSpec`;
- write the already-specified deterministic candidate tree/commit object;
- create/read/delete exact private recovery ref `refs/jig/recovery/<dataset-id>`;
- compare-and-set authoritative local `refs/heads/jig-data`;
- expose only typed evidence/effects consumed by the synchronization shell.

It consumes `RecoveryCommitSpec` from `src/core/synchronization-recovery.ts`; it must not choose parents, merge records, group conflicts, choose timestamps/messages or validate user resolution independently.

There is no `src/shell/git/index.ts` barrel. Consumers import the narrow owning module directly so dependencies remain visible.

### Synchronization-controller ownership

The following values are removed from the Git adapter:

- `SYNC_HEALTHY_POLL_MS`;
- `EXPORT_DEBOUNCE_MS`;
- `EXPORT_MAX_FLUSH_MS`;
- `SYNC_RETRY_SECONDS`;
- `retryDelayMs`.

Ownership after refactor:

- shared `SYNCHRONIZATION_MUTATION_DEBOUNCE_MS = 3_000` lives in `src/core/synchronization.ts` and is consumed by Linux and Android;
- Linux `SYNC_HEALTHY_POLL_MS = 60_000`, `EXPORT_MAX_FLUSH_MS = 15_000`, `SYNC_RETRY_SECONDS = [5,10,20,40,80,160,300]` and the pure Linux retry-delay calculation live beside the Linux scheduler in `src/shell/sync.ts`;
- Android does not import Linux shell scheduling constants.

### Dependency rules

The source graph after migration is binding:

```text
core/**                         no outward dependencies
  ↑
persistence/**                  canonical durability; no Git/process/UI
  ↑
protocol/runtime.ts             shared runtime envelopes only

core/** <----- github/**        GitHub provider protocol/orchestration only
  ↑             ↑
  |             |
shell/**      ui/src/native/**   platform effects
  \             /
   \           /
    configured runtime / UI
```

More precisely:

- `src/core/**` imports only `src/core/**` and standard language APIs;
- `src/persistence/**` may import `src/core/**`, never shell/UI/provider modules;
- `src/github/**` never imports shell, persistence, UI/native or local Git mechanics;
- `src/protocol/runtime.ts` imports types from core and contains no effect implementation;
- `src/shell/git/**` may import core portable/synchronization types and sibling shell Git modules, never UI/native;
- `ui/src/native/**` may import core/persistence/protocol/GitHub shared modules, never `src/shell/**`;
- Linux and Android synchronization shells call the same pure synchronization/recovery owners and differ only in effects.

### Migration and architecture gates

The ownership refactor is behavior-preserving and lands **before** diagnostics/root-cause/recovery behavior changes. Move and split first; then IMP-15..17 modify the new owners.

Permanent tests/static checks reject:

- any remaining loose `src/portable.ts`, `src/protocol.ts`, `src/github.ts`, `src/github-auth.ts`, `src/github-device-flow.ts`, `src/github-onboarding.ts`, `src/github-reconnect.ts`, `src/github-registration.ts` or `src/shell/git.ts`;
- any import of those removed paths;
- a compatibility barrel/re-export that recreates the old ownership surface;
- portable-core symbols re-exported from a shell Git module;
- synchronization scheduler constants/functions exported from `src/shell/git/**`;
- GitHub URL normalization remaining in `src/shell/setup.ts`;
- `src/github/**` importing platform/local-persistence modules;
- `src/core/**` importing GitHub, shell, protocol, persistence or UI modules;
- `ui/src/native/**` importing `src/shell/**`;
- duplicated Linux/Android recovery policy;
- new DTO/service/repository class stacks introduced merely to perform the move.

IMP-14 acceptance requires `typecheck`, unit/repository tests and the exact pre-refactor synchronization/onboarding behavior suite to pass immediately after the structural move, before corrective behavior is layered on top. At that intermediate point every removed legacy owner is gone and every existing responsibility is in its SD-17 owner; `src/shell/git/recovery.ts` remains intentionally absent until IMP-17. Final SD-17 certification in IMP-18 requires IMP-17 to add that recovery-only effect owner.
