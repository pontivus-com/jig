# Jig v1.1 — Android mobile, reminders and repository onboarding functional design

**Status:** DESIGN COMPLETE — amended 2026-11-20 after physical-device acceptance exposed compact-header, Task-card alignment, historical-date feedback and recurring-rollover accumulation defects, after the cross-platform motion inventory was accepted, and after week navigation was re-governed as one desktop+narrow WeekPager. The amendments preserve the existing synchronization, persistence, recurrence and Task-movement ownership model while correcting the affected functional contracts. JIG-110-IMP-23 is reopened for the FR-33/SD-43 WeekPager refactor and exact-head certification; prior raw-pointer/usePanGesture evidence is historical only. SYNC-E1..SYNC-E6 remain the complete v1.1 synchronization edge-case scope.
**Concern:** User-visible behaviour for mobile usability, reminder attention, two-phase setup, repository selection and independent mobile installation.  
**Baseline:** Jig v1.0.6 as released on `master`. This document defines proposed v1.1 behaviour only. Until adopted into the canonical product/requirements set, it does not retroactively change the v1.0.x release contract.

## 1. Purpose

Jig v1.1 extends the local-first planner so the same planning model is practical on a phone and so first-time repository setup no longer requires users to understand installer flags or filesystem placement before the application can open.

The release has eight user-visible goals:

1. make the narrow/mobile application chrome touch-usable and continuously available while scrolling;
2. make reminders dependable enough to be actionable and make missed/past reminder state visible in the plan itself;
3. split application installation from planning-repository configuration so repository onboarding occurs inside Jig;
4. add an independent Android application path that can acquire and synchronize the user's planning repository without exposing mobile filesystem mechanics;
5. replace the imprecise Task-card drag/drop interaction with a visibly targeted reorder/reschedule interaction whose exact insertion result is clear before release;
6. add bounded recurring Tasks so repeated planning intentions and their reminders reappear on exact weekly/monthly patterns without becoming an unlimited schedule;
7. define one restrained, accessible motion language for meaningful interaction feedback on Linux/Desktop and Android/mobile without making motion a second product-state system;
8. make adjacent-week paging one shared Planner interaction on desktop and narrow/mobile, without creating another displayed-week, Task, drag/drop or platform-specific state owner.

The release does **not** change the fundamental product job: Jig schedules attention, not project execution.

### 1.1 Cross-platform interaction principle

Desktop Linux and Android follow the same product-interaction principles. Platform differences may change composition, native permission/consent surfaces and storage/runtime adapters; they do not change which responsibilities belong to the user.

Jig is intentionally minimal and purpose-built. Normal UI must present only:
- a user goal or explicit user choice;
- the product state needed to make that choice;
- progress while Jig performs work on the user's behalf; or
- an actionable exception that Jig cannot resolve without user involvement.

Internal implementation sequences are not user workflows. Authentication polling, provider-access discovery, Git transport, clone/fetch, repository validation, portable-data adoption, SQLite initialization, synchronization scheduling/retry and similar technical phases must be orchestrated automatically unless an external authority requires a real user decision or consent action.

A technical state may be visible in diagnostics when useful, but must not become a sequence of buttons, refresh steps or protocol terminology in the primary experience. In particular, the normal UI must not ask the user to manually advance an internal state machine.

The same rule applies to desktop and Android. Responsive/mobile design may recompose the same product meaning for touch and available space, but must not expose additional technical responsibility merely because a native platform uses different implementation mechanisms.

## 2. Product invariants retained from v1.0.x

The following remain unchanged unless this document explicitly says otherwise:

- one canonical Task model and one planning authority;
- every active Task belongs to a date and an explicit within-day order;
- the same seven dated sections exist on desktop and narrow/mobile;
- SQLite remains the local operational authority;
- deterministic portable Jig records remain the Git synchronization representation;
- Git remains the continuity mechanism between installations;
- unrelated repository content must remain untouched;
- Git history, branches, merge/rebase/conflict handling and reconciliation are not Jig workflows;
- Planner, History and Settings remain the primary destinations;
- Task workspace state remains shared across responsive presentation;
- local/offline planning remains fundamental;
- a missing remote must never make an otherwise valid local repository unusable.

## 3. v1.1 operating environments

### 3.1 Desktop Linux

Desktop Linux remains supported.

The application installation and repository configuration steps become independent:

1. the Jig application/runtime is installed;
2. Jig can open in an unconfigured bootstrap state;
3. the user selects or acquires a planning repository from inside Jig;
4. Jig validates/adopts/initializes the repository;
5. normal Planner operation begins.

An already-configured v1.0.x installation upgrades without being forced through onboarding again.

### 3.2 Native Android

v1.1 introduces an independently installable Android application. iOS is explicitly outside the v1.1 release scope: the product architecture may remain portable enough to support a later Apple release, but v1.1 does not build, certify or distribute an iOS application.

The Android application must:

- present the same canonical Planner/History/Settings product semantics;
- keep its repository and operational database in application-owned storage without requiring the user to understand a filesystem path;
- synchronize the same portable Jig records through Git;
- retain useful local/offline planning when the network is unavailable;
- use the mobile OS for local reminder delivery;
- preserve compatibility with the same planning repository used by desktop Jig.

The initial Android onboarding path is intentionally narrower than desktop: v1.1 mobile acquires a remote GitHub repository into app-owned storage. Importing arbitrary device-local Git worktrees is excluded from the first mobile release.

## 4. Responsive application header

### JIG-110-FR-01 — sticky narrow/mobile header

At narrow/mobile widths, the complete Jig application header remains fixed to the top of the visible application viewport while the Planner, History or Settings content scrolls.

Scrolling must never cause navigation, synchronization status or the current Planner temporal controls to disappear above the viewport.

The sticky region must respect platform safe-area insets where applicable.

### JIG-110-FR-02 — compact destination header with Planner temporal row

The v1.0.x single-row narrow header is superseded.

Every configured mobile destination uses one destination-invariant **application row** with three semantic zones:

- **left:** the canonical Jig home/brand remains present on Planner, History and Settings;
- **center:** the active destination title is visible and centered: **Planner**, **History** or **Settings**;
- **right:** restrained synchronization status.

The destination title must never replace the Jig identity. Planner therefore has an explicit title in the application row rather than relying on temporal controls or bottom-navigation state as its only page identification.

Planner alone adds a second **temporal row** containing Previous week · readable displayed-week range · Next week · Today. History and Settings do not render that row. Planner-only Add remains the one bottom-end FAB above persistent bottom navigation rather than occupying the application row.

Both Planner rows belong to one sticky header region and must not overlap, detach or scroll away. Planner/History/Settings primary navigation remains the persistent bottom navigation from the shared destination owner.

### JIG-110-FR-03 — mobile interaction geometry and navigation-menu usability

Narrow/mobile controls must be deliberately touch usable rather than desktop controls compressed into less space. This is an **application-wide interaction rule**, not a header-only exception.

The governed mobile UX/UI reference at `../design/reference/jig-v1.1-mobile-ux-ui-governed-reference.html` is the binding v1.1 presentation standard for onboarding, the complete Task BottomSheet and directly analogous mobile form surfaces. It governs the visible hierarchy, spacing/density, scrolling/action placement and touch geometry while Astryx remains component implementation authority.

On touch-oriented narrow/mobile presentation:

- every ordinary tappable primary control, icon action, checkbox target, drag grip, task-menu trigger, BottomSheet action, date-level Add action and settings/repeat action has a rendered hit area of at least **48 × 48 CSS px**;
- a smaller icon glyph or text label may sit inside that hit area, but the interactive target itself must not shrink below it;
- adjacent standalone controls must have visible breathing room rather than touching or appearing as one accidental target; use at least **8 CSS px** separation where the controls are not intentionally one segmented/grouped control;
- the mobile application row and Planner temporal row use a **52 CSS px normal-content target** with a **56 CSS px maximum at normal text sizing**, while preserving every 48px interaction target; safe-area inset is additive and accessibility text growth may increase content height rather than clip;
- controls must not overlap, clip, collapse labels or create horizontal overflow at 320, 360, 390 or 414 CSS px;
- normal touch scrolling must remain available on non-control/non-drag surfaces.

Persistent bottom navigation exposes Planner/History/Settings from the one semantic destination owner. Each item retains a >=48px hit target and readable label. **Interactive text uses at least the normal base/body action typography (`font-size-base` equivalent); smaller typography is reserved for non-interactive metadata/help text, not primary button or navigation labels.**

The use of an Astryx `size="sm"` control is not acceptable merely because it fits the header. A small public component variant may be used only when its public typography remains readable and Jig's public semantic composition still meets the rendered touch geometry without private Astryx overrides.

Desktop may remain intentionally denser for precise pointer input, but the same information hierarchy, action meaning and focus/keyboard accessibility remain shared. Do not enlarge desktop merely to mimic phone density.

The former narrow-header `<=56px` acceptance budget remains removed. Acceptance verifies actual rendered hit rectangles, spacing and non-overlap across the complete mobile-reachable UI, not only the header.

### JIG-110-FR-30 — one destination-title owner without replacing Jig identity

The application header is the single destination-title owner for all configured destinations.

- compact/mobile always keeps the canonical Jig identity at left and shows the active destination title centered: **Planner**, **History** or **Settings**;
- compact/mobile does not render a second subtitle line in the application row; explanatory History/Settings subtitles are omitted there to keep chrome compact rather than displacing the Jig identity or increasing header height;
- desktop History and Settings may retain the concise centered title/subtitle composition (**History — Completed work grouped by actual completion date**; **Settings — Repository, synchronization, appearance and diagnostics**) because the 44px desktop center region can accommodate it without changing destination identity;
- History and Settings content surfaces do not render a duplicate page-level title;
- after the header, History begins with its completion groups/empty state and Settings begins with its first settings section.

There is one typed destination definition owner. Do not maintain separate mobile/desktop title maps or replace brand geometry with live destination text.

## 5. Reminder semantics

### JIG-110-FR-04 — reminder-due attention is derived product state

A Task has **reminder-due attention** when all of the following are true:

- the Task is incomplete;
- it has a reminder time;
- its scheduled date is the current local date;
- the reminder time has passed.

This state is derived from canonical Task data and the current local date/time. It is not defined by whether an OS/browser notification was successfully displayed.

A browser/OS delivery failure must therefore never hide the fact that a Task requires attention. If Jig remains open while local time crosses the reminder boundary, the Task must enter reminder-due attention without requiring navigation, reload or another Task mutation.

### JIG-110-FR-05 — past reminders remain visible

Opening or returning to Jig after a reminder time has passed must immediately show the Task as reminder-due.

v1.1 removes the v1.0.x behaviour where a reminder that became due before the current browser session could be silently ignored as a historical reminder.

An outstanding rolled-forward Task preserves its reminder time. If the rolled Task's reminder time is already past on the current local date, it is reminder-due immediately.

### JIG-110-FR-06 — reminder-due card treatment

A reminder-due Task receives a persistent, accessible attention indication in Planner until the condition is resolved.

The indication must:

- be visible without opening the Task;
- use a governed warning/attention semantic rather than impersonating priority, error, selection or drag state;
- include non-colour meaning such as an attention/reminder icon and accessible text;
- remain visible when combined with selection, priority and drag/focus states according to the established state-precedence rules.

The state ends when any of the following occurs:

- the Task is completed;
- the reminder is removed;
- the reminder is changed to a future time;
- the Task is rescheduled such that its reminder is no longer due.

No separate acknowledgement workflow is introduced in v1.1.

### JIG-110-FR-07 — notification delivery is honest

Jig must distinguish **scheduled** notification state from **displayed/delivered** notification state.

A successful future OS scheduling request may be reported as scheduled. Jig must not describe that as delivered/displayed unless the platform API actually provides evidence for that stronger outcome. Permission denied, unsupported delivery, scheduling failure or runtime failure must not be represented as success.

The card-level reminder-due state remains the durable user-visible truth regardless of notification scheduling or delivery.

### JIG-110-FR-08 — mobile reminder delivery

On native Android, a saved future reminder is scheduled with the Android operating system so it can be delivered when Jig is backgrounded or not currently open, subject to OS permission and platform scheduling policy.

Editing, removing, rescheduling or completing the Task must update/cancel the corresponding pending local notification as necessary.

Jig does not introduce a remote push-notification service for v1.1.

### JIG-110-FR-09 — desktop/browser reminder delivery

On the Linux/browser application, reminder delivery must use a browser-supported notification path rather than relying exclusively on the direct `new Notification(...)` constructor that is not portable to mobile browsers.

v1.1 does not require a remote push service. Desktop closed-browser delivery remains outside the requirement unless the chosen local platform adapter can provide it without adding a new service dependency.

## 6. Two-phase application setup

### JIG-110-FR-10 — application can start before repository configuration

A freshly installed Jig application must be able to start before a planning repository has been selected.

An unconfigured installation shows a deliberate onboarding experience rather than a broken Planner, configuration-file error or technical setup utility.

Onboarding is a state of the Jig application, not a separate visual application. From first render on both desktop and Android it uses the governed Jig application frame, theme, brand/header ownership, body geometry, safe-area handling and interaction language. The onboarding body is distinct from Planner/History/Settings and contains only the product orientation, genuine choices, provider handoff, passive progress and bounded recovery needed to establish the planning-data home.

The onboarding presentation must conform to the governed v1.1 mobile/desktop references and follows one observable hierarchy:
1. establish Jig's planning/local-first/continuity value before asking for provider authorization;
2. present only the genuine repository choice available on that platform;
3. expose the minimum provider mechanics required by that chosen path;
4. keep automatic work passive and product-level rather than surfacing Git/protocol phases;
5. transition directly into Planner after successful setup.

Android uses the governed narrow single-column composition. Desktop uses the governed two-region composition: a stable value/context region plus a bounded setup pane containing the active choice/authorization/selection/recovery state. This is a responsive presentation difference only; the setup semantics remain shared.

Planner/History/Settings and Task actions remain unavailable until repository initialization succeeds, but the application must not replace the Jig shell with a standalone setup page while unconfigured. On successful setup there is no completion ceremony or extra Continue action. If the entered Planner has no Tasks in the displayed week, it uses the governed lightweight empty-week activation rather than another onboarding screen; this is a normal Planner projection and does not require persisted onboarding progress.

### JIG-110-FR-11 — configured upgrades bypass onboarding

If a valid existing Jig configuration and planning repository are present, upgrading the application must preserve that configuration and enter the normal Planner without asking the user to reconnect or reselect the repository.

### JIG-110-FR-12 — desktop repository choices

Desktop first-run setup presents two genuine choices with explicit visual priority:

1. primary **Connect GitHub repository**;
2. secondary **Use an existing local repository**.

The governed desktop reference keeps the value/context region stable while the bounded setup pane changes from initial choice to GitHub authorization, repository selection, local-path entry or recovery. The normal in-app flow must not expose installer-oriented `--repo-url` / `--checkout` concepts.

Expert/noninteractive CLI installation inputs remain available for automation and provider-neutral workflows.

## 7. Existing local repository path

### JIG-110-FR-13 — existing local Git repository is sufficient

On desktop, selecting an accessible existing Git worktree root is sufficient to configure Jig.

Jig validates/adopts/initializes its own data there and does not require the repository to have a remote.

### JIG-110-FR-14 — existing repository with remote

If the selected local repository already has a remote, Jig uses the repository's existing Git topology and ordinary system Git authentication.

Jig must not require a separate GitHub login merely because the repository happens to be hosted on GitHub.

If synchronization succeeds, the repository can reach `synchronized`.

If authentication or another Git operation fails, Jig reports the ordinary repository synchronization issue without corrupting local planning data.

### JIG-110-FR-15 — existing repository without remote

If the selected local repository has no remote, setup still succeeds.

The repository operates in the healthy `local-only` state.

Jig does not silently create a remote or force the user through provider authentication.

Adding/changing Git remotes remains ordinary Git configuration outside Jig's required v1.1 workflow.

### JIG-110-FR-16 — provider neutrality of local selection

A selected existing local repository may use GitHub, GitLab, Bitbucket, an enterprise Git server, SSH, HTTPS or another Git-supported transport.

Jig does not infer provider-specific product semantics from an already-configured local repository.

## 8. GitHub acquisition path

### JIG-110-FR-17 — Connect GitHub is one user intent with automatic acquisition

When no suitable local checkout exists, Jig provides a low-friction GitHub connection flow whose primary user intent is **Connect GitHub repository**.

The normal experience is:

1. the user chooses **Connect GitHub repository** once;
2. Jig initiates the governed GitHub authorization/access flow and continues it automatically;
3. GitHub may present provider-owned identity, consent, organization/SSO or repository-access decisions when GitHub requires them;
4. if more than one eligible repository remains and Jig cannot determine the intended planning-data home, Jig presents one repository-selection surface;
5. after that required user choice, Jig automatically acquires, validates, adopts/initializes and opens the Planner.

Jig owns continuation between these points. The normal UI must not require the user to poll, refresh provider state, resume an internal phase, operate installation/access discovery, choose a checkout location, invoke clone/fetch, or separately trigger repository adoption. Buttons such as **Refresh access**, **Grant repository access**, **Manage GitHub access** or other protocol/state-machine controls are not normal Jig workflow. If GitHub requires a provider-owned access change, Jig may route the user to that GitHub-owned surface and must automatically resume discovery when control returns.

During automatic work Jig presents one coherent connecting state in product language. That state may render the governed user-facing variants needed for the actual situation — GitHub device-code authorization, GitHub-owned repository-access handoff, or passive **Getting your plan ready…** progress — without becoming a stepper or exposing internal phases such as polling, installation discovery, acquiring, cloning, validating, adopting or initializing as separate user steps.

Users are not required to create or paste a personal access token, configure SSH keys, copy a clone URL, choose a checkout directory or understand Git/GitHub protocol mechanics in the normal GitHub flow.

### JIG-110-FR-18 — least privilege

The GitHub integration must request no broader repository/account permissions than are required to:

- enumerate/select repositories available to the integration;
- clone/fetch the selected repository;
- commit and push Jig-owned portable records through the existing synchronization design.

The user must be able to restrict the GitHub App installation to selected repositories using GitHub's own authorization surface.

### JIG-110-FR-19 — provider owns authentication policy; Jig owns orchestration

GitHub owns user identity, account authorization, organization policy, SSO policy, repository-access consent and token semantics.

Jig owns the product-level orchestration around those provider decisions: initiating the supported authorization flow, recognizing when provider-owned user action is required, resuming automatically after that action, discovering the repositories available to the authorized integration, securely retaining the resulting credential on the current device and presenting it to the Git transport for the selected repository.

Provider-owned consent is a legitimate user interaction. GitHub protocol progression is not. Jig must not turn token polling, access discovery, credential refresh, installation enumeration or transport retry into separate user responsibilities.

Jig must not implement passwords, SSH key management, personal-access-token creation, organization authorization policy or a general credential manager.

### JIG-110-FR-20 — credentials are not planning data

Provider credentials must never be written into:

- canonical Task data;
- portable Jig records;
- the planning repository;
- a persisted remote URL containing embedded credentials;
- ordinary shareable Jig configuration.

Credentials must use platform-appropriate secure storage and may be removed/re-authorized independently of planning data.

## 9. Repository acquisition and storage

### JIG-110-FR-21 — desktop managed checkout default

For GitHub acquisition on desktop, Jig chooses a deterministic application-managed checkout location by default.

The user is not required to choose a filesystem path.

The normal GitHub onboarding UI does not offer a checkout-path override. Expert users who require a specific filesystem location use the existing local-repository/CLI path rather than adding managed-checkout configuration to Jig.

The managed repository location must not sit inside an application directory that is atomically replaced during Jig upgrades.

### JIG-110-FR-22 — Android checkout is private implementation detail

On native Android, the selected GitHub repository is cloned into Jig-owned application storage.

The normal Android UI does not expose or ask the user to choose the checkout directory.

Removing the application may remove app-owned local checkout/database storage according to platform rules; the remote Git repository remains the portable continuity source.

### JIG-110-FR-23 — acquisition converges to one repository adoption path

Whether the repository arrived through:

- an existing desktop checkout;
- desktop GitHub acquisition; or
- Android GitHub acquisition,

Jig validates/adopts/initializes the resulting repository through the same semantic repository-setup rules.

There is no separate "GitHub Task model", "mobile repository model" or repository migration domain.

## 10. Android continuity

### JIG-110-FR-24 — same portable data contract and cross-installation continuity

Desktop and Android must read/write the same governed portable Jig record format.

A planning repository used on Linux can be acquired on Android and vice versa without an export/import conversion workflow.

After more than one supported Jig installation uses the same planning repository, ordinary alternating use must continue to synchronize automatically in both directions. A valid portable-state advance produced by another supported Jig installation is not, by itself, a repository synchronization fault.

#### Normal synchronization outcomes

| Condition | Required Jig outcome |
|---|---|
| No synchronization remote is configured | Continue as healthy **Local only**. Local SQLite planning and local portable export remain usable. |
| Local and remote portable heads are the same | Report **Up to date** once the current SQLite revision is represented by that head. |
| Only the current installation has advanced | Synchronize automatically through the configured repository. |
| Only another supported Jig installation has advanced | Validate and adopt that newer portable state automatically; no manual Git repair, reconnect or repeat onboarding is required. |

#### Bounded v1.1 synchronization edge-case audit

Only the following edge cases are part of the v1.1 remediation:

| ID | Edge case | Required Jig outcome |
|---|---|---|
| **SYNC-E1** | The current installation has unsynchronized local planning changes and another installation has also advanced the shared repository before those changes were synchronized. | Preserve the current local SQLite planning state and the remote portable state. Report **Needs attention**. Do not create another local Git snapshot on a known-stale base and do not attempt an automatic Task/Git merge. |
| **SYNC-E2** | The remote advances after Jig observed it but before Jig's push completes, so the push is rejected/non-fast-forward. | Re-observe the repository before any further write. Continue automatically only if the newly observed state is again an ordinary fast-forward case; otherwise use SYNC-E1/Needs attention. Do not repeat the stale push in a loop. |
| **SYNC-E3** | A push may have succeeded but the response/connection is lost, so success is ambiguous. | Re-observe the remote before writing again. If the remote already contains the exact local exported head, treat synchronization as successful; otherwise classify the newly observed state normally. |
| **SYNC-E4** | Authentication or transport is temporarily unavailable. | Keep locally accepted planning usable and durable. Retry/reconnect through the existing bounded synchronization outcome model. Connectivity failure must not cause history rewriting or data replacement. |
| **SYNC-E5** | Jig restarts/crashes between SQLite mutation/adoption, local portable Git update and synchronization-status bookkeeping. | Recover from durable SQLite plus the concrete Jig portable Git state. Do not lose accepted planning, overwrite a newer SQLite revision, or create duplicate semantic snapshot history merely to repair bookkeeping. |
| **SYNC-E6** | The configured remote cannot be consumed safely: target selection is ambiguous, the previously synchronized portable history was deleted/rewritten or is otherwise not fast-forward compatible, ancestry cannot be established, or the presented portable snapshot/dataset is invalid or incompatible. | Preserve local planning and observed repository state and report **Needs attention**. Jig must not guess a target, force/recreate history, replace a real dataset identity, or introduce Git merge/rebase/conflict workflow. |

These six cases are the complete v1.1 synchronization edge-case scope. Simultaneous fresh-dataset reconciliation, arbitrary Git corruption repair, multi-remote replication, semantic merging of independently edited Tasks and provider-specific topology management are **not** v1.1 responsibilities.

Routine races and interruptions must not create an endless write/retry loop. A terminal attention state is quiescent: local planning remains usable, no destructive synchronization write repeats while the observed condition is unchanged, and a later synchronization opportunity may resume automatically if the repository again becomes an ordinary fast-forward-compatible state.

Local planning remains usable throughout every condition.

### JIG-110-FR-25 — same planning semantics

Android must not introduce alternative Task semantics, a separate selected-day model, a reduced Task record, or an Android-only lifecycle.

The existing daily rollover rule is part of that shared behaviour: when Android launches/resumes after the local date has advanced, all unfinished earlier-day Tasks must roll into the current local date before the Planner is presented. If Jig remains foregrounded across local midnight, rollover must occur without requiring an application restart.

Responsive/native presentation may differ, but canonical Task/planning behaviour remains shared.

### JIG-110-FR-26 — offline-first mobile edits

After successful initial acquisition, Android planning edits must save locally without requiring network connectivity.

Repository synchronization may become pending/retrying/sync-issue while offline and resume according to the same coarse operational outcome model when connectivity returns.

## 11. Android distribution

### JIG-110-FR-27 — Android development installation and F-Droid-first distribution

v1.1 does not include an Apple/iOS release path.

Android development and product validation must **not** depend on an app-store publication cycle. The development workflow must produce an installable development APK that can be installed directly on a physical Android phone and used to validate the complete mobile experience, including onboarding, Git synchronization, offline operation, reminders, touch interaction and responsive layout.

**F-Droid is the first public Android app-store/repository target for Jig.** The v1.1 Android application and its dependency/build chain must therefore remain compatible with the F-Droid main-repository inclusion model: the application is open source, its Android build is buildable from publicly available source with a FLOSS-compatible toolchain/dependency set, and core product behaviour does not depend on proprietary Google Play services.

Development APKs are sideloaded only for development and certification. v1.1 does not establish a second public Android APK distribution channel alongside F-Droid.

F-Droid is the first public Android distribution target. A Jig v1.1 Android candidate must be F-Droid-submission-ready and the F-Droid submission path must be exercised. External F-Droid review timing does not block local development, physical-device testing or completion of the implementation candidate.

Google Play publication is explicitly deferred to a later Jig version. Later Google Play packaging/publication must not require changing the Android application identity, canonical planning data, repository compatibility, onboarding semantics or core functionality.

## 12. Task-card drag and drop correction

### JIG-110-FR-28 — reliable, precise and recoverable Task movement

The current Pangea-based implementation is rejected by physical-device use: touch drags can leave a card visually suspended while no valid destination is committed, and initiation/destination updates are not reliable enough for a primary Planner interaction. That implementation is defect evidence, not a compatibility target.

A replacement direct-manipulation interaction must make the **exact result of releasing the Task visible before the user drops it** and must satisfy all of the following:

- dragging a Task within a date produces an explicit insertion slot at the exact before/after position where the Task will be placed;
- dragging a Task to another date identifies both the destination date and exact insertion slot;
- the spaces **between** cards are first-class insertion targets rather than incidental whitespace that can clear or oscillate the destination;
- dropping into an empty date has one unambiguous index-0 target;
- the final persisted Task date/order exactly matches the insertion location shown immediately before release;
- canonical Task state/order does not mutate until a successful drop; cancel, pointer cancellation, app/window interruption or outside-drop restores the original arrangement exactly;
- the source Task remains visibly identifiable while dragging and cannot remain stranded in a floating/overlay state after the gesture ends;
- drag targeting remains stable across different card heights, scrolling, long lists and cross-date movement;
- automatic scrolling must allow the user to reach off-screen Tasks/dates without losing the active insertion slot;
- Task-body touch scrolling remains normal; only the dedicated grip initiates movement;
- checkbox, action menu, references, Task open/select and other interactive descendants remain independent of drag.

The dedicated grip is always visible on touch/mobile and follows the FR-03 minimum 48 × 48px interaction target. Desktop keeps a clearly visible pointer/keyboard-operable grip with an appropriately compact pointer target.

A drag/drop library is an implementation detail and is not itself a product requirement. A candidate library must pass a small physical Android + desktop proof **before** it becomes implementation authority. The failed Pangea behavior must be removed rather than layered with a second sensor or workaround stack.

The non-drag alternatives remain authoritative and satisfy the same movement outcome without a dragging gesture:

- same-date **Move up / Move down** actions remain available through the Task action menu;
- editing the Task date remains the explicit non-drag cross-date reschedule path.

The interaction changes only direct manipulation. It does not change canonical Task ordering semantics, persistence or Git representation.

**Past-date movement is an invalid active-scheduling intent.** A Task may be dragged/rescheduled only to the current local civil date or a future date. Past-date insertion targets must communicate that they are unavailable; releasing onto one preserves the Task exactly and produces concise user-visible feedback explaining that outstanding work cannot be scheduled into a past date. Date-field rescheduling uses the same canonical rule and error rather than a separate drag-only policy.

## 13. Recurring Tasks

### JIG-110-FR-29 — bounded recurrence with independent Task occurrences

A Task may optionally repeat, but every recurrence must be finite. Repeat has a required inclusive end date and no "forever" option.

The supported v1.1 patterns are deliberately small:

- **Weekly:** repeat every positive whole number of weeks on one or more selected weekdays. This covers once per week, multiple days in each active week, every day by selecting all seven weekdays, and intervals such as every four weeks.
- **Monthly:** repeat on an exact day of month. If a month does not contain that day, that month has no occurrence; Jig does not silently move the occurrence to month-end.

The Task on which Repeat is first enabled remains the seed occurrence. Further matching dates after the seed, through the inclusive end date, become ordinary canonical Task occurrences. Every occurrence has its own Task identity, date, persisted order, completion state and reminder lifecycle; Planner and History never display virtual recurrence copies.

Occurrence behavior is exact:

- every occurrence is linked to the same recurrence series and opening **any** occurrence exposes that shared Repeat configuration;
- the pattern/end-date configuration has one series owner and must not be copied into each Task as independently editable values;
- completing or reopening one occurrence affects that occurrence only;
- deleting one occurrence does not cancel the series;
- moving or explicitly rescheduling one occurrence does not shift the recurrence cadence;
- ordinary daily rollover remains shared with one-off Tasks, but recurrence has one **non-accumulation exception**: before rollover, Jig identifies the latest outstanding occurrence in each series whose immutable recurrence slot is due on or before the current local date, preserves that occurrence, and supersedes older outstanding occurrences from the same series that are actually overdue (`scheduled_date < today`);
- future occurrences remain anchored to their original recurrence dates and are untouched; an occurrence explicitly moved to a future date is not considered overdue and is preserved as explicit user intent;
- supersession removes the stale outstanding occurrence without marking it completed. It is canonical rollover maintenance, not a third recurrence mutation scope or a new Task status;
- generated occurrences copy the source Task's title, priority, context, reference, note and reminder time only at materialization time. After that, those fields are occurrence-local: editing the title or any other ordinary Task field on one copy never propagates to already-existing siblings. If a later Repeat edit introduces new recurrence slots, only those newly created Tasks copy the invoking occurrence's current fields;
- reminder eligibility/delivery then follows the existing reminder rules for that occurrence's own scheduled date.

### Governing recurrence mutation scopes

v1.1 has exactly two recurrence-related mutation scopes:

- **Occurrence scope** owns ordinary Task content and lifecycle state: title, priority, context, reference, note, reminder, scheduled date, position, completion/reopen and **Delete this Task**. These mutations affect only the invoking Task occurrence.
- **Series scope** owns only the recurrence configuration and series teardown: weekly/monthly pattern, interval/weekday or day-of-month selection, inclusive end date, and **Stop repeating / Remove recurrence**. Because every occurrence resolves the same `RecurrenceSeries`, opening Repeat on any occurrence shows and edits that same shared configuration.

There is deliberately no third scope for "all occurrences", "this and following Task details", template propagation or any equivalent bulk Task-content rewrite in v1.1. Once an occurrence exists, its Task fields remain independent from every sibling.

Changing the **Repeat** setting is therefore a **series-membership reconciliation**, not a Task-content edit. Reconciliation is anchored at the invoking occurrence's immutable recurrence slot:

- preserve the invoking occurrence, every earlier occurrence and every completed occurrence;
- keep a later outstanding occurrence when its immutable recurrence slot remains selected by the updated schedule, preserving its Task ID and all occurrence-local edits;
- remove a later outstanding occurrence only when its immutable slot is no longer selected by the updated schedule;
- create one Task for each newly introduced later slot, copying the invoking occurrence's current Task fields at creation time only;
- update the one shared series configuration in the same user operation;
- never rewrite title, priority, context, reference, note, reminder, scheduled date, position, completion or other Task-local state on any retained sibling.

**Remove recurrence / Stop repeating** is explicitly different from **Delete this Task**. From any recurrence occurrence, Stop repeating retains the invoking Task as a one-off Task, preserves every completed occurrence in History and removes **all other outstanding occurrences in that series** in one canonical mutation, including rolled/overdue siblings. The user must never need to delete the remaining generated cards individually. Delete this Task remains occurrence-only and leaves the recurrence rule and sibling occurrences intact.

The Task workspace exposes **Repeat as an ordinary field in the same Task form**, logically adjacent to Date and Reminder, on creation and on every existing recurrence occurrence. Repeat is not a second editor below the Task form and does not have its own ordinary Save button.

The complete governed form order is **Title → Date → Repeat → Reminder → Priority → Context → Reference → Notes**. Every Repeat state retains that complete form in one scrollable Drawer/BottomSheet; recurrence controls expand in place immediately below Repeat. A recurrence-only form/reference or a form that visually terminates after Repeat is non-conforming.

The Repeat field uses progressive disclosure:

- default/non-recurring state is **Does not repeat** and exposes no recurrence-detail fields;
- choosing **Weekly** reveals only the weekly interval, weekday selection and required inclusive end date;
- choosing **Monthly** reveals only the day-of-month and required inclusive end date;
- changing back to **Does not repeat** hides recurrence details and, for an existing series, clearly communicates the series-level Stop repeating effect before the Task is saved;
- weekday choices and Repeat controls obey the FR-03 touch geometry rather than using cramped small checkboxes on mobile.
- on mobile, weekday choices wrap when needed to preserve the >=48×48px target budget rather than being squeezed into one row;
- existing-series presentation includes concise ownership copy equivalent to **Repeat changes the series schedule. Other Task fields change this Task only.**

The workspace has one primary **Save** gesture for the complete Task draft. On an existing Task, that one user operation applies ordinary occurrence-local edits and any changed series-level Repeat configuration atomically: the two semantic scopes remain distinct in the core, but the user must not complete two separate saves or see a recurrence editor after the Task has already been saved. If any part of that save fails, neither the ordinary Task edits nor the Repeat mutation may be partially committed.

On narrow/mobile, expanding Weekly or Monthly must not make the remainder of the canonical form unreachable: Reminder, Priority, Context, Reference and Notes stay in the same normally scrollable BottomSheet beneath the disclosed Repeat controls, and the action area must not cover required controls, validation or Notes.

A recurring Task/card has a compact accessible repeat indication/summary so recurrence is visible without opening the Task, but recurrence does not become a priority/status color and does not introduce another Planner destination.

## 14. Git authority boundary for v1.1

### JIG-110-FR-31 — Settings presents user-level data-home and synchronization state

The primary Settings synchronization experience must use the user's mental model rather than Git implementation topology.

It must answer, in product language:
1. **where Jig's planning data is connected** — a credential-free, human-readable repository identity when a remote-backed repository exists, or a clear local-only state;
2. **whether the user's current work is safe locally**;
3. **whether remote continuity is up to date, in progress or needs attention**; and
4. **whether any user action is actually required**.

When the current Jig state is durable locally but remote synchronization is pending or failing, the UI must preserve that distinction in user language such as **Saved locally · Sync needs attention**. It must not force the user to understand local Git refs, commit/export phases, remote names or transport mechanics to know whether work is safe.

Automatic synchronization remains the default. A standing primary **Sync now** control is not required merely because a transport operation exists. Retry/reconnect actions appear when they are actionable recovery choices, and a manual synchronization trigger may remain in diagnostics for expert use.

Detailed facts such as local Git snapshot/commit state, configured Git remote name/location, service health, SQLite state and transport diagnostics may remain available in a clearly secondary diagnostics/technical-details surface. They must not define the primary Settings information hierarchy.

Settings is a **reading/configuration hierarchy, not a dashboard of equal cards**. The default Settings body therefore uses full-width semantic groups/rows within the existing bounded reading measure:

1. **Data & sync** — combines planning-data home, local-save safety, remote-continuity state and any actionable retry/reconnect into one coherent group;
2. **Appearance** — Theme and System/Light/Dark only;
3. **Notifications** — permission/scheduling state and its actions; notification configuration is not part of Appearance;
4. **Diagnostics / technical details** — collapsed or otherwise visually subordinate by default, containing repository path, Local Git/Remote Git, service/database state and expert manual sync.

Do not allocate equal-height or equal-width dashboard cards to values whose content is only one or two lines. Section geometry follows content. The user should be able to scan a left-aligned label/value/supporting-text hierarchy without empty card acreage or forcing related continuity facts into separate boxes.

The existing local-first promise belongs as contextual supporting copy inside Data & sync where it helps interpret local safety; it is not a fifth decorative Settings panel.

The compact header synchronization indicator remains one derived user-level summary such as Local only, Syncing, Up to date or Needs attention. It is a pure presentation projection of the same underlying synchronization state rather than an independent status authority.

The v1.0.x Git boundary is retained with one explicit refinement for provider authorization.

**Jig owns:**
- the user's choice of planning-data home;
- requesting acquisition of a chosen remote repository;
- securely presenting an authorized provider credential to the narrow Git transport;
- Jig portable record generation/validation;
- automatic synchronization scheduling and coarse outcome reporting.

**Git/Git provider owns:**
- repository topology;
- branches, refs and upstream semantics;
- clone/fetch/push transport semantics;
- identity and account authorization policy;
- remote history;
- merge/rebase/conflict resolution;
- credential/token semantics and revocation.

Jig must still not become a general repository manager.

## 15. Cross-platform motion, reduced-motion and week-paging contract

### JIG-110-FR-32 — restrained, accessible interaction motion

Jig uses motion only to clarify a meaningful user interaction or a change in an already-visible product state. This contract applies to both the Linux/Desktop browser application and the independently installed Android application. Motion is presentation feedback, never canonical Task/planning state, notification-delivery state, synchronization authority or a prerequisite for completing an operation.

The eligible motion events are:

| Event | Required user-visible motion | Linux/Desktop browser | Android application |
|---|---|---|---|
| Destination navigation | Brief content transition and active-navigation indicator transition | Header navigation; pointer hover/focus may apply | Bottom navigation; touch press/focus may apply |
| Open/close Task workspace and open Add-task workspace | Enter/exit transition for the existing workspace surface | Astryx Drawer from the right | Astryx BottomSheet from the bottom |
| Save, complete/reopen and delete | Loading/state feedback followed by a restrained card insertion, update, completion or removal transition | Existing Planner/History surfaces | Same semantic card transition inside Android WebView without avoidable surrounding layout shift |
| Drag start, valid slot, invalid drop and successful move | Source lift, valid insertion-slot emphasis, existing feedback-owner error emphasis, and short positional settling | Pointer/keyboard drag | Touch grip drag in the Android WebView |
| Previous/Next week and explicit Today | Controlled content transition or an explicit smooth settle to the current day | Week/content transition | Week/content transition or current-day scroll in the WebView |
| Synchronization state change | Small status/icon transition and one-time attention reveal for actionable error | Header/Settings status | Header/Settings status in the WebView/native shell |
| Reminder lifecycle change | Subtle metadata/status transition only | Task card | Task card in the WebView; OS notification delivery remains non-animated Jig-owned state |
| Theme/appearance change and focus/hover/pressed/disabled states | Short semantic color/opacity/elevation transition where stable | Pointer hover/focus/pressed states apply | Touch pressed/focus/disabled states apply; hover is not required |

The following must not receive Jig-owned motion: healthy synchronization loops, reminder Toasts, GitHub/provider protocol choreography, automatic travel on initial Planner load, desktop/mobile composition changes, large page slides between destinations, repeated reminder pulsing, decorative header/logo/bottom-navigation animation, or any transition that hides validation, scheduling rejection or synchronization failure.

Adjacent-week paging itself is governed by JIG-110-FR-33. FR-32 governs only the motion/reduced-motion qualities of that interaction: paging must remain interruptible, canonical state must never depend on animation completion, and reduced motion must remove avoidable programmatic travel without changing the selected week.

Linux/Desktop and Android express the same semantic event even when their Astryx surface, input modality or viewport differs. Allowed platform differences are limited to Drawer versus BottomSheet, header versus bottom navigation, pointer/hover versus touch/pressed feedback, and the corresponding content-scrolling mechanics. They must not change event eligibility, state meaning, timing budget class, interruption behavior, accessibility outcome or mutation semantics. Motion must be short, interruptible and subordinate to content. State changes, focus, accessible names, announcements and recovery remain available immediately; no operation waits for an animation to finish. The initial Android/narrow Planner view lands directly on the current day and does not animate an automatic scroll.

The application respects the user's reduced-motion preference. Reduced motion removes translation, scaling, looping/pulsing and smooth scrolling, and reduces composed transitions to immediate or near-immediate state changes while retaining non-motion status, focus and color-semantic feedback. Jig does not create a second JavaScript motion-preference engine or persist a motion setting in planning data.

### JIG-110-FR-33 — cross-platform paged week navigation

Planner uses one adjacent-week paging interaction on Linux/Desktop and Android/narrow while retaining the same canonical displayed-week state and the existing responsive week composition. Desktop continues to render seven dated columns; narrow/mobile continues to render the same seven dates as vertically stacked sections. Paging changes which complete week is displayed; it does not add a selected-day state, route or second data projection.

Explicit Previous and Next controls and direct horizontal touch/trackpad paging are equivalent inputs to the same presentation owner. One completed adjacent-page movement changes the canonical displayed week by exactly seven civil days and never skips an intermediate week. Today is not an adjacent-page traversal: it directly restores the week containing the current local date, and narrow/mobile then performs the existing current-day vertical positioning inside that week.

The paging surface may render the immediately previous and next weeks to provide direct-manipulation continuity, but those neighbours are visual previews only. The canonical active week is the only interactive Planner workspace and the only source of Task selection, Add/edit/complete/delete actions, drag handles, insertion-slot droppables and keyboard/focus navigation. Adjacent previews are inert/non-focusable and do not create another accessibility tree or Task-movement domain. A Task drag never pages the week, never targets an adjacent preview and cannot mutate displayed-week state.

The interaction must remain one shared implementation across desktop and narrow/mobile. Direct touch/trackpad movement follows the browser/WebView's native horizontal scrolling and snapping behavior; vertical scrolling remains ordinary narrow Planner content scrolling. Mouse/keyboard users retain explicit Previous/Next/Today. Cancellation/interruption leaves one canonical week selected. Breakpoint reflow preserves the same displayed week and does not create another temporal mutation.

The product requirement does not select a gesture recognizer or third-party carousel component. The technical solution must use the narrowest public integration that satisfies these outcomes without private component internals, duplicate semantic owners or platform-specific navigation state.

## 16. Explicit non-goals for v1.1

v1.1 does not add:

- multiple simultaneously active planning repositories;
- an in-app Git branch manager;
- remote creation/provisioning;
- remote editing or arbitrary repository migration;
- merge/rebase/conflict-resolution UI;
- provider-independent account login for every Git host;
- Android adoption of arbitrary external filesystem worktrees;
- push-notification servers;
- reminder acknowledgement/snooze workflows;
- a second Task schema or mobile Task projection;
- project-management functionality;
- iOS application build, certification or App Store distribution in v1.1;
- retaining dnd-kit as the Planner Task-card drag/drop owner;
- bulk propagation of title/details/reminder or other ordinary Task content across existing recurrence occurrences.
