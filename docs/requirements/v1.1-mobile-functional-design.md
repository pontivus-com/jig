# Jig v1.1 — Android mobile, reminders and repository onboarding functional design

**Status:** DESIGN COMPLETE — reviewed and amended 2026-11-18 on branch `v1.1`; bounded Task recurrence is now part of the v1.1 functional contract.  
**Concern:** User-visible behaviour for mobile usability, reminder attention, two-phase setup, repository selection and independent mobile installation.  
**Baseline:** Jig v1.0.6 as released on `master`. This document defines proposed v1.1 behaviour only. Until adopted into the canonical product/requirements set, it does not retroactively change the v1.0.x release contract.

## 1. Purpose

Jig v1.1 extends the local-first planner so the same planning model is practical on a phone and so first-time repository setup no longer requires users to understand installer flags or filesystem placement before the application can open.

The release has six user-visible goals:

1. make the narrow/mobile application chrome touch-usable and continuously available while scrolling;
2. make reminders dependable enough to be actionable and make missed/past reminder state visible in the plan itself;
3. split application installation from planning-repository configuration so repository onboarding occurs inside Jig;
4. add an independent Android application path that can acquire and synchronize the user's planning repository without exposing mobile filesystem mechanics;
5. replace the imprecise Task-card drag/drop interaction with a visibly targeted reorder/reschedule interaction whose exact insertion result is clear before release;
6. add bounded recurring Tasks so repeated planning intentions and their reminders reappear on exact weekly/monthly patterns without becoming an unlimited schedule.

The release does **not** change the fundamental product job: Jig schedules attention, not project execution.

### 1.1 Cross-platform interaction principle

Desktop Linux and Android follow the same product-interaction principles. Platform differences may change composition, native permission/consent surfaces and storage/runtime adapters; they do not change which responsibilities belong to the user.

Jig is intentionally minimal and purpose-built. Normal UI must present only:
- a user goal or explicit user choice;
- the product state needed to make that choice;
- progress while Jig performs work on the user's behalf; or
- an actionable exception that Jig cannot resolve without user involvement.

Internal implementation sequences are not user workflows. Authentication polling, provider-access discovery, Git transport, clone/fetch, repository validation, portable-data adoption, SQLite initialization, synchronization scheduling/retry and similar technical phases must be orchestrated automatically unless an external authority requires a real user decision or consent action.

A technical state may be visible in diagnostics when useful, but must not become a sequence of buttons, refresh steps or protocol terminology in the primary experience. In particular, the normal UI must not ask the user to manually advance an internal state machine.

The same rule applies to desktop and Android. Responsive/mobile design may recompose the same product meaning for touch and available space, but must not expose additional technical responsibility merely because a native platform uses different implementation mechanisms.

## 2. Product invariants retained from v1.0.x

The following remain unchanged unless this document explicitly says otherwise:

- one canonical Task model and one planning authority;
- every active Task belongs to a date and an explicit within-day order;
- the same seven dated sections exist on desktop and narrow/mobile;
- SQLite remains the local operational authority;
- deterministic portable Jig records remain the Git synchronization representation;
- Git remains the continuity mechanism between installations;
- unrelated repository content must remain untouched;
- Git history, branches, merge/rebase/conflict handling and reconciliation are not Jig workflows;
- Planner, History and Settings remain the primary destinations;
- Task workspace state remains shared across responsive presentation;
- local/offline planning remains fundamental;
- a missing remote must never make an otherwise valid local repository unusable.

## 3. v1.1 operating environments

### 3.1 Desktop Linux

Desktop Linux remains supported.

The application installation and repository configuration steps become independent:

1. the Jig application/runtime is installed;
2. Jig can open in an unconfigured bootstrap state;
3. the user selects or acquires a planning repository from inside Jig;
4. Jig validates/adopts/initializes the repository;
5. normal Planner operation begins.

An already-configured v1.0.x installation upgrades without being forced through onboarding again.

### 3.2 Native Android

v1.1 introduces an independently installable Android application. iOS is explicitly outside the v1.1 release scope: the product architecture may remain portable enough to support a later Apple release, but v1.1 does not build, certify or distribute an iOS application.

The Android application must:

- present the same canonical Planner/History/Settings product semantics;
- keep its repository and operational database in application-owned storage without requiring the user to understand a filesystem path;
- synchronize the same portable Jig records through Git;
- retain useful local/offline planning when the network is unavailable;
- use the mobile OS for local reminder delivery;
- preserve compatibility with the same planning repository used by desktop Jig.

The initial Android onboarding path is intentionally narrower than desktop: v1.1 mobile acquires a remote GitHub repository into app-owned storage. Importing arbitrary device-local Git worktrees is excluded from the first mobile release.

## 4. Responsive application header

### JIG-110-FR-01 — sticky narrow/mobile header

At narrow/mobile widths, the complete Jig application header remains fixed to the top of the visible application viewport while the Planner, History or Settings content scrolls.

Scrolling must never cause navigation, synchronization status or the current Planner temporal controls to disappear above the viewport.

The sticky region must respect platform safe-area insets where applicable.

### JIG-110-FR-02 — two-level Planner mobile composition

The v1.0.x single-row narrow header is superseded.

On the mobile Planner, the sticky header is composed as two coordinated rows:

**Application row**
- Jig home/brand;
- Planner-only Add Task action when the active destination is Planner;
- compact synchronization status;
- primary navigation menu.

**Planner temporal row**
- Previous week;
- compact displayed-week range;
- Next week;
- Today.

Both rows belong to one sticky header region. They must not independently overlap, detach or scroll away.

History and Settings do not render the Planner temporal row or Planner-only Add Task action. Their sticky application row remains present while the destination content scrolls and continues to identify the active destination.

### JIG-110-FR-03 — touch target and navigation-menu usability

Narrow/mobile controls must be deliberately touch usable rather than merely desktop controls compressed into less space.

The navigation menu continues to expose the same Planner/History/Settings destination set from one semantic owner. It remains a compact popover/menu rather than a permanent side navigation drawer.

Its rows and the header's icon controls must provide materially larger touch targets than the v1.0.6 `size="sm"`-dominated composition. Acceptance must verify actual rendered interaction geometry at representative phone widths rather than only asserting a maximum header height.

The former narrow-header `<=56px` acceptance budget is removed.

### JIG-110-FR-30 — History/Settings heading ownership is in the application header

History and Settings already identify their active destination in the application header. v1.1 makes that header the single owner of the complete secondary-destination heading:

- History header shows **History** plus the concise subtitle **Completed work grouped by actual completion date**;
- Settings header shows **Settings** plus the concise subtitle **Repository, synchronization, appearance and diagnostics**;
- desktop and narrow/mobile use the same title/subtitle meaning, recomposed only for available space;
- the History and Settings content surfaces do not render a second page-level title or subtitle;
- after the header, History begins with its completion groups/empty state and Settings begins with its first settings section.

The subtitle is secondary orientation text, not a second navigation row or another destination state. It may use compact secondary typography and wrap within the governed header composition when necessary, but it must not be duplicated into body content.

## 5. Reminder semantics

### JIG-110-FR-04 — reminder-due attention is derived product state

A Task has **reminder-due attention** when all of the following are true:

- the Task is incomplete;
- it has a reminder time;
- its scheduled date is the current local date;
- the reminder time has passed.

This state is derived from canonical Task data and the current local date/time. It is not defined by whether an OS/browser notification was successfully displayed.

A browser/OS delivery failure must therefore never hide the fact that a Task requires attention. If Jig remains open while local time crosses the reminder boundary, the Task must enter reminder-due attention without requiring navigation, reload or another Task mutation.

### JIG-110-FR-05 — past reminders remain visible

Opening or returning to Jig after a reminder time has passed must immediately show the Task as reminder-due.

v1.1 removes the v1.0.x behaviour where a reminder that became due before the current browser session could be silently ignored as a historical reminder.

An outstanding rolled-forward Task preserves its reminder time. If the rolled Task's reminder time is already past on the current local date, it is reminder-due immediately.

### JIG-110-FR-06 — reminder-due card treatment

A reminder-due Task receives a persistent, accessible attention indication in Planner until the condition is resolved.

The indication must:

- be visible without opening the Task;
- use a governed warning/attention semantic rather than impersonating priority, error, selection or drag state;
- include non-colour meaning such as an attention/reminder icon and accessible text;
- remain visible when combined with selection, priority and drag/focus states according to the established state-precedence rules.

The state ends when any of the following occurs:

- the Task is completed;
- the reminder is removed;
- the reminder is changed to a future time;
- the Task is rescheduled such that its reminder is no longer due.

No separate acknowledgement workflow is introduced in v1.1.

### JIG-110-FR-07 — notification delivery is honest

Jig must distinguish **scheduled** notification state from **displayed/delivered** notification state.

A successful future OS scheduling request may be reported as scheduled. Jig must not describe that as delivered/displayed unless the platform API actually provides evidence for that stronger outcome. Permission denied, unsupported delivery, scheduling failure or runtime failure must not be represented as success.

The card-level reminder-due state remains the durable user-visible truth regardless of notification scheduling or delivery.

### JIG-110-FR-08 — mobile reminder delivery

On native Android, a saved future reminder is scheduled with the Android operating system so it can be delivered when Jig is backgrounded or not currently open, subject to OS permission and platform scheduling policy.

Editing, removing, rescheduling or completing the Task must update/cancel the corresponding pending local notification as necessary.

Jig does not introduce a remote push-notification service for v1.1.

### JIG-110-FR-09 — desktop/browser reminder delivery

On the Linux/browser application, reminder delivery must use a browser-supported notification path rather than relying exclusively on the direct `new Notification(...)` constructor that is not portable to mobile browsers.

v1.1 does not require a remote push service. Desktop closed-browser delivery remains outside the requirement unless the chosen local platform adapter can provide it without adding a new service dependency.

## 6. Two-phase application setup

### JIG-110-FR-10 — application can start before repository configuration

A freshly installed Jig application must be able to start before a planning repository has been selected.

An unconfigured installation shows a deliberate onboarding experience rather than a broken Planner, configuration-file error or technical setup utility.

Onboarding is a state of the Jig application, not a separate visual application. From first render on both desktop and Android it uses the governed Jig application frame, theme, brand/header ownership, body geometry, safe-area handling and interaction language. The onboarding body is distinct from Planner/History/Settings and contains only the choices and progress needed to establish the planning-data home.

Planner/History/Settings and Task actions remain unavailable until repository initialization succeeds, but the application must not replace the Jig shell with a standalone setup page while unconfigured.

### JIG-110-FR-11 — configured upgrades bypass onboarding

If a valid existing Jig configuration and planning repository are present, upgrading the application must preserve that configuration and enter the normal Planner without asking the user to reconnect or reselect the repository.

### JIG-110-FR-12 — desktop repository choices

Desktop first-run setup presents two primary choices:

1. **Use a repository already on this computer**
2. **Connect GitHub**

The normal in-app flow must not expose installer-oriented `--repo-url` / `--checkout` concepts.

Expert/noninteractive CLI installation inputs remain available for automation and provider-neutral workflows.

## 7. Existing local repository path

### JIG-110-FR-13 — existing local Git repository is sufficient

On desktop, selecting an accessible existing Git worktree root is sufficient to configure Jig.

Jig validates/adopts/initializes its own data there and does not require the repository to have a remote.

### JIG-110-FR-14 — existing repository with remote

If the selected local repository already has a remote, Jig uses the repository's existing Git topology and ordinary system Git authentication.

Jig must not require a separate GitHub login merely because the repository happens to be hosted on GitHub.

If synchronization succeeds, the repository can reach `synchronized`.

If authentication or another Git operation fails, Jig reports the ordinary repository synchronization issue without corrupting local planning data.

### JIG-110-FR-15 — existing repository without remote

If the selected local repository has no remote, setup still succeeds.

The repository operates in the healthy `local-only` state.

Jig does not silently create a remote or force the user through provider authentication.

Adding/changing Git remotes remains ordinary Git configuration outside Jig's required v1.1 workflow.

### JIG-110-FR-16 — provider neutrality of local selection

A selected existing local repository may use GitHub, GitLab, Bitbucket, an enterprise Git server, SSH, HTTPS or another Git-supported transport.

Jig does not infer provider-specific product semantics from an already-configured local repository.

## 8. GitHub acquisition path

### JIG-110-FR-17 — Connect GitHub is one user intent with automatic acquisition

When no suitable local checkout exists, Jig provides a low-friction GitHub connection flow whose primary user intent is **Connect GitHub repository**.

The normal experience is:

1. the user chooses **Connect GitHub repository** once;
2. Jig initiates the governed GitHub authorization/access flow and continues it automatically;
3. GitHub may present provider-owned identity, consent, organization/SSO or repository-access decisions when GitHub requires them;
4. if more than one eligible repository remains and Jig cannot determine the intended planning-data home, Jig presents one repository-selection surface;
5. after that required user choice, Jig automatically acquires, validates, adopts/initializes and opens the Planner.

Jig owns continuation between these points. The normal UI must not require the user to poll, refresh provider state, resume an internal phase, operate installation/access discovery, choose a checkout location, invoke clone/fetch, or separately trigger repository adoption. Buttons such as **Refresh access**, **Grant repository access**, **Manage GitHub access** or other protocol/state-machine controls are not normal Jig workflow. If GitHub requires a provider-owned access change, Jig may route the user to that GitHub-owned surface and must automatically resume discovery when control returns.

During automatic work Jig presents one coherent connecting/progress state in product language. It does not expose internal phases such as authorizing, polling, installation discovery, acquiring, cloning, validating, adopting or initializing as separate user steps.

Users are not required to create or paste a personal access token, configure SSH keys, copy a clone URL, choose a checkout directory or understand Git/GitHub protocol mechanics in the normal GitHub flow.

### JIG-110-FR-18 — least privilege

The GitHub integration must request no broader repository/account permissions than are required to:

- enumerate/select repositories available to the integration;
- clone/fetch the selected repository;
- commit and push Jig-owned portable records through the existing synchronization design.

The user must be able to restrict the GitHub App installation to selected repositories using GitHub's own authorization surface.

### JIG-110-FR-19 — provider owns authentication policy; Jig owns orchestration

GitHub owns user identity, account authorization, organization policy, SSO policy, repository-access consent and token semantics.

Jig owns the product-level orchestration around those provider decisions: initiating the supported authorization flow, recognizing when provider-owned user action is required, resuming automatically after that action, discovering the repositories available to the authorized integration, securely retaining the resulting credential on the current device and presenting it to the Git transport for the selected repository.

Provider-owned consent is a legitimate user interaction. GitHub protocol progression is not. Jig must not turn token polling, access discovery, credential refresh, installation enumeration or transport retry into separate user responsibilities.

Jig must not implement passwords, SSH key management, personal-access-token creation, organization authorization policy or a general credential manager.

### JIG-110-FR-20 — credentials are not planning data

Provider credentials must never be written into:

- canonical Task data;
- portable Jig records;
- the planning repository;
- a persisted remote URL containing embedded credentials;
- ordinary shareable Jig configuration.

Credentials must use platform-appropriate secure storage and may be removed/re-authorized independently of planning data.

## 9. Repository acquisition and storage

### JIG-110-FR-21 — desktop managed checkout default

For GitHub acquisition on desktop, Jig chooses a deterministic application-managed checkout location by default.

The user is not required to choose a filesystem path.

The normal GitHub onboarding UI does not offer a checkout-path override. Expert users who require a specific filesystem location use the existing local-repository/CLI path rather than adding managed-checkout configuration to Jig.

The managed repository location must not sit inside an application directory that is atomically replaced during Jig upgrades.

### JIG-110-FR-22 — Android checkout is private implementation detail

On native Android, the selected GitHub repository is cloned into Jig-owned application storage.

The normal Android UI does not expose or ask the user to choose the checkout directory.

Removing the application may remove app-owned local checkout/database storage according to platform rules; the remote Git repository remains the portable continuity source.

### JIG-110-FR-23 — acquisition converges to one repository adoption path

Whether the repository arrived through:

- an existing desktop checkout;
- desktop GitHub acquisition; or
- Android GitHub acquisition,

Jig validates/adopts/initializes the resulting repository through the same semantic repository-setup rules.

There is no separate "GitHub Task model", "mobile repository model" or repository migration domain.

## 10. Android continuity

### JIG-110-FR-24 — same portable data contract

Desktop and Android must read/write the same governed portable Jig record format.

A planning repository used on Linux can be acquired on Android and vice versa without an export/import conversion workflow.

### JIG-110-FR-25 — same planning semantics

Android must not introduce alternative Task semantics, a separate selected-day model, a reduced Task record, or an Android-only lifecycle.

The existing daily rollover rule is part of that shared behaviour: when Android launches/resumes after the local date has advanced, all unfinished earlier-day Tasks must roll into the current local date before the Planner is presented. If Jig remains foregrounded across local midnight, rollover must occur without requiring an application restart.

Responsive/native presentation may differ, but canonical Task/planning behaviour remains shared.

### JIG-110-FR-26 — offline-first mobile edits

After successful initial acquisition, Android planning edits must save locally without requiring network connectivity.

Repository synchronization may become pending/retrying/sync-issue while offline and resume according to the same coarse operational outcome model when connectivity returns.

## 11. Android distribution

### JIG-110-FR-27 — Android development installation and F-Droid-first distribution

v1.1 does not include an Apple/iOS release path.

Android development and product validation must **not** depend on an app-store publication cycle. The development workflow must produce an installable development APK that can be installed directly on a physical Android phone and used to validate the complete mobile experience, including onboarding, Git synchronization, offline operation, reminders, touch interaction and responsive layout.

**F-Droid is the first public Android app-store/repository target for Jig.** The v1.1 Android application and its dependency/build chain must therefore remain compatible with the F-Droid main-repository inclusion model: the application is open source, its Android build is buildable from publicly available source with a FLOSS-compatible toolchain/dependency set, and core product behaviour does not depend on proprietary Google Play services.

Development APKs are sideloaded only for development and certification. v1.1 does not establish a second public Android APK distribution channel alongside F-Droid.

F-Droid is the first public Android distribution target. A Jig v1.1 Android candidate must be F-Droid-submission-ready and the F-Droid submission path must be exercised. External F-Droid review timing does not block local development, physical-device testing or completion of the implementation candidate.

Google Play publication is explicitly deferred to a later Jig version. Later Google Play packaging/publication must not require changing the Android application identity, canonical planning data, repository compatibility, onboarding semantics or core functionality.

## 12. Task-card drag and drop correction

### JIG-110-FR-28 — precise, visible Task-card placement

The v1.0.6 Task drag/drop interaction is superseded. A drag must make the **exact result of releasing the Task visible before the user drops it**.

The interaction must satisfy all of the following:

- dragging a Task within a date produces an explicit insertion indicator at the exact before/after slot where the Task will be placed;
- dragging a Task to another date identifies both the destination date and the exact insertion slot within that date;
- dropping into an empty date has one unambiguous empty-list target;
- the final persisted Task date/order must match the insertion location shown immediately before release;
- the interaction may transiently displace list items to preview the destination, but canonical Task state/order must not mutate until drop; cancel/outside-drop must restore the original arrangement exactly;
- the source Task remains visibly identifiable while dragging and returns unchanged if the drag is cancelled or released outside a valid target;
- drag targeting must remain stable across Task cards with different heights and across the gaps between cards;
- automatic scrolling while dragging must allow the user to reach off-screen Tasks/dates without losing the current drop target;
- the drag affordance must not compete with Task selection, checkbox, action menu, references or normal touch scrolling.

Task movement is activated from a dedicated visible drag/grip affordance on the Task card rather than treating the complete interactive card surface as the drag activator. The affordance is always visible at narrow/mobile widths and remains visible/clear enough on desktop to communicate that the Task can be moved.

The non-drag alternatives remain authoritative:

- same-date **Move up / Move down** actions remain available through the Task action menu;
- editing the Task date remains the explicit non-drag cross-date reschedule path.

The drag/drop interaction changes only the direct manipulation UX. It does not change Task ordering semantics, the Task command model, date ownership, or Git/persistence representation.

## 13. Recurring Tasks

### JIG-110-FR-29 — bounded recurrence with independent Task occurrences

A Task may optionally repeat, but every recurrence must be finite. Repeat has a required inclusive end date and no "forever" option.

The supported v1.1 patterns are deliberately small:

- **Weekly:** repeat every positive whole number of weeks on one or more selected weekdays. This covers once per week, multiple days in each active week, every day by selecting all seven weekdays, and intervals such as every four weeks.
- **Monthly:** repeat on an exact day of month. If a month does not contain that day, that month has no occurrence; Jig does not silently move the occurrence to month-end.

The Task on which Repeat is first enabled remains the seed occurrence. Further matching dates after the seed, through the inclusive end date, become ordinary canonical Task occurrences. Every occurrence has its own Task identity, date, persisted order, completion state and reminder lifecycle; Planner and History never display virtual recurrence copies.

Occurrence behavior is exact:

- every occurrence is linked to the same recurrence series and opening **any** occurrence exposes that shared Repeat configuration;
- the pattern/end-date configuration has one series owner and must not be copied into each Task as independently editable values;
- completing or reopening one occurrence affects that occurrence only;
- deleting one occurrence does not cancel the series;
- moving or explicitly rescheduling one occurrence does not shift the recurrence cadence;
- ordinary daily rollover still applies to an unfinished occurrence, while later occurrences remain anchored to their original recurrence dates;
- therefore a rolled-forward older occurrence may coexist with a later scheduled occurrence from the same series;
- generated occurrences copy the source Task's title, priority, context, reference, note and reminder time only at materialization time. After that, those fields are occurrence-local: editing the title or any other ordinary Task field on one copy never propagates to already-existing siblings. If a later Repeat edit introduces new recurrence slots, only those newly created Tasks copy the invoking occurrence's current fields;
- reminder eligibility/delivery then follows the existing reminder rules for that occurrence's own scheduled date.

### Governing recurrence mutation scopes

v1.1 has exactly two recurrence-related mutation scopes:

- **Occurrence scope** owns ordinary Task content and lifecycle state: title, priority, context, reference, note, reminder, scheduled date, position, completion/reopen and **Delete this Task**. These mutations affect only the invoking Task occurrence.
- **Series scope** owns only the recurrence configuration and series teardown: weekly/monthly pattern, interval/weekday or day-of-month selection, inclusive end date, and **Stop repeating / Remove recurrence**. Because every occurrence resolves the same `RecurrenceSeries`, opening Repeat on any occurrence shows and edits that same shared configuration.

There is deliberately no third scope for "all occurrences", "this and following Task details", template propagation or any equivalent bulk Task-content rewrite in v1.1. Once an occurrence exists, its Task fields remain independent from every sibling.

Changing the **Repeat** setting is therefore a **series-membership reconciliation**, not a Task-content edit. Reconciliation is anchored at the invoking occurrence's immutable recurrence slot:

- preserve the invoking occurrence, every earlier occurrence and every completed occurrence;
- keep a later outstanding occurrence when its immutable recurrence slot remains selected by the updated schedule, preserving its Task ID and all occurrence-local edits;
- remove a later outstanding occurrence only when its immutable slot is no longer selected by the updated schedule;
- create one Task for each newly introduced later slot, copying the invoking occurrence's current Task fields at creation time only;
- update the one shared series configuration in the same user operation;
- never rewrite title, priority, context, reference, note, reminder, scheduled date, position, completion or other Task-local state on any retained sibling.

**Remove recurrence / Stop repeating** is explicitly different from **Delete this Task**. From any recurrence occurrence, Stop repeating retains the invoking Task as a one-off Task, preserves every completed occurrence in History and removes **all other outstanding occurrences in that series** in one canonical mutation, including rolled/overdue siblings. The user must never need to delete the remaining generated cards individually. Delete this Task remains occurrence-only and leaves the recurrence rule and sibling occurrences intact.

The Task workspace exposes Repeat alongside the existing Date/Reminder fields on **every** recurrence occurrence. A recurring Task/card has a compact accessible repeat indication/summary so the recurrence and its series relationship are visible without opening the Task, but recurrence does not become a priority/status color and does not introduce another Planner destination.

## 14. Git authority boundary for v1.1

### JIG-110-FR-31 — Settings presents user-level data-home and synchronization state

The primary Settings synchronization experience must use the user's mental model rather than Git implementation topology.

It must answer, in product language:
1. **where Jig's planning data is connected** — a credential-free, human-readable repository identity when a remote-backed repository exists, or a clear local-only state;
2. **whether the user's current work is safe locally**;
3. **whether remote continuity is up to date, in progress or needs attention**; and
4. **whether any user action is actually required**.

When the current Jig state is durable locally but remote synchronization is pending or failing, the UI must preserve that distinction in user language such as **Saved locally · Sync needs attention**. It must not force the user to understand local Git refs, commit/export phases, remote names or transport mechanics to know whether work is safe.

Automatic synchronization remains the default. A standing primary **Sync now** control is not required merely because a transport operation exists. Retry/reconnect actions appear when they are actionable recovery choices, and a manual synchronization trigger may remain in diagnostics for expert use.

Detailed facts such as local Git snapshot/commit state, configured Git remote name/location, service health, SQLite state and transport diagnostics may remain available in a clearly secondary diagnostics/technical-details surface. They must not define the primary Settings information hierarchy.

The compact header synchronization indicator remains one derived user-level summary such as Local only, Syncing, Up to date or Needs attention. It is a pure presentation projection of the same underlying synchronization state rather than an independent status authority.

The v1.0.x Git boundary is retained with one explicit refinement for provider authorization.

**Jig owns:**
- the user's choice of planning-data home;
- requesting acquisition of a chosen remote repository;
- securely presenting an authorized provider credential to the narrow Git transport;
- Jig portable record generation/validation;
- automatic synchronization scheduling and coarse outcome reporting.

**Git/Git provider owns:**
- repository topology;
- branches, refs and upstream semantics;
- clone/fetch/push transport semantics;
- identity and account authorization policy;
- remote history;
- merge/rebase/conflict resolution;
- credential/token semantics and revocation.

Jig must still not become a general repository manager.

## 15. Explicit non-goals for v1.1

v1.1 does not add:

- multiple simultaneously active planning repositories;
- an in-app Git branch manager;
- remote creation/provisioning;
- remote editing or arbitrary repository migration;
- merge/rebase/conflict-resolution UI;
- provider-independent account login for every Git host;
- Android adoption of arbitrary external filesystem worktrees;
- push-notification servers;
- reminder acknowledgement/snooze workflows;
- a second Task schema or mobile Task projection;
- project-management functionality;
- iOS application build, certification or App Store distribution in v1.1;
- retaining dnd-kit as the Planner Task-card drag/drop owner;
- bulk propagation of title/details/reminder or other ordinary Task content across existing recurrence occurrences.
