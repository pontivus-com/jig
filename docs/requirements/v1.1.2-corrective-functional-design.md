# Jig v1.1.2 corrective functional design

**Status:** BINDING corrective amendment for v1.1.2.  
**Target release:** 1.1.2.  
**Tracking issue:** #66.

This amendment supersedes only the affected v1.1/v1.0.x clauses for Task drag feedback, synchronization diagnostics/recovery including bounded user-assisted conflict resolution, theme surface separation, configured viewport fill, motion tempo, responsive presentation ownership and the separation of responsive presentation from runtime/platform capability. All unaffected v1.1 requirements remain authoritative.

## JIG-112-FR-01 — three distinct application surface roles

**Governing solution design:** JIG-112-SD-01 defines explicit per-theme surface-role authoring; JIG-112-SD-12 defines rendered theme certification. The canonical UI/theme contract remains `../design/ui-solution.md` plus the brand/theme authority.

Every governed Theme in Light and Dark must render three perceptibly distinct roles:

1. **application chrome** — desktop header; narrow/mobile header and bottom navigation;
2. **Planner/day canvas** — the continuous planning background behind dated tracks;
3. **Task card** — the primary discrete work-item surface.

No supported theme may collapse any two of those three roles into an effectively identical fill.

The three roles are authored **per theme and appearance mode**. v1.1.2 explicitly rejects one universal body/surface/card mixing formula as the final authority because the governed theme families do not share one tonal structure and some upstream semantic background roles intentionally alias. The exact chrome/canvas/card expressions are fixed by the JIG-112-SD-01 binding surface-role table; implementation does not select or tune them.

Feature CSS must consume only the three product roles; it must never branch on theme name or embed theme palette literals. Generated theme artifacts remain compiler-owned.

Acceptance requires both computed-value/perceptual checks and rendered visual review across all 13 themes × Light/Dark. The numeric check is a guardrail against accidental collapse, not a substitute for design review.

## JIG-112-FR-02 — configured application fills the viewport

**Governing solution design:** JIG-112-SD-02 owns the AppShell fill/scroll chain; JIG-112-SD-11 enforces one scrolling authority across desktop/narrow. Detailed frame and safe-area ownership is in `../architecture/v1.1.2-responsive-presentation-architecture.md` §§10 and 16.

The configured application must use the pinned Astryx AppShell fill contract rather than creating a second viewport owner.

On desktop the AppShell main region owns the complete viewport below its header. Planner canvas color continues to the bottom of the available main region when content is empty or short. When content is long, the AppShell main region remains the single application scroll owner.

Narrow/mobile keeps its sticky header, persistent bottom navigation and safe-area behavior inside the same AppShell ownership model. Bottom-navigation/safe-area reservation must not create a second nested application scroller or fixed-height clipping surface.

## JIG-112-FR-03 — drag shows live card placement

**Governing solution design:** JIG-112-SD-03 defines React-owned prospective placement over dnd-kit mechanics; JIG-112-SD-08 defines the regression/acceptance proof. Shared desktop/narrow projection ownership is further governed by `../architecture/v1.1.2-responsive-presentation-architecture.md` §§7, 11 and the adaptive matrix Task-drag rows.

The insertion-line interaction is rejected.

While a Task is held and moved:

- the user sees the real Task-card presentation continuously under the pointer/finger;
- surrounding Task cards visibly reflow to the current prospective order before release;
- the destination is represented as actual card placement/card-sized space, not a before/after line;
- the original source position does not remain as a misleading faded copy once the prospective placement has moved elsewhere;
- same-date, cross-date and empty-date moves all use the same live-placement model;
- the persisted date/index after a successful drop exactly matches the last visible prospective placement;
- cancel, pointer cancel, invalid release or interruption restores the prior order and leaves no floating card.

Canonical Task state is still persisted once, on successful drop. The transient visual projection is interaction feedback, not a second durable Task-order authority.

## JIG-112-FR-04 — drag remains first-class on touch

**Governing solution design:** JIG-112-SD-04 defines pointer-specific activation, touch/scroll arbitration and keyboard alternatives; JIG-112-SD-08 defines the hard drag proof. Input ownership is additionally governed by `../architecture/v1.1.2-responsive-presentation-architecture.md` §9 and the adaptive matrix input rows.

Narrow/mobile must provide the same live-placement semantics as desktop while preserving vertical scrolling and independent controls.

- the dedicated grip is the touch drag activator;
- touch drag requires a deliberate press/hold with movement tolerance so ordinary scrolling does not accidentally initiate drag;
- mouse/pen uses the governed 6 CSS px movement threshold;
- auto-scroll must work for long dated lists;
- different Task-card heights must not destabilize targeting;
- checkbox, Task menu, reference/copy actions and Task open/select remain independent;
- Move up/down and Date edit remain non-drag alternatives.

## JIG-112-FR-05 — synchronization diagnostics explain failures

**Governing solution design:** JIG-112-SD-05 defines strict phase/reason diagnostics, sanitization and the Desktop evidence gate; JIG-112-SD-08 defines permanent diagnostic/redaction acceptance.

When synchronization is pending, retrying or needs attention, Diagnostics must expose enough **sanitized** technical information to understand the failure without inspecting process logs.

Diagnostics must represent **phase** and **reason** as separate facts. A phase answers where synchronization was operating; a reason answers why that operation did not complete. They must not be collapsed into one mixed classification.

The diagnostic projection uses the strict nullable/required field contract in JIG-112-SD-05; unavailable facts are null rather than omitted or inferred. It includes:

- synchronization phase;
- classified reason;
- retryable/non-retryable;
- attempt count;
- last-attempt and next-retry times;
- abbreviated local Jig head, observed remote Jig head and last-adopted head;
- observed lineage;
- sanitized remote name/location;
- automatic recovery attempted and outcome;
- sanitized final Git/adapter error summary.

Diagnostics provides a **Copy diagnostics** action suitable for support.

Credentials, authorization headers, askpass values, tokens and Task title/note/reference content are forbidden from this output.

## JIG-112-FR-06 — bounded automatic Jig-data recovery

**Governing solution design:** JIG-112-SD-05 governs evidence-driven ordinary Desktop root-cause diagnosis; JIG-112-SD-06 governs isolated validated resumable related-divergence recovery; JIG-112-SD-07 governs the complete synchronization lifecycle classification; JIG-112-SD-08 governs causal/recovery acceptance.

The reported Desktop/Linux `Needs attention` defect must be investigated and, only if reproduced, corrected from observed evidence rather than from an assumed failure mechanism. v1.1.2 diagnostics must make the first failing synchronization boundary reproducible before any causal correction is claimed.

The existing controller already follows observe-before-write for normal synchronization and re-observes after push. Therefore v1.1.2 must not state that lack of remote observation is the established root cause unless runtime evidence proves a different concrete path.

**2026-11-23 evidence disposition.** The permanent upgraded Desktop reproduction now exercises initial synchronization, a local mutation and push, controller restart, an external remote fast-forward, re-observation and adoption. It completes synchronized with `pending_sync = false` and idle diagnostics, so no ordinary Desktop failing boundary is reproduced. The causal-correction obligation is therefore closed as **NO DEFECT REPRODUCED / NO CAUSAL FIX REQUIRED**. This disposition authorizes no speculative synchronization-policy change and does not claim that the historical report was fixed; a future reproducible failing boundary would require a new evidence-driven correction.

Separately, Jig owns the normal continuity outcome for its isolated portable planning history. A divergence between two supported Jig installations is no longer automatically terminal when Jig can prove a safe recovery.

The following cases recover automatically:

1. transient transport/authentication: bounded retry and existing credential refresh/reconnect ownership;
2. push race/ambiguous result: re-observe before another write and recognize an already-landed local head;
3. remote-only fast-forward: validate and adopt;
4. local-only fast-forward: push normally;
5. diverged but provably related Jig data: if local and remote Jig heads share provable common ancestry, every candidate uses the configured dataset identity, and the inputs are canonical Jig snapshots, attempt one isolated three-way reconciliation.

The reconciliation is accepted only if the complete candidate portable snapshot passes all Task, ordering, recurrence and dataset invariants. A Git-clean result that fails semantic validation is a failed recovery, not success.

Bounded divergence recovery is a v1.1.2 continuity capability. It must not be presented as the proven root-cause fix for the reported Desktop synchronization defect unless the new evidence identifies related divergence as that cause.

## JIG-112-FR-07 — recovery safety boundary

**Governing solution design:** JIG-112-SD-06 defines acceptance ordering and crash-safe recovery; JIG-112-SD-07 defines recoverable versus terminal states; JIG-112-SD-08 defines destructive-safety and unrelated-history acceptance.

Automatic recovery is restricted to Jig-owned portable history.

Jig must never use this capability to merge, rebase, reset, rewrite, stage, commit or force-push unrelated repository branches/files.

A conflict inside **provably related, valid, same-dataset Jig history** is not terminal merely because automatic reconciliation cannot choose between two legitimate user changes. JIG-112-FR-15 provides bounded user-assisted resolution for that case.

The following remain terminal **Needs attention** because Jig cannot establish a safe resolution domain:

- no provable common ancestor or ambiguous/multiple ancestry;
- previously synchronized remote history deleted or rewritten incompatibly;
- incompatible dataset identity;
- invalid/unsafe ancestor, local or remote portable snapshot;
- ambiguous synchronization remote;
- adapter/ref state that prevents Jig from proving the exact two heads being resolved;
- another condition where Jig cannot prove that user choices can produce one complete canonical Jig snapshot without touching unrelated history.

On terminal attention, both local planning state and observed remote data are preserved. Diagnostics states the reason and attempted recovery, if any. No terminal state exposes arbitrary Git command execution inside Jig.

## JIG-112-FR-08 — corrective release audit

**Governing solution design:** JIG-112-SD-01..08 define the theme, viewport, drag and synchronization behaviors being audited; JIG-112-SD-11 and JIG-112-SD-12 define adaptive architecture and rendered/browser certification; JIG-112-SD-17 defines mandatory Git/provider/portable/protocol source-ownership remediation. The adaptive interaction matrix is part of this acceptance authority.

v1.1.2 is not complete until permanent browser/unit/architecture coverage verifies:

- 13 themes × Light/Dark: reviewed chrome/canvas/card separation with no generic-formula collapse;
- empty, short and overflowing desktop Planner viewport fill with one AppShell-main scroll owner;
- live card placement on desktop and narrow/mobile;
- touch activation, auto-scroll, cancel/pointercancel and cross-date movement;
- at least 20 sequential same-date/cross-date drag cycles with zero React/DOM reconciliation errors, stranded overlays or incorrect persisted placement;
- every synchronization presentation;
- diagnostic phase/reason projection and secret/content redaction;
- automatic recovery for safe divergence, guided in-app resolution for eligible same-dataset semantic conflicts, and refusal/crash-safe preservation for unsafe divergence;
- no mutation of unrelated repository history;
- source-ownership debt closed: canonical portable semantics under `src/core`, shared provider modules under `src/github`, configured-runtime envelopes under `src/protocol`, Linux system-Git mechanics decomposed under `src/shell/git`, with no legacy root compatibility shims or monolithic `src/shell/git.ts`;
- permanent dependency tests proving core/provider/shell/native ownership direction and no duplicated synchronization/recovery policy;
- every distinct desktop/narrow presentation pair and every shared-adaptive surface in the responsive interaction matrix.

## JIG-112-FR-09 — perceptible application motion

**Governing solution design:** JIG-112-SD-09 defines the single public duration-token scale and reduced-motion ownership; JIG-112-SD-12 defines rendered motion/reduced-motion acceptance.

Ordinary Jig motion must be visibly perceptible rather than reading as instantaneous.

The current effective duration scale is doubled at minimum for normal motion:
- 95/125/165ms fast family → at least 190/250/330ms;
- 225/300/400ms medium family → at least 450/600/800ms;
- 525/700/935ms slow family → at least 1050/1400/1870ms.

This governs Jig-authored transitions and Astryx primitives used by Jig, including destination entry, Drawer/BottomSheet, menus/popovers/dialog transitions, Task-card movement, feedback reveal/dismiss, navigation state, theme/surface interpolation and other ordinary application motion.

The application must not create a collection of component-local arbitrary durations. One motion scale owns the normal tempo.

`prefers-reduced-motion: reduce` remains authoritative and removes/reduces animation rather than applying the slower normal tempo.

## JIG-112-FR-10 — desktop and narrow/mobile are two explicit presentation compositions

**Governing solution design:** JIG-112-SD-11 defines the binding responsive registry/enforcement, JIG-112-SD-13 defines branch/share semantics, and JIG-112-SD-14 prevents presentation class from becoming platform identity. The detailed composition topology and placement contract are `../architecture/v1.1.2-responsive-presentation-architecture.md` and `../design/v1.1.2-responsive-interaction-matrix.md`.

Jig has one semantic/application state model and **two intentionally different presentation compositions** at the governed 73rem semantic layout boundary:

- **desktop / expanded**;
- **narrow / mobile**.

The boundary is selected by available layout width through the existing `LayoutMode`; it is not selected by operating-system identity. A narrow Linux window receives the narrow composition, and a future sufficiently wide Android window is not forced into phone composition merely because it is Android.

Material differences in hierarchy, placement, primitive, fixed/floating behavior, focus/dismiss path, safe-area ownership or interaction geometry require distinct presentation owners. In particular, application chrome/navigation, Planner composition, Task workspace, operation feedback and onboarding are distinct desktop/narrow compositions.

Shared semantic state, commands and domain rules remain above the presentation branch. Task content/form semantics, History, Settings, Diagnostics, delete confirmation and menu actions remain singular unless the responsive audit proves a genuine composition difference.

Only one presentation tree may be mounted at a time. Rendering desktop and narrow trees simultaneously and hiding one with CSS is prohibited.

The [v1.1.2 responsive interaction matrix](../design/v1.1.2-responsive-interaction-matrix.md) is the binding placement/ownership registry for every governed surface.

## JIG-112-FR-11 — feedback presentation is viewport-appropriate

**Governing solution design:** JIG-112-SD-10 defines one feedback semantic state/content owner with separate desktop/narrow placement owners; JIG-112-SD-12 governs rendered placement/motion acceptance; JIG-112-SD-13 governs the presentation split.

Short-lived operation confirmation has two presentations over one confirmation state:

- **desktop:** compact bounded top-end toast/notification stack inside the configured application viewport; it must not span the Planner/application width;
- **narrow/mobile:** inset safe-area-aware snackbar/notification above persistent bottom navigation.

Durable operation/synchronization attention is not an ephemeral toast:

- **desktop:** bounded wide-screen alert region aligned to the application content/top-end without becoming a full-width mobile banner;
- **narrow/mobile:** inline/inset available-width alert below sticky application chrome and above content.

The same message, dismissal and accessibility semantics are shared. Only presentation composition and placement differ.

## JIG-112-FR-12 — responsive interaction audit is a release gate

**Governing solution design:** JIG-112-SD-11 defines matrix enforcement, JIG-112-SD-12 defines rendered browser acceptance, JIG-112-SD-13 defines presentation ownership, and JIG-112-SD-14/15 define the platform/input separation required by the now-complete adaptive matrix. `../design/v1.1.2-responsive-interaction-matrix.md` §§A–E is the row-level acceptance registry.

v1.1.2 is not complete until every row in the responsive interaction matrix is reviewed in desktop and narrow/mobile real-browser evidence.

The audit must explicitly verify:

- the declared desktop and narrow placement for every distinct surface;
- that only the correct presentation tree is mounted;
- that fixed/floating controls exist only in their declared viewport class;
- that shared-adaptive surfaces preserve one semantic implementation;
- overlay primitive and placement;
- action placement and hierarchy;
- focus/dismiss behavior;
- touch geometry and safe areas;
- motion and reduced motion;
- no accidental mobile-on-desktop or desktop-on-mobile composition.


## JIG-112-FR-13 — presentation class and runtime capability are orthogonal

**Governing solution design:** JIG-112-SD-14 defines the three independent selectors/detection boundaries; JIG-112-SD-15 defines Linux/browser versus Android/native capability and lifecycle ownership. `../architecture/v1.1.2-responsive-presentation-architecture.md` §§1–4, 9 and 13–15 define the detailed topology.

v1.1.2 must not use one ambiguous "desktop/mobile" switch to own unrelated concerns.

Jig has two independent axes:

1. **presentation class** — `desktop/expanded` or `narrow`, selected only from the governed 73rem available-width boundary;
2. **runtime capability** — Linux/browser or Android/native capabilities selected at the imperative-shell integration boundary.

A third interaction fact, **input modality**, is observed only where needed (for example pointer type for drag activation or software-keyboard/IME behavior). It must not become another application/domain state store.

Consequences:

- a narrow Linux/browser window uses the narrow presentation while retaining Linux/browser runtime capabilities;
- Android uses native lifecycle, system-bar, notification, secure-storage and repository adapters regardless of which presentation class is active;
- platform-only capabilities must never be inferred from `LayoutMode`;
- responsive geometry must never be inferred from `Capacitor.isNativePlatform()` or another runtime identity check;
- raw runtime detection belongs only at platform adapter/composition boundaries, not scattered through Planner, Task, History, Settings or other feature components;
- input-specific behavior uses actual input/capability evidence, not an assumed device category.

The user-visible product semantics remain singular across all combinations.

## JIG-112-FR-14 — complete adaptive/platform concern registry is binding

**Governing solution design:** JIG-112-SD-11, SD-13, SD-14 and SD-15 jointly define registry enforcement, presentation ownership, orthogonal selection and platform lifecycle/capability boundaries. `../architecture/v1.1.2-responsive-presentation-architecture.md` is the complete architecture contract and `../design/v1.1.2-responsive-interaction-matrix.md` §§A–E is the complete row-level concern/acceptance registry.

The v1.1.2 adaptive interaction matrix must classify every current concern that differs by presentation class, runtime capability or input modality.

At minimum the registry must explicitly govern:

- application shell, header, destination title, navigation, Add and synchronization-status placement;
- Planner composition, date sections, empty states, Today/focus behavior, Task-card geometry and drag;
- Task workspace primitive, editor action placement, Repeat controls, software-keyboard/IME and focus/dismissal;
- transient confirmation, durable attention, loading/fatal and other operational feedback;
- History, Settings, Diagnostics, Appearance, Notifications and references/actions;
- onboarding composition and the platform-specific availability of existing-local-repository setup;
- GitHub provider handoff/return-to-app continuation;
- repository storage/path visibility and platform credential ownership;
- configured runtime transport and synchronization opportunities;
- browser notification delivery versus Android local-notification scheduling, permission and exact-timing settings;
- Android activation/resume, native Back, app exit delegation, system bars and safe-area ownership;
- theme/System appearance interaction with native system bars;
- touch/coarse-pointer hit geometry, pointer-specific drag activation and keyboard alternatives.

A concern may be **shared**, **presentation-specific**, **runtime-specific**, **input-specific**, or a combination. The matrix must state the owner and acceptance evidence for each.

v1.1.2 is not implementation-ready if a material desktop/narrow or Linux/Android difference exists in code or governing v1.1 authority but has no explicit classification.

## JIG-112-FR-15 — guided Jig-data conflict resolution is available in-app

**Governing solution design:** JIG-112-SD-16 defines the bounded conflict-resolution model, responsive recovery workspace, candidate construction and acceptance protocol. JIG-112-SD-06 remains authoritative for three-way evidence and crash-safe candidate acceptance; JIG-112-SD-08 governs permanent recovery verification; JIG-112-SD-17 fixes the shared-core/platform-shell source ownership used to implement it.

When automatic related-divergence recovery reaches `semantic-conflict` **after** Jig has already proved exact local/remote heads, exactly one common ancestor, matching dataset identity and valid ancestor/local/remote portable snapshots, **Needs attention** becomes actionable rather than requiring external Git tooling.

The user must be able to choose **Resolve sync conflict** from Data & sync / synchronization attention on both desktop/expanded and narrow/mobile.

The recovery experience:

- works entirely inside Jig and therefore works on Android where the managed repository is app-private;
- explains that both devices changed the same planning data and that local work remains safe;
- presents conflicts in planning terms rather than Git-file/merge-marker terms;
- identifies each conflicting Task or recurrence family and shows **This device** versus **Remote** values for the changed user-visible fields;
- for delete-versus-change conflicts, explicitly presents **Keep deleted** versus **Keep changed Task/series**;
- never performs field-by-field automatic synthesis between two conflicting records;
- requires an explicit choice for every unresolved record conflict;
- when the chosen records still leave an affected date with ambiguous/invalid **outstanding-Task** order, presents only that date's surviving outstanding Tasks (`completed_at === null`) as an editable order and requires the user to establish the final order using the normal Jig ordering interaction plus Move up/down accessibility controls; completed Tasks remain whole-record choices, retain `position=null`, and never enter the order draft;
- validates the complete resulting Task/recurrence/dataset snapshot before the user can confirm;
- shows a final summary and requires explicit **Use this resolution** confirmation;
- preserves both authoritative heads until the confirmed candidate has passed the same revision/head re-check and crash-safe acceptance contract as automatic recovery.

The conflict workspace may expose read-only **Technical details** containing the exact classified reason and abbreviated base/local/remote heads plus read-only/copyable canonical record JSON for the currently selected conflict. It must not expose credentials or an arbitrary shell/terminal.

A user may cancel at any time before **Use this resolution**. Cancellation changes neither canonical SQLite nor the authoritative local Git ref. If the app is killed before confirmation, the resolution draft is discarded and reconstructed from the still-authoritative heads on the next attempt.

After confirmation, interruption/restart behavior is identical to JIG-112-SD-06: Jig either remains at the pre-acceptance authoritative state or proves/resumes the accepted candidate. No force push is authorized.

A general Git terminal, arbitrary command runner, merge/rebase editor, unrelated-history resolver or filesystem browser is **not** part of this requirement.
