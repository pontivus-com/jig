# Jig v1.1 — desktop/mobile UX/UI implementation-fidelity audit

**Status:** UX-F0 governed fidelity baseline — accepted 2026-11-19.  
**Branch authority:** `v1.1`.  
**Governing inputs:** `docs/design/ui-solution.md`, `docs/design/brand-and-theme.md`, the v1.1 governed HTML references, current `v1.1` implementation, and retained browser evidence artifact `14525538706`.  
**Purpose:** distinguish design-authority gaps from implementation gaps before further UI work. This audit does not reopen correct Task/domain, recurrence, persistence, GitHub orchestration, synchronization or Android runtime architecture.

## 1. Executive finding

The previous v1.1 non-device closure was valid for many functional/runtime mechanics but invalid as UX/UI fidelity certification.

The implementation applied several structural decisions correctly — one Planner destination, full-width desktop Planner, integrated Task form/Repeat, right Drawer / mobile BottomSheet, Settings section regrouping, touch-target minimums and the replacement drag owner — but the visual hierarchy and design language were not implemented with the fidelity implied by the closure status.

The failure mechanism was systematic:

1. **mechanical acceptance was treated as visual acceptance** — dimensions, overflow, reachability and semantic DOM assertions passed;
2. **retained screenshots were captured, not reviewed against a complete visual acceptance matrix**;
3. **some authority was itself insufficient or wrong for Android**, especially the mobile hamburger + Add + sync header composition;
4. implementation therefore optimized literal geometry rather than hierarchy, prominence, reachability, rhythm and cross-surface coherence.

UX-F0 corrects the authority before implementation continues.

## 2. Platform/design-system basis for the correction

The compact Android shell is now governed by the following platform conventions:

- three peer destinations use persistent compact-window primary navigation rather than a top-reach hamburger;
- the highest-priority screen action may use one prominent floating action affordance;
- secondary actions belong in the top bar or contextual surface;
- a touch target is at least 48×48dp, but the **visible glyph/container may be smaller**;
- essential interactions should remain reachable and the screen should not be overloaded with equally prominent actions.

Jig remains an Astryx application. Astryx 0.7.13 supplies Button/IconButton, StatusDot, AppShell, Layout, Drawer, BottomSheet and the semantic theme system, but no public bottom-navigation or FAB component. Therefore Jig may own the smallest product-specific bottom-navigation/FAB placement composition while using Astryx public interactive leaves, icons and tokens. This is not permission for a second component system.

## 3. Corrected cross-platform hierarchy

### 3.1 Compact/mobile configured application

Primary visual hierarchy:

1. **current destination / planning context**;
2. **Planner content and Tasks**;
3. **one primary Planner creation action**;
4. **primary destination navigation**;
5. **healthy synchronization status**;
6. secondary/contextual actions.

Configured compact Planner therefore uses:

- a quiet top application bar with Jig identity and a low-prominence synchronization indicator;
- a dedicated temporal row with Previous, readable week range, Next and explicit **Today**;
- one bottom-end **Add task** FAB on Planner only;
- persistent bottom navigation for exactly **Planner / History / Settings**;
- no hamburger as primary destination navigation;
- no healthy sync pill/circle competing visually with Add or the week context.

History and Settings use:

- one compact top bar owning the destination title;
- the same persistent bottom navigation;
- no Planner FAB;
- sync attention may escalate through a semantic indicator/banner when genuinely actionable.

### 3.2 Desktop configured application

Desktop retains the shallow three-zone 44px header because it matches Jig's stable three-destination information architecture and avoids wasting Planner width:

- left: Jig Home;
- center: Planner temporal group, or the active History/Settings destination heading;
- right: Planner-only Add, direct Planner/History/Settings navigation, restrained synchronization status.

Desktop must still pass a visual-balance review. The structural decision is retained; the previous absence of comprehensive screenshots is not evidence of conformance.

## 5. Authority changes locked by UX-F0

The following are no longer implementation choices.

### 5.1 Mobile shell/navigation

1. Compact configured Jig uses persistent bottom navigation for **Planner / History / Settings**.
2. The hamburger/popover is removed as primary compact destination navigation.
3. Planner Add is one prominent bottom-end FAB above the navigation/system inset, not a filled top-bar square.
4. The top application bar does not contain three peer action containers. It contains product/destination identity plus restrained status/exception affordances only.
5. Healthy sync is deliberately low-prominence. A small semantic status glyph/dot may sit in a 48px target, but its visible colored container must not visually rival Add or temporal context.
6. Sync attention may escalate to warning/error icon treatment and a contextual banner/action.
7. Previous/Next retain 48px hit areas but quiet visible icon treatment.
8. **Today remains textually identifiable**; a calendar glyph alone is not sufficient.
9. The week range is the dominant temporal label in the temporal row.
10. Bottom safe-area/gesture insets are owned by the bottom-navigation/FAB composition.

### 5.2 Planner density

1. Empty mobile dates are content-driven compact sections; they do not reserve task-card-like vertical acreage.
2. A date header contains full weekday + day number and a quiet date-specific Add affordance.
3. Populated dates grow with their Task sequence; empty dates remain rapidly scannable.
4. Task cards remain the principal discrete surfaces, with title first and metadata/action chrome subordinate.
5. Completion, grip and overflow each keep independent touch targets without forming three equally prominent visual columns.

### 5.3 Onboarding

1. The existing v1.1 onboarding references remain semantic/state authority but are now interpreted as **minimum composition**, not permission to flatten visual signifiers into plain text.
2. Initial onboarding must visibly communicate: product promise → three concise proof/reassurance points → genuine setup action.
3. The three proof points use consistent semantic icon/signifier treatment and concise copy.
4. Mobile does not wrap the primary CTA in a generic dashboard-style settings card merely because Section is available.
5. Desktop preserves a strong stable value region and a clearly bounded action pane; the two regions must feel intentionally related rather than independently centered utilities.

### 5.4 Task workspace/form

The canonical field order and one-Save behavior remain unchanged. Visual grouping is now explicit:

- **Task** — Title;
- **Schedule** — Date, Repeat and Reminder, with recurrence details directly under Repeat;
- **Details** — Priority, Context and Reference;
- **Notes** — Notes;
- lifecycle actions remain visually separated from Save/Cancel.

Grouping is created through spacing, headings/supporting copy and Astryx form/layout primitives — not nested cards around every field.

### 5.5 History and Settings

History:
- one chronological reading column;
- date group heading → completed Task rows;
- Task title dominates; completion time/context/scheduled date remain secondary;
- no dashboard cards.

Settings:
- one reading column, not a stack of equal visual cards;
- **Data & sync** presents human-readable planning-data identity, local safety, continuity and recovery;
- raw repository path, service/database and exact Git mechanics are Diagnostics only;
- Appearance and Notifications are concise settings groups;
- Diagnostics is collapsed/subordinate by default;
- mobile header does not carry a multi-line explanatory subtitle.

## 6. Evidence standard after UX-F0

The permanent visual-certification process is now governed by [Jig UX/UI visual audit standard](ux-ui-visual-audit-standard.md).

UX-F0's earlier exhaustive mobile-width screenshot list is superseded. The visual audit deliberately uses canonical **1440×900 desktop** and **390×844 narrow** evidence for the complete surface review, with **1280×800** and **320×844** restricted to designated stress surfaces. The **1168/1167** presentation boundary is proven mechanically rather than multiplied into the visual corpus.

The standard requires settled-state capture, paired desktop/narrow judgment, explicit per-surface targets, hierarchy/density/typography/content/color/contrast/action/overlay/state review, constrained theme evidence and criterion-level PASS/FAIL disposition. Screenshot collection without that review is not fidelity certification.

## 7. Implementation boundaries

UX-F1..F6 must not:

- replace the canonical Task/TaskCommand model;
- alter recurrence semantics merely to restyle the form;
- replace the dnd-kit movement owner merely to restyle cards/slots;
- reopen GitHub Device Flow/orchestration merely to restyle onboarding;
- change structured repository synchronization truth merely to simplify its presentation;
- introduce a second icon/component/theme system;
- target Astryx private DOM/CSS.

Implementation remains direct on `v1.1`.
