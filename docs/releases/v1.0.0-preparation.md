# Jig v1.0.0 release-preparation task set

**Status:** Historical v1.0.0 release-preparation execution contract; not current general release authority.  
**Canonical current release authority:** `docs/releases/README.md`.  
**Candidate:** Jig v1 MVP release candidate on `implementation/v1-mvp`.  
**Target release:** `v1.0.0`.

This task set prepares the already-complete product implementation for public release. It must not reopen the product model or introduce a second runtime, installer, persistence authority or release channel.

## RP-01 — Public release history

Create root `CHANGELOG.md` with a non-empty `[Unreleased]` section describing the completed v1 candidate. Future ordinary PRs append there. The dedicated release PR freezes those entries under `[1.0.0] - YYYY-MM-DD`.

**Gate:** changelog represents the actual implemented/certified candidate and does not claim deferred features.

## RP-02 — Release documentation

Create the permanent release index, v1.0.0 release-notes draft and installation guide. Update the documentation index and root README to expose them.

**Gate:** a new user can identify supported platforms, install from a release asset, understand data placement/sync boundaries, upgrade/uninstall, and locate support/security instructions without reading implementation plans.

## RP-03 — Distribution contract

Publish exactly four Jig-owned assets per release: x64 bundle, arm64 bundle, `SHA256SUMS`, and `jig-install.sh`.

**Gate:** both bundles identify exact version/commit/runtime/architecture and contain the certified prebuilt UI plus canonical runtime/installer material.

## RP-04 — Canonical release installer path

Keep `scripts/install.sh` as the one installer behavior. Add a bootstrap that only selects the architecture, downloads/verifies the immutable bundle and delegates to that installer. Teach the canonical installer to consume a certified prebuilt bundle without dependency reinstall/rebuild while preserving the existing frozen source-checkout path.

**Gate:** release installation and source-checkout installation converge on the same setup, service, data-boundary and uninstall behavior.

## RP-05 — Repeatable release automation

Add permanent release verification/packaging scripts and a GitHub Actions release workflow. Release automation runs only for a merged version change on `master` or an exact retry, reruns complete verification, packages/checksums both architectures, creates immutable `vX.Y.Z`, uploads the complete asset set through a draft release and publishes only after asset completion.

**Gate:** no tag/release can point at an unmerged PR head or a different commit than the packaged assets.

## RP-06 — Public repository presentation

Bring the root README to the established Pontivus layout: centered brand plate, concise proposition/supporting text, CI/license/runtime/platform/release badges, quick-start navigation, product explanation, install path, documentation/support/security/changelog links and license.

**Gate:** README accurately describes v1 without implementation-plan language or unsupported claims.

## RP-07 — Jig visual identity

Establish canonical product identity and brand assets under `assets/`. The mark must remain legible in monochrome and provide README/light/dark/icon variants from one geometry.

**Gate:** README uses the fixed dark plate; all variants document one geometry authority and colour system.

## RP-08 — PR and release handoff

The implementation/release-prep PR declares SemVer impact **major** and target release **1.0.0**, passes permanent verification and is made ready for review. After merge, create `release/v1.0.0`; that release PR contains no new product behavior and only freezes version/changelog/release-facing metadata.

**Gate:** release publication occurs only after the dedicated release PR merges and the permanent release workflow passes.
